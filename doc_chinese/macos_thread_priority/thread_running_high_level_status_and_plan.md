## 4. macOS 的 "RT" 到底是什么（四层机制，**实测只有一层曾经生效，而它被我们自己关掉了**）

| 层 | 机制 | 现状（2026-10-01 实测，开发文档 10.5）|
|---|---|---|
| 1 | **QoS 类**（`pthread_set_qos_class_self_np`）| **能设、能生效、也能读回** —— 但**紧跟着的 `pthread_setschedparam` 会把它清成 `UNSPECIFIED`，且此后 `set_qos` 返回 EPERM（不可恢复）**。⇒ 今天**没有一条实时线程带着档**；只有不调用 POSIX 的线程（`io_timer`、`io_broker`…）留着 `USER_INITIATED` |
| 2 | Mach affinity tag（`THREAD_AFFINITY_POLICY`）| **Apple Silicon 不支持**（`KERN_NOT_SUPPORTED`）⇒ 本机**空操作** |
| 3 | POSIX `pthread_setschedparam(SCHED_FIFO, prio)` | 无特权**成功并读回**（`policy=4`、`prio=46`），内核**只记录**；★ 它的**副作用**是把第 1 层抹掉 —— 这就是 2026-09-01 那次"改了运行语义"的真正内容 |
| 4 | **Mach 时间约束**（`THREAD_TIME_CONSTRAINT_POLICY`）| 实现存在、**生产未用**；实测与 QoS **互斥**：`thread_policy_set` 成功（rc=0）但**同样把 QoS 档清 0**，且此后 `pthread_setschedparam(SCHED_FIFO)` 返回 **EINVAL** |

**一句话规则**：Darwin 上线程**要么由 QoS 管、要么是显式调度**（POSIX 参数 / Mach 时间约束），**不能两者兼有**；
显式调度那一侧会把 QoS 档**静默清掉**。我们过去**两条路都走**，先设档再抹档 ⇒ 净效果 = **无档**。
⇒ `taskinfo` 的 `UI 0.000 / IN 0.000 / ceiling THREAD_QOS_LEGACY` 由此解释完毕；
观察到的 P 核 99.55% 来自**进程级 boost/donation**（§2.2 的 `req other=boosted`），**不是**我们的 per-thread QoS。

⇒ **可选修法（需用户裁决，§10）**：`OCUDU_SCHED_SKIP_POSIX_RT=1` 跳过 POSIX 调用，让档活下来；
同一条腿里已验证两臂读数（`eff=UNSPECIFIED` vs `eff=USER_INTERACTIVE`）。P3 的 attr-QoS **单独做没有意义**（同样被抹）。

## 5. 目标与判据（**先写死**）

### 5.1 目标（四条）
1. **可测**：每条关键线程都能给出**它自己**的 CPU/调度读数（不是进程级）；
2. **可归因**：任一 max 尖峰能落到"**哪条线程 + 哪一类原因**（CPU 被抢 / 等 IO / 等同步 / 等 GPU）"；
3. **可设置**：能对关键线程施加并**回读**优先级/QoS/时间约束，且**有档位对照**；
4. **Linux/Ubuntu 逐字不变**：见 §8。

> ⚠ macOS 上**不承诺**"达到 Linux 的确定性"；本线的判据写成"**尾部率/最坏值 ≤ 登记阈值**"，并**同时记录 Linux 的同读数**作对照。

### 5.2 判据（阈值**从分布导出、飞行前登记**，不在这里拍）

★ **规则在 2026-10-01 被它自己的第一次运行推翻并已重写**（开发文档 10.4）：原来打算用 `max ≤ k×中位`，
但实测同家族 20 条腿（10 个 commit、无调度改动）里 `ce` 的 per-leg `max` 摆动 **×24**，而 per-leg `p99` 只在
**146…173 µs** 之间。⇒ `max` 是重尾的一次抽样，**不能承载判据**；`p99` 是总体的性质，**可以**。

**登记的判据（每条腿，按 regime 分别判；出处 = `wip/threshold_candidates.py`，先登记再飞，不追溯）**

   后两条的**主体本身就宽**，不是只有尾巴长；
2. **`max/min` 是用户定义的那个数**，但它同时被两端拉动：`min` 可能是一次"跳过/极快"的样本
   （`ce` min 14.9 µs、`t2f` min 61.4 µs），所以它必须与 `p95/median`、`min/median` 一起读 ——
   **低 min 与高 max 是两种病**；
3. **`t2f` 的 min 不是稳定性问题**：该序列定义上 = `[ul_rx_wait] + 前端工作`（文档已写明），
   主机"落后于电台"时 wait=0，样本就退化成纯前端工作（~60 µs）⇒ 它的 min 反映的是**接收节奏**，不是线程抖动。

**登记（前瞻，2026-10-01 第三次登记；前两版都是我对定义的误读，见开发文档 10.19/10.20/10.22）**
* **主判据 C3**：每条序列的 **`p95/median ≤ 登记值`**（主体宽度）**且 `p99/median ≤ 登记值`**；
* **读数**：`max/min`、`max/median`、`min/median` 一并打印，**由 `max` 那侧承载的部分不设阈值**（尾部归因仍由事件表负责）；
* **登记带**（baseline = p189/p190 + p181 三条腿的实测中位）：

**★ 改进目标（本线"改稳定性"的落点）**：`ce` 的主体宽度（p95/median **1.73**）—— 该段从 `t2f_end`（UL 线程）
到 `ce_end`（**池线程**），**包含线程间交棒与池排队**，所以它宽就是**池线程的调度延迟**，
正是本线优先级/调度能动的地方（`eqd` 1.19、整跳 1.16 说明池一旦跑起来并不慢）。

### 4bis. ★★ 结论（2026-10-01 收口）：`max` 不是处理时间，而是**外部停顿**

> 本节是本线的结论节：现象、已确立、已排除、未知（含重开条件）、以及"能不能让 gNB 免受系统进程干扰"的回答。
> 全部读数与出处见开发文档 §10.25–§10.28。

#### 现象（一句话）
处理链的**主体极稳**（同一次运行内 `t2f` 的 8 个窗口中位落在 **489.4–491.8 µs**、`ul_gpu_pipeline` 1242–1261 µs，
`ce` 63–68 µs），**只有 `max` 差**；而 `max` 的取值**等于该腿最大的一次外部停顿**。

#### 已确立（有读数、可复核）
1. **macOS 上我们唯一的优先级机制（QoS 类）过去从未生效**：`pthread_setschedparam(SCHED_FIFO)` 会**静默抹掉**它且不可恢复
   （再设返回 EPERM）。默认改为跳过 POSIX 后，真机上 **10/10** 条实时线程回读 `eff=USER_INTERACTIVE`。
2. **主体稳定与跨腿稳定都成立**：p99 在几条腿间落在几 % 内；`max` 与它们无关。
3. **`max` = 外部停顿**，指纹是**多序列同时停顿 + 进程 CPU 掉到 0.1–0.5 核 + 非自愿切换率掉到本腿基线的 1/10–1/16**：
   | 腿 | 时长 | ≥8 ms 停顿 | 该腿 `max`（rx/ce/eqd）|
   |---|---|---|---|
   | p190（响）| 3 min | 0 | 2.6 / 1.8 / 3.5 ms |
   | p187_2040（响）| 3.6 min | **1**（14.7 ms）| 14.7 ms |
   | p192（响+档位）| 18.5 min | **3**（8.3–11.6 ms）| 11.0 / 11.2 / 11.6 ms |
   | **p193（安静）** | 12 min | **0** | 2.4 / 1.1 / 3.3 ms |
   | **p194（安静）** | 12 min | **0** | 2.1 / 1.8 / 2.9 ms |
4. **停顿时刻与系统守护进程活动爆发吻合**（用事件自带的时刻查 `log show`）：
   `ContinuityCaptureAgent`/`bluetoothd`（BLE/接力发现 —— 正在发现**被测那部手机**）、
   `launchd`/`sandboxd`/`runningboardd`（进程创建风暴）、`deleted`/`biomesyncd`/`mobileassetd`（系统维护风暴，某 2 s 内 4 000 行）。
5. **安静机器有效且不违反反作弊**：`ce` max 11 185→**1 120 µs**、`eqd` 11 571→**2 905–3 293**、`rx_wait` 10 998→**2 116–2 442**；
   `min` **未上升**（≤1%，仍低于响腿）、`median/p95/p99` 不变或更优、`gaps=0`、契约 MET。
6. **进程级档位（`taskpolicy -l 5`）无效**（同一条腿内前后半段对比，每窗超阈 3.5 vs 3.7）——因为尾部的成因不在调度。

#### 已排除
* QoS 未生效（**已修**）；POSIX `SCHED_FIFO` 有效（它正是抹档的那只手）；Mach affinity tag（Apple Silicon **不支持**）；
* `taskpolicy -l 5`（实测无效）；"处理线程抢不到 CPU"（宿主空闲、进程已 `USER_INTERACTIVE`+boosted）；
* 观察者扰动（`sample`/`taskinfo`/`powermetrics`，§2.4）；本机自建构建对腿的污染（§10.24，纪律 11）。
* ★ **2026-09-01 回归的两个"显然"病因**（2026-10-01 晚用微基准逐条否掉，§10.29）：**参数形状**
  （`period==computation==constraint==1 ms` 实测 p50 **4.9** / max **12.1** µs，与标定形状无差别，
  16 个 spinner 的吞吐也没被抢）与**丢掉 QoS 档**（QoS 对唤醒延迟几乎无收益：p50 102.9→103.1 µs）。
  ⇒ "优先级/参数改不动 `max`"这个说法要按机制拆开：**QoS 改不动，`SCHED_FIFO` 改得动一点，时间约束改得动 700×**。

#### 未知 + 重开条件（每个都写清"怎么判定"）
| # | 未知 | 判定方法 |
|---|---|---|
| 1 | 停顿的**内核路径**：①进程被挂起 ②阻塞在驱动/内核 ③CPU 被抢 —— 三者都产生同一指纹 | ★ **1 ms 看门狗线程**（探针内、env 门控）：所有线程一起停 ⇒①；只有流水线线程停 ⇒②。**尚未实施** |

| 3 | `ce` 窗口为何对**载荷**敏感（窗口含池交棒/排队，"交棒等待 vs 池排队 vs Metal 派发"未拆开）| 在 `record_t2f_end`/`record_ce_end` 之间加更细的地标（一次小改动）|

#### ★ 能不能让 gNB 免受系统进程干扰？（用户问）

**靠"优先级"（QoS 档）：不能。** 三种机制里只有"CPU 被抢"与调度有关。腿上"宿主空闲 + 档位改了没用"
说明的是**那几条腿里 CPU 被抢不是主因**，而**不是**"优先级对 CPU 被抢无效"——这两句话此前被混为一谈。
另外两种（被挂起 / 阻塞在驱动）**没有可运行的线程可供调度**，任何 QoS/档位都无从作用。

★ **但"CPU 被抢"这一类的答案是可以**：微基准（§10.29）在 2× 超订下把唤醒尾延迟从 5358 µs 压到
**9.9 µs**，用的不是 QoS 而是 **Mach 时间约束**（唯一能向内核预留 CPU 的机制）。

⇒ 于是正确的问题变成"**我们的腿里究竟有没有 CPU 被抢**"，而这件事**当前尚未判定**：现有指纹
（进程 CPU 掉到 0.1–0.5 核、`ivcsw` 掉到本腿基线的 1/10–1/16）只能证明"**几乎没有可运行线程**"，
**挂起 / 驱动阻塞 / 被抢光这三者不可区分**（§10.28 已更正过这一点）。
这正是"**1 ms 看门狗线程**"要回答的问题 —— 也是 P4 即便要飞，也应当**同时带看门狗**去飞的理由：
否则腿若变好，我们分不清是"约束挡住了抢占"还是"那几段本来就没人抢"。

### 5.4 ★★ 本线的**最终目标与判据**（用户 2026-10-01 定调）

## 6. 三层测量（由内到外）—— **三层都已实现**

1. **线程级（新，已实现）**：`ocudu::this_thread_sched_snapshot()` —— 关键线程读**自己**的 CPU / 运行态 / 请求档 vs 实际档。
   macOS：`THREAD_BASIC_INFO` + `pthread_get_qos_class_np()`；Linux：`RUSAGE_THREAD`。**平台上给不出的字段是 `-1`，不是 0**
   （macOS 上**没有** per-thread 切换计数 —— SDK 已核；Linux 上**没有** QoS 概念）。
2. **事件级（已扩展 `OCUDU_UL_TIMING_EVENTS`）**：最慢 K 条现在带 **`thread=<名字>#<id>`**、
   **`tcpu=<本线程窗口内 CPU>`**（与进程级 `cpu=` 并列）、**`ivcsw_rate=`**（切换/ms）+ 报告头一条 `leg :` 基线速率；
   **`ce`/`ldpc`/`t2f`/`eqdem` 四条相位序列的尾部接进同一机制**（每序列一个 floor）。判读写在报告头：
   `cpu=12.00ms tcpu=0.00ms` = 这条线程丢核；`cpu=0.00ms` = 整个进程没跑；两者 ≈ `win` = 线程一直在跑（活儿/IO 慢）。
3. **平台旁观（零代码，已固化成腿配方）**：`wip/observe_threads.sh`（**默认 light**；`--heavy` 才 taskinfo/powermetrics/sample，
