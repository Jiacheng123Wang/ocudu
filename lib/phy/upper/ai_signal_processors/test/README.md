# `ruler_s2_amc_5000` — 交付比特比较的**尺子**

一组**固定不变的 5 000 个接收样本**，用来把**任意接收机**放在同一把尺子上比较：
经典 PUSCH 链、depth3 的各个模型、以及将来的任何候选。

**它不是训练数据，也不是回归测试集。** 它只有一件事要做：让"谁的接收机更好"这个问题**可以被回答**，
并且**换个时间、换个模型、换个人来跑，都得到可比的数**。

---

## 1. 为什么需要它

### 1.1 我们原来用错了尺子

在这把尺子之前，模型对比用的是 dump 的 `crc=OK` 子集。那个子集是**经典链**跑出来的，
所以它**按定义**是"CPU 能解的接收"——经典链在那个子集上是 **100%，那是构造使然，不是测量**。
网络在那里得到的 95.87%，被读成"比 CPU 差 4 个点"，而它其实是在一个**为对手量身挑过的总体**上考的。

### 1.2 而且量错了东西

同一个比较用的是**块数**。但块的大小差三个数量级：一个 10 000 比特的 CB 和一个 100 比特的 CB
都记作"一个 OK"。在本尺子的总体里，**≥500 字节的块只占块数的 33.8%，却贡献 54.4% 的比特**。
按块计数的尺子会系统性地低估大块，而大块正是高速率调制与宽分配产出的东西。

**正确的量是交付的比特数**（goodput）：`crc=OK` 的块各自 `tbs_bytes × 8` 求和。

### 1.3 三次测量事故，这把尺子要防的就是它们

| # | 事故 | 后果 |
|---|---|---|
| **1** | 样本按被比较一方的判决筛过 | 那一方 100%，结论反向 |
| **2** | 用块数代替比特数 | 大块被低估，方向被块大小分布带偏 |
| **3** | 两个 replay 进程并发 | 数据被互相覆盖（出现 −36 dB 的 SINR），结论**符号翻转** |

第 3 条是这条尺子**为什么必须串行、必须带守卫**的原因。

## 2. 结论摘要（截至 2026-11-03）

**在 5 000 个未按 CRC 过滤的单元上，两条臂（经典链 vs depth3）的交付比特：**

| 臂 | 交付比特 | 块率 | bits/单元 | 中位耗时 |
|---|---|---|---|---|
| 经典链（`--pusch_receiver_backend classic`） | **8 933 800** | 69.30% | 1 786.8 | 0.210 s |
| E4（depth3，PURE） | **8 844 864** | 68.58% | 1 769.0 | 0.450 s |
| **差** | **−88 936（−1.00%）** | −0.72 pp | | +2.14× |

**bootstrap 95% 置信区间 [−248 928, +70 120]（含 0）、McNemar p = 0.108 ⇒ 统计上打平。**
经典链名义领先 1%，但**样本只能排除约 2.8% 以上的差异**——所以"打平"的准确含义是
**"没有证据说它们不同"**，不是"证明相等"。

**方向性上网络确实救回了一些单元**：只有经典链能解 **255** 个（893 096 比特），
**只有网络能解 219 个（804 160 比特）**。后者多是**窄带 256QAM**，即 GPU 流水线的弱项。

**长短板的形状很清楚**：网络在高 SNR 上**明显更强**（≥30 dB：**97.3% vs 64.4%**），
弱在 **256QAM × 窄带 × 20–30 dB**（全部缺口 −105 560 比特都在这里）。

**另一条独立的实验（四个互不相交的重采样集，10 228 个单元）**给出模型的相对次序：
**E4 与 E17 统计上不可分**（合并 +0.16 pt、p = 0.30、CI 跨零），
**W2-cond 确实最差**（落后 6.8–8.1 pt、p ≈ 2×10⁻²¹¹、从不翻转）。

## 3. 内容

```
ruler_s2_amc_5000/
├── corpus/                  # 5 000 × (<unit>.txt + <unit>.bin)，真副本，无 symlink
├── units.txt                # 5 000 个单元名
├── index.csv                # 这 5 000 个单元在 dump 里的行（crc / tbs_bytes / sinr_db / iterations）
├── clean_cpu.csv            # 经典链的逐单元结果（参照答案）
├── clean_ai.csv             # E4 的逐单元结果（参照答案）
├── prep_sample.py           # 当年怎么抽的（可复现）
├── SHA256SUMS               # 10 000 个 corpus 文件的校验和
└── README.md                # 本文件
```

**`SHA256SUMS` 里的 10 000 条 = 5 000 个 `.txt` ＋ 5 000 个 `.bin` 的校验和**
（不是单元数与索引数相加）。校验：

```bash
cd ruler_s2_amc_5000 && shasum -a 256 -c SHA256SUMS
```

### 3.1 为什么只有两个文件

`ul_chain_replay <base>` 只打开 `<base>.txt`（PDU 侧车）与 `<base>.bin`（接收网格）。
采集目录里另有 `_h.bin`（逐符号信道）与 `_ce.txt`（估计器标量），那是**分析的产物，不是重放的输入**。
证据：官方测试集 `replay_test_s2_amc_a/corpus/` 里每单元恰好只有 `.txt` 与 `.bin`，而它跑得通。

### 3.2 怎么重建这把尺子

原始语料（`s2_amc_ping_1102a`，50 000 个捕获）还在时：

```bash
python3 prep_sample.py        # 均匀抽 5 000，seed 20261102，不按 CRC 过滤
```

然后按 `units.txt` 从语料里取 `<unit>.txt` 与 `<unit>.bin` 即可。

## 4. 怎么用

### 4.1 跑一条臂

```bash
cd ruler_s2_amc_5000

# 经典链
ul_chain_replay corpus/<unit> --out /tmp/c --metal --phy_pipeline gpu --pusch_receiver_backend classic

# depth3 模型（PURE 模式）
OCUDU_DEPTH3_FALLBACK=none OCUDU_REPLAY_MODEL=<bundle>.mlmodelc \
  ul_chain_replay corpus/<unit> --out /tmp/a --metal --phy_pipeline gpu --pusch_receiver_backend ai
```

`.mlmodelc` bundle 旁边**必须有** `depth3_scales.txt`；`.keras` 走 TensorFlow 路径也能跑，只是慢。

### 4.2 四条硬要求

| # | 要求 | 不做会怎样 |
|---|---|---|
| **1** | **`OCUDU_DEPTH3_FALLBACK=none`** | 网络拒收/放弃的单元会被经典链接手，两条臂不再独立，测的变成"经典链+网络帮忙" |
| **2** | **`depth3_scales.txt` 与 bundle 同目录** | 静默退回默认标定，比较不再是**模型之间**，而是"模型 vs 默认标定" |
| **3** | **每单元一进程、串行** | 两个 replay 并发会**互相覆盖信道数据**（实测：10/198 翻转、出现 −36 dB 的 SINR） |
| **4** | **守卫：每单元前查一次有没有第二个 replay** | 同上。守卫**必须先被看到真的触发过**再用（用一个冒充 argv[0] 的进程试） |

### 4.3 算分

```
交付比特 = Σ (crc=OK 的块的 tbs_bytes × 8)
块率     = crc=OK 块数 / 总数            ← 保留作对照，但不要用它下结论
```

**置信区间**：对单元做**有放回重采样**（每次抽 5 000 次，同一个单元可能被抽 2 次、另一些一次不中），
对每遍重算总差，取中间 95%。**注意**：每次重采样是"抽 5 000 **次**"，不是"取那 5 000 个"——
后者每遍都一样，毫无意义。典型只有约 **63%**（1 − 1/e）的单元会出现在某一遍里。

**配对检验**：McNemar，**只用两条臂判决不一致的单元**（本例 255 : 219），"都对"与"都不行"不提供信息。

## 5. 已知边界（不要误读）

| 项 | 说明 |
|---|---|
| **439 / 5 000（8.78%）是重传** | `new_data=0`，两条臂都无法使用（`cannot reserve a receive buffer`），0 比特 |
| **5 / 5 000 是 1-PRB** | depth3 的分配下限现已改为 **1**（默认不拒收）；此前按 2 PRB 拒收 |
| **约 31% 的单元经典链也解不出** | **这是有意的**：否则就是让 CPU 当裁判又当选手 |
| **绝对率随调制构成变化** | 本尺子的 256QAM 占比约 38%，不要与"QPSK/16QAM 为主的小样本"上的数直接对比 |
| **耗时受机器负载影响** | `bits/s` 只能作同批次内的相对值，不是调优基准 |
