# macOS 上 PHY 信号处理的**实时性保证** —— 审查与详细规划

> 状态：规划（v1.0，2026-10-02）
> 定位：在既有 P0–P4 工作**之上**的完整规划。回答一个问题：
> **在 macOS 上，"保证 PHY 信号处理的实时性"到底能保证什么、怎么保证、先做哪一步。**
>
> 本文做了三件既有文档没做的事：
> ① 把"实时性"变成一个**已有的、可测的操作性定义**（`[dl_tx_slack]` + 四个率），而不是一句愿望；
> ② 指出**三个杠杆各治一种停顿，而调度只治其中一种** —— 并据此**重排优先级**：先装看门狗判种类，
>    再决定投哪个杠杆（这与"先上 P4"的默认顺序不同）；
> ③ **一处新归因**：`lower_phy_*` 的 "0/12" 闸门是**loopback 台架流控的伪影**，机制已定位到三处代码 ——
>    而它挡住的正是**承载用户观察到的 `[ul_rx_wait]` 尾部的那三条线程**。
>
> 关联（本目录）：`thread_running_high_level_status_and_plan.md`（§4bis 收口、§5.4 目标）、
> `thread_priority_optimization_design_and_implementation.md`（§10.29–§10.33）、
> `wip/sched_microbench/README.md`（杠杆表、loopback 臂扫描）。
>
> **⚠ 引用规则（沿用本目录 README）**：一台仪器两把钥匙（编译 + env，默认关，关着逐字节不变）；
> 每个新字段要有反向臂；**判据先登记再飞且不追溯**；Linux 逐字不变；
> 引用"停顿/尾部"必须同时给 `cpu`/`win`/`ivcsw`/`base_age` + 同秒的 `[RF]` 行。

## 0. 一句话

> **macOS 给不了"有界最坏延迟"，所以"保证实时性"在这里只能有一个含义：**
> **把"错过截止期的比例"做成一个有界、可测量、可归因的量，并把它压到可接受的水平。**
>
> 好消息是：**这个量已经存在、已经在测、已经有界**——
> **`[dl_tx_slack]` 的余量分布 + `AT/BELOW 0` 率 + `slip`/`recv` 率 + `gaps`**。
> 实时性的操作性定义**不是"一个 slot 内跑完"，而是"在电台要样本之前交出去"**。
>
> **⇒ 于是规划的骨架是**：先装**看门狗**判定停顿属于哪一类（①进程被挂起 ②阻塞在驱动 ③CPU 被抢），
> **因为三个杠杆只治其中一种**；再按判定结果投杠杆；而**余量**（而不是优先级）才是吸收残余停顿的那个东西。

## A. "实时性"在本项目里的**操作性定义**（已存在，不必发明）

### A.1 四个已经登记的判据

| 量 | 代码/出处 | 含义 | 当前界限 |
|---|---|---|---|
| **`[dl_tx_slack]`** | `lib/phy/lower/lower_phy_baseband_processor.cpp:72-125` | **每次 DL TX 交棒时还剩多少余量**（相对电台要样本的时刻）。median **≈1.5 ms** | `AT/BELOW 0` = 交棒时刻 **≥ 截止期** |
| **`AT/BELOW 0` 率** | 同上；`leg_gate.sh` | **错过 DL 截止期的比例** | **≤ 0.0005%**（计数界 10 已改率，§10.33(1)） |
| **`slip` / `recv` 率** | 同上 + 传输层计数 | 传输/收包迟到 >1 ms 的比例（"传输风暴"） | **slip ≤ 0.0005% / recv ≤ 0.0004%** |
| **`gaps`** | `radio sample continuity` | 接收流不连续 | **0** |

**⇒ 这就是"实时性"的定义。** 它包含三层含义，缺一不可：
① **余量**（`slack` 的分布，中位数与 p1）；② **超阈率**（`AT/BELOW 0`、`slip`/`recv`）；
③ **可归因性**（`[dl_tx_call]` 把"我们交晚了"与"电台/驱动晚了"分开）。

### A.2 ★ 一条把"归因"写进仪器的注释（值得逐字引用）

`lower_phy_baseband_processor.cpp:80-83`：

> This is the number an `underflow` should correspond to: **a leg with `AT/BELOW 0 = 0` here and UHD failures
> in its log says the lateness is INSIDE the radio or its driver, not in this hand-over.**

**⇒ 这条区分是整个规划的基础**：它把"实时性问题"劈成**我们的责任**与**平台的责任**。
而 `[dl_tx_call]`（`transmit()` 调用本身多久）进一步劈开**驱动/USB**与**UHD 自己的 worker 线程**：

> If `transmit()` itself blocks for milliseconds, the radio or the USB link is pushing back **inside the call
> (and no host scheduling change can help)**; if it returns at once, the samples are sitting in UHD's own queue
> and **its worker thread** is the one that is late.

★ **"no host scheduling change can help" 这句话，就是本规划要求"先判定再投杠杆"的代码级依据。**

### A.3 余量预算（把"保证"变成算术）

```
电台要样本的时刻
   ▲
   │  ← [dl_tx_slack] 余量（median ≈1.5 ms）─── 这是吸收停顿的**唯一缓冲**
   │
交棒时刻（lower_phy_tx 调用 transmit()）
   ▲
   │  ← DL 处理 + 调度延迟
DL 处理开始
```

**⇒ 结论**：**停顿只要小于余量，就不产生 `AT/BELOW 0`。**
所以"保证实时性"有两条等价的路：

| 路 | 做法 | 本项目的现状 |
|---|---|---|
| **(a) 减小停顿** | 环境 / 调度 / 架构三杠杆 | 环境已验证（4–5×）；调度已有机制未判；架构未评估 |
| **(b) 增大余量** | 更早开始（收包粒度）、更快处理（GPU 车道）、更宽的池 | 部分已做（`[ul_rx_wait]` 的整槽等待就是 (b) 的反面） |

**★ 并且 (a) 与 (b) 必须一起读**：用户观察到的 `[ul_rx_wait]` 尾部（**10 998 µs**，安静机器
**2 116–2 442 µs**）说明**停顿的量级（~10 ms）已经超过余量（~1.5 ms）**——
这正是"偶尔丢"的算术来源。

## B. 三种停顿 × 三个杠杆（★ 本节是本规划的核心）

### B.1 三种停顿，指纹相同

`§4bis` 的"未知 #1"（**未解决**）：

> ① 进程被挂起 ② 阻塞在驱动/内核 ③ CPU 被抢
> ——**三者产生同一指纹**：进程 CPU 掉到 0.1–0.5 核 + `ivcsw` 率掉到本腿基线的 1/10–1/16。

**⇒ 判定方法（`§4bis` 已给出，尚未实施）**：**1 ms 看门狗线程**。
所有线程一起停 ⇒ ①；只有流水线线程停 ⇒ ②。

### B.2 ★ 三个杠杆只治其中一种

| 杠杆 | 治 ①挂起 | 治 ②驱动阻塞 | 治 ③CPU 被抢 | 实测效果 | 代价 |
|---|:---:|:---:|:---:|---|---|
| **架构**（余量 / 池 / 路由） | ✅ | ✅ | ✅ | **未量化** | 设计改动 |
| **环境**（安静机器） | ⚠️ 间接 | ✖️ | ⚠️ 间接 | ce max **11 185 → 1 120 µs**；eqd 11 571 → 2 905–3 293；rx_wait 10 998 → **2 116–2 442**；**`min` 未升** | **零**（部署要求；已验证） |
| **调度**（Mach 时间约束，P4） | ✖️ | ✖️ | ✅ | 微基准唤醒尾延迟 max **5358 → 9.9 µs（540×）** | 丢掉该线程的 QoS 档（`§10.29`：这笔代价可接受） |

**⇒ 三条必须同时说出口的话：**

1. **调度只治"CPU 被抢"。** 被挂起的进程**没有可运行的线程**，驱动阻塞**在别的线程里**——
   两者都**没有可调度的对象**。任何优先级/预算机制对它们**无从作用**。
   （这正是 `§4bis` 的更正："优先级改不动 `max`"只对 **QoS 档**成立，对**时间约束**不成立；
   而"能不能免疫系统进程"的答案要按**停顿种类**分，不能整句回答。）
2. **环境杠杆已被证明有效且零代价** —— 它是唯一**已验证**的一个。
3. **我们连腿里是哪种停顿都还不知道** ⇒ **先装看门狗**。

### B.3 由此得出的顺序（**与默认顺序不同**）

> **默认顺序**：P4 已实现 → 先飞长腿对（`p198`/`p199`）判 `max`。
> **本规划的顺序**：**先装看门狗**，与 P4 长腿对**同构再飞**。
>
> **理由**：`§4bis` 自己写了——"**P4 即便要飞，也应当同时带看门狗去飞**：
> 否则腿若变好，我们分不清是'约束挡住了抢占'还是'那几段本来就没人抢'。"
>
> **这不是推翻 `p198`/`p199`**（它们的判据已登记、安全性与反作弊已成立、值得飞），
> 而是**加一条前置**：**看门狗的规格与反向臂先登记，与长腿对一起飞。**

## C. 三个杠杆的详细规划

### C.1 杠杆一：环境（**已确立，零代价，先固化**）

| 项 | 内容 |
|---|---|
| 做法 | 腿期间关蓝牙/接力/Spotlight；不跑别的负载；不跑自建构建（纪律 11，§10.24 的一次作废就是它） |
| 证据 | 两条安静长腿 p193/p194：**≥8 ms 的停顿 0 次**（响腿 p190/p187/p192 是 0/1/3 次），`max` 降 3–10×，`min` **未升**（反作弊） |
| 归因 | 停顿时刻与 `ContinuityCaptureAgent`/`bluetoothd`（**正在发现被测那部手机**）、`launchd`/`sandboxd`/`runningboardd`、`deleted`/`biomesyncd`/`mobileassetd` 的活动爆发吻合（用事件自带时刻查 `log show`） |
| **尚未解决** | 残余 **1.7–2.2 ms** 小停顿（已定位到 `launchd`/`runningboardd`/`mDNSResponder`）⇒ **受控实验：逐项关掉/避开，看计数是否下降** |

**★ 对"保证"的意义**：这是**部署要求**，可以写进产品文档：
**"本节点要求宿主在 PHY 运行期间不执行后台发现/维护类活动。"**
⇒ 它把"平台不给实时性"变成"**我们声明运行环境**"，这是工程上可交付的承诺。

### C.2 杠杆二：调度（**Mach 时间约束 = 唯一能向内核预留周期性 CPU 的机制**）

#### C.2.1 机制与可证性（已在代码里，默认关）

| 项 | 内容 |
|---|---|
| 接口 | `include/ocudu/support/scheduling/darwin_thread_scheduling.h`：`darwin_thread_time_constraint{period, computation, constraint, preemptible}` / `set_this_thread_time_constraint()` |
| 臂 | `OCUDU_SCHED_TIME_CONSTRAINT`（`utils/macos_compat/macos_compat.cpp:148`），**默认关 = 逐字节不变**；语法 `unset/0` / `1`/`default` / `NAME=P/C/K[;…]`，`NAME=*` 匹配全部 |
| 可证 | 每条被选中的线程打 `[sched_tc]`；`[sched]` 行多 `tc=` 字段 |
| 拒绝的形状 | 实现里**拒绝** `constraint < computation`（唯一实测有害：p50 793 µs / max 7.3 ms）与 `period < constraint` |
| **必然的代价** | 施加即**抹掉该线程的 QoS 档**，不可恢复（`§10.29`） |

#### C.2.2 逐线程规划

| 线程 | 是否约束 | 依据 | 参数 | 备注 |
|---|---|---|---|---|
| **`main_pool#0..#4`** | ✅ **第一批**（loopback 3/3 干净） | `ce`/`t2f` 的载体；实测**占空 ≈6%** | `5000/1000/2000` µs（**≈3× 宽裕**） | 唯一代价是丢 QoS 档，而该档在此指标上只有 1.6× |
| `io_timer_tick`+`io_broker_epoll` | ✅ 可选（3/3 干净） | 支持面里唯一有周期语义的两条 | `5000/500/1000` | 池线程判绿之后再单独飞 |
| **`lower_phy_rx#0`** | ⏸ **待 §D.1 判定** | ★ **用户观察到的 `[ul_rx_wait]` 尾部就在这条线程上**；现在被一个已被归因为**台架伪影**的闸门挡着 | 待定 | **本规划最重要的待解锁项** |
| `lower_phy_ul#0` | ⏸ 同上 | 承载 host 变换 + 交棒 | 待定 | 同上 |
| `lower_phy_tx#0` | ⏸ 同上 | `[dl_tx_slack]` 的载体 | 待定 | 真电台上无 spin 伪影，但**只能上电台判** |
| `radio` | ⏸ 第三批 | `single_b`（池+radio）3/3 干净 ⇒ **可以**；但是 UHD 异步线程，收益未测 | — | — |
| `ru_timing` | ❌ | 时基线程，无归因目标 | — | — |
| `phy_worker`/`phy_exec`/SCTP×5/main | ❌ **不给** | `no_realtime()` 支持面；给它们预算会**减少**关键线程的预算 | — | 与"减少调度对象"同向 |
| **全部 11 条（`*=`）** | ❌ **禁止** | **已证伪**：loopback 3/3 崩 + 2026-09-01 回归 | — | 纪律，不是偏好 |

#### C.2.3 参数取值

| 规则 | 依据 |
|---|---|
| **`constraint >= computation`** | 唯一有害形状是反向（p50 793 µs / max 7.3 ms）；实现已拒绝 |
| **`period >= constraint`** | 自相矛盾；实现已拒绝 |
| **报大免费** | 持续超额 **4.6×**、周期内突发 **3×** 都不被惩罚 ⇒ **宁可报大** |
| **不要给所有线程同一参数** | 会把 FIFO 优先级（44/45/46）编码的**线程间次序拍平**——§10.29 里唯一未被微基准否掉的病因 |
| **占空 ≈6% 是唯一实测值** | `[ul_thread_cpu]`：对照与臂**换算后都是 ≈6%**（mean 随 PUSCH 率变，**必须比占空/速率，不能比 mean**） |

#### C.2.4 ★ `preemptible`：一个**从未被变动过**的维度

`darwin_thread_time_constraint` 的第四个字段 `preemptible` 在头文件里的语义是：

> A **non-preemptible** thread is **not interrupted by lower-priority work (e.g., network I/O)**
> while it has computation budget left.

**而它在代码里硬编码 `true`，且不在臂的语法里**（默认形状与 `parse_time_constraint_values()` 都写死 `true`）。⇒

* **P4 的 540× 是在 `preemptible=true` 下拿到的** ⇒ **"有保障的预算"本身就够，不需要"不可抢占"。**
  对交付是**好消息**：不可抢占会给面向电台的线程带来真正的优先级反转风险。
* **"更硬的预留是否更好"是未测维度** ⇒ 登记为**未变动维度**（而不是让它继续隐式）。
  只有当池线程的尾部率目标达不到时，才单独开这个臂。

### C.3 杠杆三：架构（**唯一能治全部三种停顿的杠杆，也是唯一没被评估过的**）

**原则**：**停顿不可消除，余量可以设计。**

| 手段 | 治什么 | 现状 / 待办 |
|---|---|---|
| **收包粒度**（符号粒度 vs 整槽） | 直接减少 `[ul_rx_wait]`（**整槽 ⇒ 结构性等一个 slot**） | ★ 这是**最大的单项**：用户 log 里 `[ul_rx_wait] mean=496.2 µs / median=473.0` ≈ **一个 slot（30 kHz = 0.5 ms）**。S-7g-13 已提出该路线，**未做** |
| **接收池水位与三种状态** | 吸收突发 | 已有：`free_min ≥2` OK / `==1` TOUCHED / `==0` **DRAINED**；池大小 = 流水线跨度（`max(8, …)`） |
| **路由**（URLLC→CPU / eMBB→GPU） | 让时延敏感业务**不排队** | 已有模式（`phy_pipeline`），未做按业务类型的分流 |
| **余量监控** | 让"余量被吃光"可见 | `[dl_tx_slack]` 已有 `below_2ms/1ms/500us` 三个阈值计数 ⇒ **把它们变成率并登记为判据** |
| **减少调度对象** | 减少被抢的概率 | 未试（池并发与交付形态绑定） |
| **1 ms 看门狗** | 判定停顿种类 | **未实施**（见 §D） |

**★ 为什么架构是"保证"的真正来源**：`[dl_tx_slack]` median ≈1.5 ms，而观察到的停顿最大到 **14.7 ms**。
**停顿 > 余量 ⇒ 必然丢。** 所以要么把停顿压到余量以下（环境+调度），要么把余量做大到停顿以上（架构），
**两者是乘法关系，不是替代关系。**

## D. 必须先做的一件仪器：**1 ms 看门狗**

**没有它，本规划的两个杠杆（调度、架构）都无法判定该不该投、投了有没有用。**

| 项 | 规格（建议） | 理由 |
|---|---|---|
| 周期 | **1 ms** | 与停顿的观测尺度匹配（8–14.7 ms 里应有 ~10 次采样） |
| 落点 | `OCUDU_FLOW_PROBES` 编译 + env，**默认关** | 两把钥匙 |
| 记录 | 每次唤醒的**迟到量**（实际间隔 − 1 ms），log2 直方图（40 桶）+ max | 与 `[ul_thread_cpu]` 同形 |
| **反向臂** | 探针里人为 `sleep(20 ms)` ⇒ 直方图必须出现 20 ms 桶且 `late_max` 变大 | 纪律 79 |
| **判读** | 看门狗迟到**与**被观测序列的停顿**同时**发生 ⇒ **①进程被挂起**；**只有后者** ⇒ **②驱动阻塞**或**③CPU 被抢**（这两者再用"宿主是否空闲 + 进程 CPU"分开） | 这正是 `§4bis` 未知 #1 的判定 |
| 额外 | 把看门狗**自己**也纳入 `[sched]`（不给约束） | 它的迟到是被测量对象，不是参与者 |

## E. 新归因：`lower_phy_*` 的 "0/12" 是**台架流控伪影**（★ 解锁 `[ul_rx_wait]` 那三条线程）

### E.1 事实

`wip/sched_microbench/loopback_arm_sweep.sh`：

| 臂 | 约束的线程 | 干净 | 崩溃 |
|---|---|---|---|
| 不设 / `pool5` / `io2` / `single_b` | — / 池 5 / io 2 / 池+radio | **3** | 0 |
| **全量 `*=`** | 全部 11 条 | 0 | **3** |
| **`lower3`**（+ `_min`/`_hist`/`_loose` 三种形状，含 **2.5% 占空**） | `lower_phy_tx/rx/ul` | **0** | **3** |

崩溃永远是同一句（生产者跑到消费者前面）：

```
OCUDU FATAL ERROR: Attempting to write samples [...] that would overwrite unread sample [...]. buffer size: 2304000
```

工作流的结论是"**不是参数，是线程**"，并把这条闸门当作**上电台前的便宜闸门**。**本文更正后半句。**

### E.2 机制：loopback 的 TX **按墙钟配速、按读者进度断言**，中间借了 OS 的调度

三处代码（`lib/radio/realtime_loopback/`）：

| # | 代码 | 依据什么 |
|---|---|---|
| ① | `radio_session_realtime_loopback_impl.cpp:196-206`："block until that's no longer the case" —— `while (last_requested > get_current_rf_timestamp() - tx_processing_delay + max_nof_buffered_tx_samples) { sleep_for(1 µs); }` | **墙钟**：`get_current_rf_timestamp` 由 `ts0_epoch = steady_clock::now()` 派生（同文件 `:29`） |
| ② | `loopback_buffer.cpp:31-38`：`report_fatal_error_if_not((timestamp + nof) - last_rx_ts <= buffer.get_nof_samples(), …)` | **读者进度**：`last_rx_timestamp` |
| ③ | ① 的等待体是 `sleep_for(1 µs)` 自旋 | **OS 调度器**：它假设"这 1 µs 的让出里读者会被调度并推进 `last_rx_timestamp`" |

**⇒ 三件事凑成一个隐含假设**：写者的**墙钟配速**与读者的**实际进度**在正常调度下**恰好同步**——
而这个"恰好"是**借来的**。

**⇒ 给写者一份有保障的 CPU 预算 = 收回这笔借来的调度**：被约束的线程唤醒变准时（微基准 p50 3.2 µs）、
预算有保障 ⇒ `sleep_for(1 µs)` **不再有效地让出** ⇒ 写者通过墙钟检查（①）而读者尚未推进（②）⇒ **FATAL**。
**这解释了为什么连 2.5% 占空的 `2000/50/100` 也 0/3 —— 不是"要了多少 CPU"，是"拿得太准时"。**

### E.3 这改变了闸门的性质

| 旧读法 | 新读法 |
|---|---|
| "`lower_phy_*` 这三条线程**不可以**被约束" | "**在这套 loopback 台上**，约束它们会抽掉写者自旋所依赖的让出" |
| 闸门是**线程属性**的判据 | 闸门是**台架流控**的判据 |
| 可以作为"上电台前的筛子" | ★ **不能**，而方向可能是**反的**：真电台的 TX 路径**不 spin**（`lib/radio/uhd/radio_uhd_tx_stream.cpp` 无 `sleep_for`，配速来自驱动/硬件） ⇒ **真电台不需要借 OS 的调度来配速，那个伪影不存在** |

### E.4 一个便宜的判定实验（**建议先做**）

**改法（只改台架，不动产品路径）**：把 ① 的等待条件从"墙钟超前量"改为"**与 ② 逐字一致的读者进度**"
（条件变量在读者 `store` 后唤醒，或退一步 `while (… last_rx_ts …) { yield; }`）。

**判据（可判定）**：

| 观察 | 判定 |
|---|---|
| 改后 `lower3` **3/3 干净** | ⇒ 约束无罪，**台架流控**是元凶 ⇒ "`lower_phy_*` 不可约束"**作废**，三条线程进入规划范围 |
| 改后仍 **0/3** | ⇒ 约束确与这三条线程的产品语义冲突 ⇒ 保留"不可约束"，并做更深的机制分析 |
| 改后**不设约束**的臂仍 3/3 干净 | ⇒ 反向臂：**先证明改法不破坏对照臂** |

**成本**：无电台、无 UE、无 sudo，**18 s/轮 × 3 轮**。**这是本规划里性价比最高的一条。**

## G. 不做的事

| ❌ | 为什么 |
|---|---|
| **`*=` 全量约束** | loopback 3/3 崩 + 2026-09-01 回归；**已证伪** |
| **把 loopback 闸门当"上电台前的筛子"** | 它筛的是**台架流控伪影**（§E.2），不是线程属性；真电台的 UHD TX 路径不 spin |
| **在同一对腿里改两件事** | 2026-09-01 正是"约束 + 范围"一起改，导致归因拖了很久 |
| **用 `max` 当短腿判据** | 重尾里的一次抽样：3 min 腿 `ce` 超阈各只有 **1 个**（64852/34554 样本）⇒ 无功效 |
| **先投调度、后判定停顿种类** | 三个杠杆只治一种；`§4bis` 自己要求"P4 要飞就带看门狗" |
| **把"优先级"当一个整体回答"能不能免疫系统进程"** | 按**停顿种类**分开答；被挂起/驱动阻塞**没有可调度对象** |
| **给支持面线程发预算** | 会减少关键线程可用的预算 |
| **拿 `cpu=`（进程口径）当线程预算** | 窗口 1.3–1.8 ms 却记到 4.4–6.9 ms。**用 `[ul_thread_cpu]`** |
| **动 `preemptible`** 除非目标达不到 | 会让"网络 I/O 抢不动我"成为事实；540× 是在 `true` 下拿到的 |

## H. 诚实清单

| 项 | 现状 |
|---|---|
| **"有界最坏延迟"** | **macOS 给不了，本规划也不承诺。** 承诺的是**有界的超阈率**（`AT/BELOW 0`、`slip`/`recv`、`gaps`）+ **可归因性** |
| **停顿种类（`§4bis` 未知 #1）** | **未判定**。看门狗未实施 ⇒ 步 2 之前的结论都只能是"臂安全"，不是"臂有效" |
| **`[dl_tx_slack]` 的三个阈值计数尚未变成率** | `below_2ms/1ms/500us` 已存在，但**未登记为判据**（其余三条已是率）。建议与步 2 一起登记 |
| **§E.2 的机制** | 三处代码是**读出来的**；**"约束抽掉让出"这一步是推论**，由 §E.4 判定。**不要把推论当结论引用** |
| **`[ul_thread_cpu]` 只在池线程上有数** | 记账落在 `record_ce_end()`，只在池线程上 ⇒ `lower_phy_*`/`radio`/`io_*` 的每 slot CPU **未测**，§C.2.2 的参数栏只能是"待定" |
