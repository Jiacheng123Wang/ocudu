> 活文档（可重写）。现状读数与证据见 `00_status.md`；仪表与复跑配方见 `02_measurement.md`。
> 立项日期 **2026-09-24**；立项依据：重上行腿（`s78/s80/s82`）上 **`gpu` 抽干 8 个接收缓冲 ⇒ 接收线程被阻塞 ⇒ 电台 underflow**，

## 1. 预算分解（优化对象的量化锚点，腿 `s82`，中位 µs）

> 下面这张表是**按工作量归属**重写后的版本——它才是优化要用的一张表。

```
一跳的串行链（中位，加总 ≈ 跨度 2675）：

  A  ≈ 473 µs  等本槽最后一个样点（receiver.receive()；整槽收包策略）   ← 电台时序，结构项
  B  ≈  48 µs  前端主机工作（14 次 encode + 交棒记账 + 通知入队）        ← 宿主
  C  ≈ 901 µs  等到单车道空出来（前一跳的车道窗口还没走完）            ← 单车道串行  ★最大可攻击项
  D  ≈1125 µs  本跳设备执行（DFT+CE+EQ+demap；busy 占驻留 97%）        ← GPU 算力     ★第二大

设备/资源侧：residency ≈1125（≈D）、busy split merged_hop 1030 + ch_wt 37、
             车道占用 58.8%、可服务 886 跳/s vs 需求 520.5 跳/s。
接收缓冲持有期 = 整个跨度；池 8 个 × 每槽 1 个 ⇒ 4 ms 抽干。
```

### 5.2 ★ 用户裁决（2026-09-24）：**V4 只约束交付，测量臂放行**

C 项（901 µs，单车道排队）与 D 项（1125 µs，本跳执行）是**同一个串行链的两半**，而它们只有两个互斥的打开方式：

* **形态 1 —— 提高并发度（P2-F）**：不减少 GPU 工作量，让第二条跳的设备执行与第一条重叠。
  代价：**在飞命令缓冲数上升 ⇒ 可能碰 V4（`cbs/lane ≤ 2.00 (max=2)`、`dropped == 0`）**；
  且 LDPC 解码器与车道**共用同一条后端口队列**（`ocudu_metal_queue.h:52-61`、decoder 引擎 `:298`）⇒ 并发跳也可能把解码挤到后面。
* **形态 2 —— 缩短单跳窗口（P2-B/E/A）**：不增加在飞数，靠减少 GPU 工作或提前启动。
  代价：已知贵项（K1 197 / 抽取 117 / 重排 117 µs）被"**逐字节不变**"钉住；
  用户已在 §5.8.19 ① 放宽过该约束（"逐字节不变太严格… 最根本的是算法逻辑正确、误差在一定范围内"），
  但**每一次用这个自由度的改动都必须飞一条空口腿**。

**裁决（用户，本轮）**：

> **V4 只约束交付；允许把 P1-8 作为纯测量臂先跑。**

⇒ 落地方式：
1. **先做 P0-6**（把生效并发度打出来）——否则这条臂在 n78 上可能无处施力（若生效值已是 3，它不是 strand）；
2. P1-8 的读数**只用于回答"并发度能不能吃掉 C 项"**，与 V4 无关；
3. **若要把并发度作为交付**（P2-F），**必须回到用户再裁一次**——那时 V4 才生效，而本轮裁决不等于预先批准交付。


### 5.1 ★ 建议**先做**的一条：P2-E「输入缓冲寿命解耦」（结构性、离线可验、不加提交、不加大池）

**观察（读码，已在 HEAD 核实）**：交棒那条命令缓冲里，**真正读"接收样点"的只有前端那一段**（DFT / 网格写）；
估计器、均衡、解映射读的是**网格**，不是输入。可是 keepalive token（把接收缓冲留在池外的那个引用）
是挂在**整条命令缓冲的完成**上的（`ocudu_dft_metal_engine.mm` 的 `release_block_tokens` +
`arm_tokens_on_complete` 的 `addCompletedHandler`）⇒ **输入被持有到整跳结束**，而它只需要活到"最后一个读输入的 dispatch"。

**机制已存在**：代码里**已经**用 `MTLSharedEvent` 在命令缓冲**中途**发信号
（`lib/phy/metal/ocudu_metal_queue.mm:464` 的 `encodeSignalEvent:grid_event`、`:528` 的 `stage_fence_event`），
所以"在某次 dispatch 之后发信号"是本代码库既有能力，不需要新机制。

**做法（形态，不是实现细节）**：在"最后一个读输入的 dispatch"之后 `encodeSignalEvent`（一个新事件或复用网格事件），
宿主用 `notifyListener:atValue:` **释放 token**（不阻塞任何线程）⇒ **持有期从"整跳跨度"降到"前端那一段"**。

**预期（可证伪）**：

| 量 | 现在 | 预期 | 判据 |
|---|---|---|---|
| 接收缓冲持有期 | ≈ 整跳跨度（中位 2675 µs）| ≈ `t2f` 段（中位 **521 µs**）| P0-2 的持有期直方图 |
| `[ul_rx_pool] held_max` | **8（=池）** | **≤ 3** | V2 |
| `starved_events` | 17–69 | **0** | **V2** |
| RF 失败 | 476–733 | **≤ 10** | **V3** |
| `cbs/lane` | 2.00 | **2.00（不变）** | **V4（关键：不靠加提交）** |
| `[ul_gpu_pipeline]` 中位 | 2675 | **不变（≈2675）** | **V1 不由此达成**——时延工作照旧做 |

**为什么它是对症的而不是治标**：输入的生命周期**本来**只该到"最后一个读者"；把它绑到"整跳完成"是**多持有**，
而多持有的代价正好落在池上。这不是把池加大去容纳浪费，而是**去掉浪费本身**。

**风险与反向臂**：
* 若**信号之后仍有 dispatch（或任何设备侧读者）读输入**，提前释放会让电台覆盖样点 ⇒ 数据错。**必须先审计"谁读输入"**（P0-1 的拆分正好能回答），
  并让**既有网**当反向臂：`l1_handover_arms` / `l1_hop_arms`（逐字节）、`value_net`（容差 + NO-NaN + LLR 符号）、`-L phy`、契约 8/8。
* 若该臂**全绿而 `starved_events` 不降**，说明持有期还有别的来源 ⇒ 回到 P0-2 的直方图。


## 6. 与"加大池"的关系（用户裁定，别搞混）

* **加大池 = 诊断**（P1-4）：它能**证明**因果链，但**不缩短时延**，因此**不作为交付**、也不满足 V1。
* **P2-D** 是它的"有 principled 版本"：容量**由测得的持有期分布导出**，并随时延的改善重算。
* 判据上二者必须分开：P1-4 只看 `starved_events`；P2-D 必须同时满足 V1 与 V2。

## 7. 里程碑关系与不做的事
