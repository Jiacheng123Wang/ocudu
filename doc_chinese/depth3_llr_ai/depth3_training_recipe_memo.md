## 1. 当前标准配方（直接可复制）

```bash
cd ~/dev/ocudu/lib/phy/upper/ai_signal_processors/depth3/ai_train
python -u train_depth3.py \
  --train  <母集抽取目录>            # 一数组一 .npy，mmap 流式（绝不用压缩 npz 直接训）
  --val    <monitor 抽取目录>        # 独立 monitor，**只作参考**
  --out    <run 目录>               # 快照与 resume 状态都写这里
  --modcond --layout spatial --in-channels 12 --no-reporting-heads \
  --c-hid  <32|128|256>  --blocks <18|72|…> \
  --batch 8  --lr 1e-3  --epochs <N> \
  --patience 0  --snapshot-every 1 \  # ★ 不早停 + 每轮快照
  --workers 4  --bler-samples 0  --seed 20261105  --max-val 181
```

**每个取值的理由**：

| 参数 | 取值 | 为什么 |
|---|---|---|
| `--modcond --layout spatial --in-channels 12` | 固定 | 16 通道（12 平面 ＋ 4 个 Qm one-hot）；部署契约要求（Core ML 导出、`depth3_qm_set`）|
| `--no-reporting-heads` | 固定 | 只留 `llr` 与 `post_eq_noise` 两个头；reporting heads 只在研究期用 |
| `--batch` | **8**（GPU 可 16）| CPU 上 8 是内存/速度的平衡点；107 的 batch 16 实测可跑 |
| `--lr` | **1e-3**（从零）／**3e-4**（暖启动）| Adam 默认量级；暖启动必须降，否则破坏已学到的解 |
| `--epochs` | 由预算定，**不是**由 val 定 | 见 §5：早停会误伤 |
| `--patience 0` | **不早停** | §6 的定量分析：`patience 3` 在一条真实曲线上会少 12.6% |
| `--snapshot-every 1` | **每轮一个快照** | 事后用尺子选；也是"从某一轮继续"的唯一入口 |
| `--bler-samples 0` | 0 | 训练期不算 coded BLER（贵且与选优无关）|
| `--seed` / `--max-val` | **必须显式传** | 默认 `20261013` / `64` 会与别的臂不一致（2026-11-05 踩过）|

## 3. 数据配方

| 项 | 配方 | 依据 |
|---|---|---|
| 母集 | 每条腿、每种调制、self/harq 各一个 `.npz`（**可解码样本全集**）| `corpus_to_training_db_manual.md` §7 |
| 分箱 | 4 调制 × 4 宽度 × 7 SNR × 2 群体 ＝ **112 箱** | 同一套边界（`census_bins.py`）|

| 训练/验证隔离 | 用 **X 行 blake2b(8B)** 去重，报告剔除数 | 小箱会被训练集吃光，事后必须剔除 |
| monitor 大小 | 目标 ≥1 000；**181 条太小**（噪声 σ≈0.0036）| §6 |

## 4. 优化配方

| 项 | 结论 | 证据 |
|---|---|---|
| 学习率 | 从零 **1e-3**；暖启动 **3e-4** | 1e-3 再续训会过拟合（val 46 轮见底、60 轮反弹）|
| 轮数 | 宁可多跑 + 快照，不要早停 | §5、§6 |
| batch | CPU 8；GPU（107）16 | 107 的 batch 16 实测可跑（4.3 GB）|
| 权重 | `--w-ch 0.1 --w-noise 0.01`（默认）| 与所有历史 run 一致，改动会让曲线不可比 |
| 种子 | **每条臂显式传入并记录** | 106 那条漏传用了默认 20261013 |
| 轮内评估 | `--bler-samples 0` | 训练期 BLER 与选优无关 |

## 5. 选模型配方：**不早停 ＋ 每轮快照 ＋ 尺子**

```
训练（固定轮数，patience 0，snapshot-every 1）
   ↓  每个快照都是一个候选
尺子（5 000 单元，交付比特，配对 bootstrap/McNemar）
   ↓  在候选之间做统计比较
选交付比特最高的那个（并按调制分解看强弱项）
```

**为什么不用 val 选**：val 是 731 条（或 181 条）上的**均值**，噪声 σ≈0.0036；而真正要回答的是
"交付比特"，它的方差由 5 000 个单元决定，配对 CI 约 ±2.8% —— **只有尺子有足够分辨率**（§6）。

**⇒ ★★★ 三个结论**：
1. ★★ **无偏**：中位与 5 000 真值几乎相同 ⇒ 随机 500 **不是**以前那个有偏前缀 ✓
2. ★★ **但很宽**：95% 区间 **±6 个百分点** ⇒ **单个 500 的点估计不能当尺子的数引用** ✓
3. ★ 那个固定子集（seed 20261105）落在**偏低一侧**（+7.98% vs 中位 +13.18%）—— 是抽样运气，不是 bug ✓

**(c) ★★★ 探针该用来干什么**

| 用途 | 500 探针行不行 |
|---|---|
| 同一 run 内**给轮次排序**（E40 < E20 < E46 < E60 的次序在 500 上完整保留 ✓）| ★ **行** |
| **发现大坑**（epoch 50 的 −4.4% vs 邻居 +3~8%）| ★★ **行** |
| **引用"这个模型比 CPU 好多少"** | ★★ **不行** —— 必须用 5 000 尺子 |
| 想用探针得到可引用的结论 | 用 **≥1 500 单元**（约 ±3.5 pp），或**三个不相交 500 取平均** |

**(d) ★★ 工具已改**：探针对自己的子集自举 2 000 次并**打印 95% 区间**，避免把 500 的点估计误当尺子的数：

```
units 500  arm 1,004,192  cpu 930,016  delta +74,176 (+7.98%)  自 95% 区间 [+2.72%, +13.99%]
```

### 5.6 ★★★★★ 500 探针的"定性"能力：**在 ≳5 个百分点以上成立，≈1 个百分点附近是掷硬币**

**⇒ 做法**：对 5 000 个单元做 **3 000 次随机 500 抽样**，看每次子集**是否保住**整跑的**符号**与**次序** ✓

**(a) ★★★ 符号正确率（子集判定"比 CPU 好/差"与 5 000 真值同号的比例）**

| 臂 | ★ 5 000 真值 | ★ 随机 500 保住符号的概率 |
|---|---|---|
| **E60** | **+13.39%** | ★★ **100.0%** |
| **E46** | **+9.86%** | ★★ **99.9%** |
| E40 | −3.37% | ★ 86.1% |
| E20 | +1.07% | ★ **63.2%（≈掷硬币）** |

**(b) ★★★ 次序正确率**

| 比较 | 真值差 | ★ 500 子集保住的概率 |
|---|---|---|
| **E60 > E46** | 3.5 pp | ★ **97.8%** |
| E46 > E20 | 8.8 pp | **100.0%** |
| E60 > E40 | 16.8 pp | **100.0%** |

**(c) ★★★ 结论（正面回答"好的好、差的差"）**

**⇒ ★★★ 是的，但有明确的边界**：

| 真实效应大小 | 500 探针能不能判对 |
|---|---|
| **≳ 5 个百分点**（如 +9.9% / +13.4%）| ★★ **几乎总是**（≥98%）|
| **≈ 3 个百分点** | ★ **多数时候**（~86–98%）|
| **≈ 1 个百分点**（且本身统计上就是平局）| ★★ **不行**（63%，硬币）|

**⇒ ★★ 所以用法**：探针用来**抓大坑、排大序**（epoch 50 比邻居差 ~10 pp 这种，可靠）；
**不要**用它判"两个都在 10% 附近的臂谁更强" ✓
**⇒ ★ 这跟 §5.5 的 ±6 pp 区间是同一件事的两种说法** ✓

## 6. 早停的定量分析（**结论：会误伤，且 val 也没资格判**）

数据：`w2c32_b18_e21`（60 轮，best = **0.10052 @ epoch 46**）。

| patience | 实际会停 | 留住的 val | 相对最佳 |
|---|---|---|---|
| 2 | ep 7 | 0.11761 | **−17.0%** |
| **3（旧默认）** | **ep 11** | 0.11316 | ★★ **−12.6%** |
| 5 | ep 29 | 0.10665 | **−6.1%** |
| 10 | ep 43 | 0.10311 | −2.6% |
| **≥15** | ep 60 | **0.10052** | **0** |

**⇒ 旧默认 `patience 3` 会在第 11 轮停，少 12.6%**；这也解释了"以前一般 10–20 轮就停"——那段正是第一个平台。

**但**：平台噪声 σ≈0.00359，而 24→46 的改进只有 0.00613（**1.7σ**）、33→46 只有 0.00258（**0.7σ**）
⇒ **val 判不出 46 比 24 好**。两个尖峰（ep9 0.1690、ep53 0.1407）说明 val 还会被个别 batch 带飞。

### 6.2 ★★★★★ 尺子上的直接证据（2026-11-05）：**交付比特一直涨到第 60 轮，val 的最佳轮不是最好的**

**⇒ 做法**：把这条 run 的 **4 个轮次（20 / 40 / 46 / 60）** 分别导出 Core ML，在**同一把尺子**上各测 5 000 单元 ✓

| 轮次 | val（731 条）| ★ 交付比特 | ★ vs CPU |
|---|---|---|---|
| CPU | — | 8 933 800 | — |
| **E20** | 0.10713 | 9 029 280 | +1.07% |
| **E40** | 0.10532 | 8 632 624 | ★ **−3.37%** |
| **E46**（★ val 最佳 0.10052）| 0.10052 | 9 814 688 | +9.86% |
| ★ **E60**（最后一轮）| 0.10570 | ★★ **10 129 952** | ★★ **+13.39%** |

**⇒ ★★★ 关键对比：E60 − E46 = +315 264 bit，CI [+214 360, +411 376]，p = 1.2×10⁻¹²** ✓
**⇒ ⇒ ★★★ 结论**：**val 说 E46 最好（0.10052 vs 0.10570），尺子说 E60 明显更好** ✓
⇒ 这正是 §6 的预言："val 的噪声（σ≈0.0036）比 24→46 的改进（1.7σ）还大，选不出来" ✓

**⇒ ★★★ 第二个结论（配方层面的代价）**：`patience 3` 会停在 ep11（≈E20 水平，**+1.07%**），
而跑到 60 轮是 **+13.39%** ⇒ **早停 = 丢掉约 12.3 个百分点的交付比特** ✓

**⇒ ★★ 第三个结论**：**曲线不单调** —— E40（−3.37%）比 E20（+1.07%）**还差**，随后 E46/E60 大涨 ✓
⇒ **任何"单点 val 选优"都会踩到这种坑；只有逐点尺子测量才看得到** ✓

**⇒ 所以 §5 的配方不是理论偏好，而是被 4 个点的交付比特直接验证过的** ✓

### 6.1 ★★★ 平滑能不能救早停？—— 用这两条真实曲线试了：**不能**

**⇒ 做法**：把 val 先做 **3/5 轮中位平滑**，再在平滑序列上跑同样的 patience 规则（`min_delta 0`）✓

**⇒ 结果（两条 run 都是真实历史）**：

| run | best | 平滑 | patience 3 | patience 5 | patience 10 |
|---|---|---|---|---|---|
| **c32，60 轮**（w2 166 495）| **0.10052 @46** | 原始 | stop@11 **+12.6%** | stop@29 +6.1% | stop@43 +2.6% |
| c32 | | 中位 3 | stop@17 +9.2% | stop@28 +6.3% | stop@33 +6.3% |
| c32 | | 中位 5 | stop@9 **+19.7%** | stop@19 +9.3% | stop@32 +6.6% |
| **c128，26 轮**（w2，跑到 26/40）| 0.09822 @19 | 原始 | stop@9 **+3.5%** | stop@15 +0.9% | stop@26 **+0%** |
| c128 | | 中位 3 | stop@12 +4.1% | stop@14 +4.1% | stop@26 +0.2% |
| c128 | | 中位 5 | stop@11 +4.1% | stop@13 +4.1% | stop@26 +0.4% |

**⇒ ★★★ 三个结论**：

1. ★★ **平滑救不了早停**：c32 上无论中位 3 还是 5，`patience ≤10` 仍要丢 **6–20%** ✓
   ⇒ 原因是曲线**真的**在 ep20–45 之间是平的、直到 46 才降，不是噪声造成的假平台 ✓
2. ★★ **`patience 3` 一律有害**：c32 丢 12.6%、c128 丢 3.5% ✓
   **`patience 10`** 才接近安全：c32 只丢 2.6%、c128 **不丢** ✓ ⇒ **若非要早停，用 ≥10** ✓
3. ★★★ **两条 run 的最佳轮差得很远**（19 vs 46）⇒ **固定的轮数预算不可移植** ✓
   ⇒ 一个语料上"60 轮正好"不代表另一个语料；**必须每轮快照 + 尺子选** ✓

**噪声根源**（`train_depth3.py:1169`）：val = 对 ~46 个 batch 均值**再取均值** ⇒ 一个病态 batch 就能拉走 1/46。
**⇒ 待改：val 用中位数/截尾均值**，否则早停始终是掷骰子。

## 7. 宽度 vs 深度（配方层面的取舍）

**块 = `1×1 卷积(C→C) → LayerScale → +残差`**，每样本 8 568 个位置 ⇒ 每块 MAC = 8 568·C²。

| 配置 | 参数 | 每样本 MAC | 实测 samples/s | 等效算力 |
|---|---|---|---|---|
| c32 × 18（221）| 26 152 | 0.16 G | 15.6 | 4.9 GFLOP/s |
| c32 × 72（221）| 102 217 | 0.63 G | **0.97** | 1.2 |
| c128 × 18（221）| 325 897 | 2.53 G | 4.0 | **20.2** |
| c128 × 18（本机）| 325 897 | 2.53 G | 23.0 | **116** |
| c32 × 231（本机）| 326 089 | 2.03 G | ≈1.5 | 6.1 |
| c32 × 72（本机）| 102 217 | 0.63 G | **20.3** | — |

**⇒ ★★ 结论**：**加深是"更多小步骤"（开销 ∝ 层数），加宽是"每步更大"（算力利用率高）**。
等参数量下（c32×231 vs c128×18，各约 326 k），深度版的有效算力只有宽度版的 **1/19**（6.1 vs 116 GFLOP/s）。
**⇒ 配方含义**：**CPU 上优先加宽**；要研究深度必须用 GPU（107）。等参数量的深度对照是 **c32 × 231**。

## 8. 暖启动 / 续训配方

| 场景 | 机制 | 注意 |
|---|---|---|
| 继续**同一次**运行（换机器、重启后）| `--resume` | 需要 `<out>/depth3_last.keras` ＋ `resume.json`（含 epoch/best/since/history）|
| 从**某个快照/最佳**继续，换配方 | `--init <x.keras>` | 只载权重、优化器全新；**lr 必须降**（3e-4）|
| 两段式（先分调制训、再合并）| 先各训单调制，再用 `warm_start_cond.py` 拼 conditional | 历史证据：c128 两段式 **+7.93%**；c32 两段式 **−18.9%**（宽度是关键）|

**已证实的细节**：
- `--resume` 会**从 history 恢复**，不会丢已跑的轮（2026-11-03 修的就是这个）；
- `depth3_best.keras` 在**每次 val 改进**时写（`train_depth3.py:1272–1275`）；
- 快照**不含** `resume.json`，所以"从快照续"要走 `--init`。

## 9. 配方层面的坑（都踩过）

| 坑 | 后果 | 规矩 |
|---|---|---|
| 漏传 `--seed` / `--max-val` | 臂之间不可比（默认 20261013 / 64）| ★ **必须显式传** |
| `--snapshot-every 10` | 最佳轮（46）落在快照之间，只能靠 `best.keras` | ★ **`1`** |
| 压缩 npz 直接训 | 整库进内存 | ★ **`.npy` 目录 ＋ mmap** |
| 早停 | 12.6% 的损失 | ★ **`--patience 0`** |
| 用 731 条 val 选模型 | 噪声级选择 | ★ **用尺子** |
| 深度扫参在 CPU 上做 | 4× 深度 6–16× 慢 | ★ **CPU 加宽，GPU 加深** |
| `ls | head` 判断文件是否存在 | 误报"最佳权重丢了" | ★ 用 `[ -f ]` / `find` |
