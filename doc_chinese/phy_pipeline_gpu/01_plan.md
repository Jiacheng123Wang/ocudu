# 01 — 分步实施计划

> **每一步都必须能单独判对错。** 判据只有三种合法形态：
> **(a)** 输出逐字节相同；**(b)** 契约明确变化（某条检查从 FAIL→OK 或 not-applicable→判定）；
> **(c)** A/B 可分辨。
> 拿不到这三者之一的改动，**先补判据再动手**。延迟、失败率、GPU 占用率**都不是判据**。

---

## 0. 每一步共用的正确性骨架

### 0.1 三模式共存是前提（你已经要求，代码里本来就有）

`phy_pipeline_mode` 是枚举，`resolve_phy_pipeline()` 按模式解析后端，validator 按模式查冲突。
**⇒ `gpu` 与 `cpu`/`cpu_gpu` 天然并存，A/B 不需要额外机制**——只要**不要**把模式相关的代码
写成全局单例式的分支。

**唯一的例外**：`phy_pipeline_mode_registry` 是**进程级**的（探针用），进程内切模式需要重启 gNB。
A/B 因此是**逐进程**的，不是逐跳的。这一点必须写进协议（`02_ab_protocol.md`）。

### 0.2 离线判据用哪张网

| 网 | 判据 | 用途 |
|---|---|---|
| 严格网（`OCUDU_CE_CPU_LS=1`）| **27/27 逐字节相同** | 最敏感，任何数值/顺序改动都会被它抓到 |
| 有界网（设备路线）| 26/27，最差 8 字节，**flips 0** | 设备路线的基线 |
| CPU 网 | 27/27 逐字节相同 | 纯 CPU 参考 |

**⚠ 不要用序 A/B（`ab_fused_lane.sh`）的红绿当判据。** 它本身 flaky：
本 session 量过**基线 2/24 轮、改动后 3/28 轮**出现假不匹配（Fisher p≈1.0），
失败总是落在不同捕获/不同序，而它比的是**默认跑 vs 显式 `event` 跑（同一条代码路径）**。

### 0.3 每一步的提交纪律

一个 commit 一个步骤；commit message 里必须写明**这一步的判据是什么、结果如何**。
本 session 已有三个这样的 commit 可作模板：`2eca4a7965`、`e0bbc34c9f`、`832832c442`。

## S1 — 解锁 `--phy_pipeline gpu`（摘掉占位拒绝）

**改动**：`apps/units/flexible_o_du/o_du_low/du_low_config_validator.cpp:94-96`
删掉那句无条件的 `fmt::print("… is not implemented yet …")` + `return false`。
**保留**第一层 `check_phy_pipeline_lane_available()`（后端可用性）。

**为什么它本身安全**：`resolve_phy_pipeline()` 的 `gpu` 分支解析出的后端是
`phy_pipeline_lane_defaults`（`dft="metal"`、`ch_est="metal_mmse"`、`equalizer="metal"`）
+ `device_grid=true`——**与旧腿脚本已经显式传的那四个值完全一致**。
而且 `lane_fused` 只被打印（`du_low_config_translator.cpp:48` 是唯一消费点）。
**⇒ 这一步不改变任何数据路径，只让一个已经存在的模式可选。**

**判据（三条都要）**：
1. **既有模式不变**：`--phy_pipeline cpu` 与 `--phy_pipeline cpu_gpu` 各跑三张网 ⇒
   严格 27/27、有界 26/27 flips 0、CPU 27/27。
2. **新模式可选且能启动**：真跑路径上 `--phy_pipeline gpu` 通过校验、gNB 起来、
   契约首行打 `contract (mode=gpu)`。（**不用 `--dryrun`**：它静默忽略未知选项。）
3. **冲突检查仍然生效**（负面用例）：给 `cpu` 传 `--expert_phy.pusch_dft_type metal`
   **必须**被 validator 拒绝；给 `gpu` 传一个 CPU 后端同样必须被拒。

**回退**：`git revert` 一个 commit。

**风险**：低。纯校验层，不碰数据。

---

## S2 — 让目标**可测**：给契约加一条"数据穿越"检查

**为什么这是第二步而不是第三步**：目标的性质是"只剩两次穿越"，而今天的契约 7 条**没有一条在数它**。
不先把它变成每跑一次就判一次的东西，后面每一步都会重新滑回"我觉得/我觉得不值"。

**改动**：新增一条 `register_phy_pipeline_check`（`include/ocudu/phy/phy_pipeline_contract.h` 的机制），
计数**宿主读取设备产出**的次数，并在 `gpu` 模式下把目标的声称写死：

| 模式 | 该检查的期望 |
|---|---|
| `cpu` | not applicable（没有设备参与） |
| `cpu_gpu` | 判定，并**打印出真实次数**（今天是 3 次标量回读/跳）——**预期 FAIL**，这正是"还没到目标"的可复现证据 |
| `gpu` | 判定，要求只剩 IQ 上传与 LLR 下载 |

**判据**：
1. **该检查不改变数据路径**：三张网逐字节不变（它是只读计数器）。
2. 在 `cpu_gpu` 下它**判定为 FAIL 并把今天的真实次数打出来**——这是我们第一次有"差距"的机器可读数字。
3. 在 `cpu` 下是 not applicable；在未发布模式的单元测试/工具里也是 not applicable
   （`phy_pipeline_mode_registry::is_published()` 已经是现成的守卫）。

**风险**：低。只加计数器与一条检查。

---

## S3 — 用零风险 A/B 证明"那次回读对 GPU 已经死了"

**假设**（`00_goal_and_gap.md` §3.3）：`ocudu_mmse_corr.metal:151` 在 `sigma2_from_device` 置位时
不读 `p.sigma2`，而 `OCUDU_CE_K0A_RATIO_DEV` 默认 1 ⇒ 宿主那三个标量算出来的东西，
**对 GPU 已经是死的**。

**做法**：加一个 A/B 旋钮（**默认关**）。打开后宿主**跳过**这些回读与派生的统计量，
只保留宿主上报所需的最小集合。

**判据（这条是这一步的全部意义）**：
**旋钮开与关，发布的 `_llr.bin` / `_h.bin` / `_ce.txt` 逐字节相同。**
- 相同 ⇒ 假设**被证实**，那次 dev→host 回读可以安全移除，S4 按此推进。
- 不同 ⇒ 假设**被推翻**，说明还有人在读；**停下来查是谁**，不要继续。

**风险**：低（默认关）。**这一步是"不要照算式施工"的落地**——先用 A/B 让数据说话。

---

## S4 — 按 S2/S3 的实测清单逐条消灭残留穿越

**顺序由实测决定，不预先拍。** 已知的两个候选：

| 候选 | 前置条件 | 判据 |
|---|---|---|
| 移除标量回读 + 宿主统计量 | S3 的 A/B 证实"对 GPU 是死的" | S2 的穿越计数下降；三张网不变 |
| 消灭宿主建矩阵（`:1440/:1720/:1858/:1953`）| **需要先量出各路线在当前 testbed 的占比**（`00_goal_and_gap.md` §7 第 2 项，旧数字 37.5% 来自 b22 腿、不可用）| 这些路线上 `build_correlation_matrices` 调用数 → 0；三张网不变 |

**每条的通用判据**：**S2 的穿越计数下降，且发布的 LLR 不变。**

### S4 的实测结论（2026-09-18，已完成到"定位"为止）

`OCUDU_CE_TAIL_DEV=1`（设备侧建 edge 矩阵）**能跑通，但值不对**：与宿主建相比
15/27 捕获不同、6043 字节，差异集中在 `_h.bin` 的 **edge 区域**。
两轮排除后（`S4_taildev.md`）剩下的唯一嫌疑是**超大槽位路线本身**：
edge 组的槽位是标准组的（`a_stride = L_std > L_e`），而 `k0d` 只覆盖过标准组的**精确**槽位。

**S6（见下）把这条嫌疑收得更紧**，并给出了探针。

---

## S6 — 合并 batch 的**第二个**相关矩阵前缀（`OCUDU_CE_EDGE_FUSE`）

**目的**：一个"合并 batch"里住着两个几何（标准组 + edge 组），而引擎的 `corr` 前缀一次只描述
**一个**。edge 组因此走 `mmse_engine::build_correlation()`——**它自己一条命令缓冲**，
多一次提交 + 一次等待。这正是融合车道上多出来的那 0.28（`cbs/lane` 3.00 → 3.28）。

**改动**：`encode_run` / `run_async` 增加末位参数 `corr_edge`（同一缓冲、同一 barrier），
`build_slots_on_device()` 可以**回填**而不是提交。详见 `wip/S6_edge_prefix.md`。

**判据**：默认关闭 ⇒ 三张网逐字节不变（**已实测：6043 = 改动前**）；
开启后必须与独立形态**逐字节相同**——**实测 50590 字节不同，故未开启**。

**⇒ S6 现在的身份是"探针"，不是"胜利"。** 它没有修掉 S4，但它证明了
**两个设备形态彼此也不同**，从而排除了"命令缓冲的编排方式"这个方向。

---

## S5 — 收口：`gpu` 模式的契约成立

**⚠ 前置条件已明确**：S5 的"跳过宿主标量回读"必须等 **S4 的设备侧 edge 构造改对**
（否则跳过之后 `TAIL_DEV` 路线会错，实测 602 个 LLR 翻转）。**先修 S4，再落 S5。**

**判据**：
1. `--phy_pipeline gpu` 实跑：`contract (mode=gpu)` + **"数据穿越"检查通过**（只剩 IQ 上传与 LLR 下载）。
2. `--phy_pipeline cpu` 与 `cpu_gpu` 各自的契约**仍然通过**（三模式共存没被破坏）。
3. 一条空口腿：契约全过、`Real-time failures` 与今天同量级、`device_sigma2 == lanes`。

---

## 明确不做

- **LDPC**：模式定义原文就把 LDPC 排除在车道之外（LLR 离开设备给 CPU 解码器）。**维持现状。**
- **任何以"省了多少 µs"为理由的改动**：本线判据是穿越次数。
- **改动旧工作区**（`doc_chinese/full_gpu_chain/wip/`）：那边写死了 `cpu_gpu`，
  本线一律用 `phy_pipeline_gpu/wip/`。

## 依赖关系

```
S1（解锁模式）
  └─ S2（让目标可测）        ← 没有 S2，后面每一步都失去判据
       └─ S3（A/B 证实回读是死的）
            └─ S4（逐条消灭）
                 ├─ S6（第二个 corr 前缀：机制 + 探针，默认关）
                 └─ S5（收口）
```

**S1 与 S2 可以同时做**（互不依赖）。**S3 之前必须先有 S2**，否则证不出"穿越次数下降"。
