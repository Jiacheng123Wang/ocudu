# W2：用 HARQ 重传**捞回**失败首传的真值

> **一句话**：`rv=0` 首传失败的捕获，本来没有标签；但同一个 TB 若在**后续重传**里被 gNB 解出，
> 那份 TB 比特就是**它自己的真值**。样本仍是"单次接收"的样本，**不需要离线做软合并**。

---

## 1. 为什么可行

| 事实 | 依据 |
|---|---|
| 上行 TB 由手机决定，gNB 只有解出来才知道比特 | 一代 §19.626 |
| 同一 HARQ 进程的多次传输**携带同一个 TB** | 3GPP HARQ 定义；PDU 里的 `rnti`／`harq_id`／`rv` 可把它们串起来 |
| 采集配置**已开启** UL HARQ | `configs/gnb_rf_b200_tdd_n78_20mhz_llr_collect_p0default.yml`：`rv_sequence: [0, 2, 3, 1]` |
| `OCUDU_HELENA_DUMP_DIR` 在**每次** CRC 通过时写 TB | `dump_tb.sh` 的机制 |

**关键区别（与旧设计的差别）**：旧说明写"重传不能当样本，因为离线回放不复现软合并"——**那是对的，但只针对"拿重传本身当样本"**。
W2 不这么做：**重传只用来产生标签，样本仍是那条 `rv=0` 的捕获**。

---

## 2. 采集要求（与以前不同的三点）

| # | 项 | 值 | 理由 |
|---|---|---|---|
| 1 | `OCUDU_UL_DUMP_RV` | **不要设置**（默认＝不过滤）| 我们此前的语料**全是 rv=0**（实测：attach 6 456 条、cmp_e4d 20 000 条，`rv` 分布只有 `0`）⇒ 因为流量里没出现重传，或重传没被采 |
| 2 | `OCUDU_UL_DUMP_COUNT` | **100 000** | 预算现在要同时容纳重传 |
| 3 | 位置 | **小区边缘**（首传失败率 10–20%）| 没有失败就没有可捞的样本 |

**飞完先验一件事**（决定这条腿有没有用）：

```bash
grep -o "rv=[0-3]" <腿日志> | sort | uniq -c
```

| 结果 | 含义 |
|---|---|
| 只有 `rv=0` | ★ **没有重传** ⇒ 这条腿对 W2 无用（要么 HARQ 没生效，要么位置太好）|
| 出现 `rv=2`/`rv=3` | ✅ 有重传 ⇒ 继续 |

## 3. 捞回流程（新工具 `harq_backfill.py`，待写）

```
输入：一条腿的捕获（PDU 侧车里有 rnti, harq_id, rv, tbs_lbrm, slot）
1. 按 (rnti, harq_id) 分组，按 slot 排序           → HARQ 链
2. 对链里每个成员回放（classical，单次接收）        → crc、迭代数、以及（若 OK）tb_*.bits
3. 找链里第一个 crc=OK 的成员 M
4. 校验：M 的 tbs 与链里更早成员一致               → 否则丢弃该链（保护）
5. 把 M 的 .bits 复制给「链里更早且 crc=KO 的成员」 → 这些捕获获得标签
6. 产出 index.csv（unit, tb_bits, crc=OK_by_harq, …）
```

**产出**：一条新的 `index.csv`，其中 `crc` 列写 `OK` 的行里，有一部分是**通过 HARQ 捞回**的
（建议加一列 `label_from=harq`，便于审计与消融）。

**训练注意**：这些样本是"经典链单次接收失败"的样本 ⇒ 正是模型要学的**困难区域**；但它们**不能进验收判据**（判据要与经典链成对比较，而这些样本经典链本来就失败）。

| 量 | 估计 | 依据 |
|---|---|---|
| 首传失败率 | 10–20% | 我们各腿的 `crc=KO` 比例 |
| 其中能在后续重传解出 | 多数（HARQ 增益大）| 需实测 |
| 每次失败提供 | **1 个困难样本 ＋ 1 份真值** | — |

即 100 000 条量级的捕获（一次 100 k 腿）。**⇒ 这正是用户说的"需要大量采集"**。

## 6. 采集用 **CPU 路径**（2026-10-27 定）

**采集不需要 AI 臂**：我们要的是捕获（网格／CE／PDU）和**活体的解码结果**，两者都在**经典链**上。
CPU 路径还更快（不占 ANE、不与门控抢设备）。

```bash
# 关键环境变量（都必须在 sudo 前 export）
unset OCUDU_UL_DUMP_RV                  # 不过滤 rv：重传也要采
export OCUDU_UL_DUMP_COUNT=100000       # 预算要能容纳重传
export OCUDU_HELENA_DUMP_DIR=<腿目录>/tb_live   # ★ 活体 TB 落盘

sudo -E bash doc_chinese/llr_ai_detection/wip/run_collect_leg.sh cpu <label>
#                                                        ^^^ 位置参数＝phy_pipeline
```

## 7. ★ 为什么必须是**活体** TB 而不是离线回放

| 事实 | 后果 |
|---|---|
| 重传常常**只有结合软缓冲**才解得出来 | 对同一条重传做**离线单次回放**往往**解不出** ⇒ 拿不到供体比特 |
| 活体链（CPU 经典链）在腿里就完成了合并与解码 | `OCUDU_HELENA_DUMP_DIR` 会在**每次 CRC 通过时**写 `tb_<idx>_tbs<bits>.bits` ＋ `dd_meta.csv` |

`dd_meta.csv` 的列：`idx, timestamp_us, tb_bits, nof_codeblocks, system_slot`
⇒ ★ **按 slot 把活体 TB 对回捕获** ✓（单 UE 场景无歧义）。

**⇒ 这是 W2 能成立的关键：供体来自**活体解码**，样本仍是**单次接收**。**

## 8. 工具已支持两种供体来源

| 来源 | 开关 | 优先级 |
|---|---|---|
| **活体 dump**（推荐）| `--live-tb <腿目录>/tb_live` | ★ 优先 |
| 离线回放（同一次接收自己解出）| 默认 | 回退 |

**已测**（合成链）：① 离线供体 → 捞回 2 条 ✓；② 离线全 KO、仅活体供体 → **仍捞回 2 条** ✓；
③ 块大小不符 → 0 ✓；④ 槽间隔过大 → 切链 0 ✓。

## 9. 腿命名约定：**一条腿 ＝ 一种业务形态**（2026-10-27 定）

业务形态靠**腿名**区分，不靠"同一条腿里换流量"。这样：
① 不用相位标记；② 每个子集天然干净；③ 建库/分析时按腿名分组即可。

| 腿名 | 业务 | 上行块形状 |
|---|---|---|
| **`w2_harq_1027`** | ping 默认（56 B）| 窄，4–6 PRB ★ 正在跑 |
| `w2_harq_ping500_1027` | `ping -s 500` | 中，约 10–25 PRB |
| `w2_harq_ping1400_1027` | `ping -s 1400` | 宽，30–51 PRB |
| `w2_harq_iperfudp_1027` | `iperf3 -R -u -b 20M -l 1200` | 宽，BLER 可控 |
| `w2_harq_iperftcp_1027` | `iperf3 -R -t 300` | 最宽，AMC 降档 |

**命名规则**：`w2_harq_<业务>_<日期>`；业务 ∈ {ping56, ping500, ping1400, iperfudp, iperftcp}。
