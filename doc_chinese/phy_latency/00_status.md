> 所有读数来自空口腿，腿日志在 `doc_chinese/phy_pipeline_gpu/wip/logs/`。
> 最近更新：**2026-09-24**（腿 `s82-phases-heavy-n78` 的三段分解）。

## 1. 一句话

**`gpu` 融合车道的端到端时延 ≈ 2675 µs（重上行、中位）**，其中
**三段几乎完全解释它**：`ul_time_frequency` 521 + `ul_channel_estimation` 901 + `ul_equalization_demod` **1234** = **2657 µs（99.3%）**。
接收缓冲的持有期 = 这个跨度；池只有 **8** 个、**每槽取一个** ⇒ **持有跨 8 个槽（≈4 ms）就把池抽干**，
`pop_blocking()` 于是阻塞接收线程，电台 **underflow**。同负载下 `cpu` 模式**零饥饿、0–1 次 underflow**。

**同一腿的设备侧读数**：

| 量 | 值 | 读法 |
|---|---|---|
| `[ul_gpu_lane] residency` 中位 | **≈1125 µs** | 车道那条命令缓冲的寿命；**与负载几乎无关**（轻载 `s75` 也是 1121）。⚠ 它的**样本总体与相位探针不同**（140204 跳 vs 97331），只能作量级比较（见 `02_measurement.md` §2.1）|

## 4. 机制（结论）

```
IQ 样点到齐 ──[ t2f 521 µs ]── 前端交出该槽的块
                                   │
                          交棒：把变换延迟进"那一跳的命令缓冲"
                                   │
                          [ ce 901 µs ]  ← 估计器等自己那块被认领/提交
                                   │
                          [ eq_demap 1234 µs ] ← 车道排队 + 均衡/解调 GPU 执行（residency ≈1125 ≈ busy 95%）
                                   │
                          LDPC 解码（70 µs，不在跨度内）
```
* **接收缓冲必须在整段跨度里活着**（交棒的设计目的就是让变换在那一跳的缓冲里执行），
  ⇒ **持有期 = 跨度**，而池 **8 个 × 每槽 1 个**：**跨度逼近 4 ms 就开始饿死接收线程**（尾部 max 已 7.9 ms）。
  ⚠ 但"输入只需要活到**最后一个读它的 dispatch**"——估计器/均衡/解映射读的是**网格**，不是输入；
  现在却把它绑在**整条命令缓冲完成**上 ⇒ **多持有**（`01_plan.md` 的 **P2-E** 就是去掉这段多余持有）。
* **车道吞吐不是瓶颈**（占用 59%、能力是需求的 1.7 倍）⇒ **瓶颈是"一跳要花 ~1.1 ms 的 GPU 时间 + 前面还要等 ~1.5 ms"**；
  "residency 里 ~95% 是 busy" 这个比例属**指示性**（两者样本总体不同，见 `02_measurement.md` §2.1），要坐实需 P0-1。
* ⇒ 优化目标不是"让池更大"，而是**把这三段里的执行/等待时间压下来**。
