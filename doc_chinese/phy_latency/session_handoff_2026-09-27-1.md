## 2. 本会话的增量结论（必读）

### 2.1 那一跳的账（**§6.123 就是权威表**；这里只放读法）

| 量（`p60`/`p70` 中位）| 值 | 一句话读法 |
|---|---|---|
| `merged_hop` cb `commit→start` | **217.0 / 214.6 µs** | **排队**：候选 = 前面排着 `ch_wt` 43 + 同队列其它 cb（2.31 × 46.6）≈ 151 µs（§3.1① 待证）|
| `merged_hop` cb `start→end` | **468.7 / 468.5 µs** | **设备真的在跑这条 cb**（十条腿散布 3 µs）—— 这才是要解释的那 470 µs |
| `busy split` | `ch_wt` **43.0 / 38.7** + `merged_hop` **474.1 / 466.8** | 一跳两条 cb，**2.00 = 平台地板**（5.9.89：cb 边界才交付写）|
| `residency` / `busy` / `gap` | **637.5 / 502.2 / 139.5** | 窗口 = residency；`gap` 可为负（cb 有重叠）|
| 宿主：阶段入口 → lane 提交 | **81.8 / 80.5 µs** | CPU 的整份参与，**不是关键路径**（G2 已量化）|
| 一跳的**墙钟** | **1935 µs = 3.86 个 500 µs 时隙** | ⚠ `receive()` 每槽一次，**上行跳每 3.86 槽一次** |
| 设备并集占用 | **29.2% / 29.5%** | 每跳设备需求 **~619 µs** ÷ 1935 µs = 32%（差 2.8 点 = cb 间重叠仅 ~27 µs/跳）|

**三条纪律级的读数口径**（写在这里，免得下一位再撞）：

1. **换量纲必须先算"每跳 1935 µs"**，不能拿 500 µs 时隙去除 —— 否则 619 µs/跳 会被读成"占用 124%"（错的）。
2. **一跳的账只能按 `p57` 之后（修复后）的腿读**；`p54`/`p55` 的 `wait=37 µs` 是**修复前**的历史值。
3. `dft_front_end` 的 **46.6 µs 是 plain 路（1 变换/cb）**，**不是融合车道的"前端"**；融合车道的前端已被并进 `merged_hop`，
   只有 `OCUDU_LANE_DIAG_SPLIT=1` 拆分臂里它才单独出现（`p47` = **452.3 µs**，87%）。`[ul_gpu_lane] dft busy`（~435 µs）是**打包前端车道自己**的读数，两者不可互证。

### 2.3 剩下的两个候选，以及"一次分辨"的判法

* **H1′ 时钟/功率状态**：同一台机器**会话间差 ~4×**（记录值 46.6 µs vs 今日 11.8–13.1 µs）；**空闲 ≥50 ms ⇒ 2.6–3.7×**（饱和 ~50 µs）；
  而空口设备**只有 29% 时间在跑**。
* **H2 派发 / 新绑定的空口单价**（Q25）：离线每派发 38 µs 是**未重叠上界**，空口读到 ~85 µs/派发。

⇒ **判别（都不破 G1/G2）**：
1. **离线**：补"**链式（互相依赖）vs 独立**派发"臂、以及"**复用绑定 vs 每跳新绑定**"臂（Q25 的账：数一次跳 cb 的首次绑定数 × 单价）；
2. **空口**：一条**并发扫描腿**（conc 1/2/4，带 Q9-F3 per-label 表）—— 若**设备越忙、每次派发越便宜** ⇒ H1′ 成立。

### 2.5 本会话新增的"仪器会撒谎"清单（每条都真的骗过我一次）

1. **Q9-F3 的 `n` 在 `p54` 之前是双倍**（`wait.size()+exec.size()`）⇒ `p54` 的 n=292316 是错的，**百分位是对的**（§6.102④，已修）。
2. **`wait`/`exec` 跨 (B) 修复边界不可比**（37 → 215 µs，§6.123①）。
3. **`[metal_stats]` 报告是 `atexit` 打的**：强制停机（`Could not stop application after 5 seconds`）会让它整段消失 —— `p70` 的第一次就只剩 74 行 stderr（§6.120）。
4. **`stale_us()` 只统计"完成过的跳"**：电台/传输卡住导致某跳永不完成时，它看不见（§6.116 前的更正）。
5. **`[ul_time_frequency]` = `[ul_rx_wait]` + 前端工作**（`record_start()` 在 `receive()` **之前**），不是纯前端时间。
6. **一个 UHD 陷阱**：`recv_frame_size=16384` 被 UHD **接受**，但链路直接崩（0 PUSCH、279385 次 RF 失败）⇒ 任何传输参数臂**第一验收条件是"手机能接入且有 PUSCH"**（§6.119②）。
