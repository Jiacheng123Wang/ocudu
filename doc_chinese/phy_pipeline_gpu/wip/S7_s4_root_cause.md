# S7（甲）— S4 的根因：相关矩阵的映射按**打包尺寸**申请，而 kernel 按**槽位行距**写

**状态**：**已修复并已提交**（`93964256aa`）。`TAIL_DEV=0` vs `TAIL_DEV=1` = **0 字节**（原 6043）。

---

## 1. 根因（一句话）

`encode_corr()` 用**打包尺寸**申请两个相关矩阵槽位的零拷贝映射：

```cpp
const NSUInteger a_per_sys   = c.l * c.l;        // 打包
const NSUInteger rhp_per_sys = nout * c.l;       // 打包
```

但两个 kernel 是**按槽位行距 `Ls` 写**的（`mmse_corr_params::Ls`，kernel 里是 `a_sys[... o * p.Ls + col]`）。
当一个块比它所在的槽位**窄**时，实际写到

```
A   : (l - 1) * Ls + l
R_hp: (nout - 1) * Ls + l
```

**远超过申请的长度，超出的写入全部丢失。**

而"块比槽位窄"**恰好就是合并 batch 的 edge 组**：分配不是块大小整数倍的那一跳，
把 `L_e` 的块塞进标准组的 `L_std` 槽位里，于是 `Ls > L`。

## 2. 为什么以前没有任何门抓到它

| 量 | 为什么躲过了 |
|---|---|
| **A 一直是逐位相同的** | A 是**方阵** `l × l`，它的实际范围 `l * Ls + l` 仍然落在 `l * l` 向上取整之后的那一页里 —— 所以 A 从来没错过 |
| **R_hp 是 `nout × l`** | 长方形，超出映射 → 丢写 |
| **`k0d` 门** | 它覆盖的是**标准组**，那里 `Ls == L`，打包尺寸与实际范围**完全相等** |
| 所有改动之前就存在的路线 | 同上，全是 `Ls == L` |

**⇒ 这是一条"只在合并 batch 的 edge 组上才存在"的路径，而那条路径从来没有被任何判据覆盖过。**

## 3. 证据（`syn004_4`：`L_e = 18` 塞进 `Ls = 54`，`nout = 168`）

| | 修复前 | 修复后 |
|---|---|---|
| 映射申请 | **3024** floats（打包 168×18） | 9036 floats（实际范围 167×54+18） |
| kernel 写到 | 偏移 **9035** | 9035 |
| 槽位实际内容 | **只到第 102 行**，103..167 **全零** | 第 167 行第 17 列 = **最后一个该写的元素** |
| A | 2916 中 **0** 个不同 | 0 个不同 |
| R_hp | 27216 中 **1170** 个不同（= 65 行 × 18），最差 \|Δ\| = **1** | **0 个不同** |

**1170 = 65 × 18 完全对得上**：`o=103` 是第一个零行，`168 − 103 = 65` 行。
`worst |Δ| = 1` 也说明这不是舍入误差而是**结构性缺失**（宿主有值、设备是 0）。

全语料：**15 个形状有 edge 块，0 个不同。**

## 4. 这次的探针（留作资产）

`OCUDU_CE_EDGE_CHECK=1`：**在同一个进程、同一跳里**把同一几何在宿主上再建一遍，
然后**逐元素**（含 pad）对照设备槽位。

**为什么它比之前的办法好**：S4 原先是用**跨进程差分发布的 dump**（6043 字节、落在 `_h` 的 edge 区域）
来定位的，于是每一个候选解释都只能"从外面论证掉"。两个构造其实**在同一瞬间、同一份输入**下都存在，
直接比就行。这个探针**一次运行就找到了边界**（第一个零行）。

## 5. 判据（全绿）

| 判据 | 结果 |
|---|---|
| `TAIL_DEV=0` vs `1` | 27/27，**0 字节**（原 6043） |
| 严格自检 27/27 | **0** |
| CPU 网 27/27 | **0** |
| 估计器单元测试 | **All PASSED** |
| 逐元素：15 个 edge 形状 | **0 个不同** |

**默认路线未变**：`Ls == L` 时 `a_extent == a_per_sys`、`rhp_extent == rhp_per_sys`，
所以修复对除 edge 外的所有路线**完全惰性**；`TAIL_DEV` **仍然默认关**。

## 6. 仍然开着的：乙（融合形态）不是这个原因

`TAIL_DEV=1` vs `TAIL_DEV=1 EDGE_FUSE=1` = **51810 字节**，
**与本次修复前、以及 `nof_systems` 修复前的数字一模一样** ⇒ **它的成因与相关矩阵的构造无关。**

**下一个嫌疑**：`encode_run` 在 `st.burst` 时**跳过** corr 与 K1 之间那道显式 barrier，
依据是注释里那句"切到 K1 的 pipeline 变更会顺带插入 barrier"。若 `stage_pipeline` 在
**同一个 encoder** 上换 pipeline 时并不插 barrier，K1 就会在 corr 写完 A 之前读 A。
这个假设可直接验证（强制插 barrier 再看 51810 是否归零），而且它**只影响融合形态**。

**顺序**：先把 `TAIL_DEV` 默认打开（产品行为第一次改变 → **需要一次 OTA**），
再做 S5 的跳过 → 穿越 **0.00**、契约转 `OK`。**乙 可以独立于这两步之后再收。**
