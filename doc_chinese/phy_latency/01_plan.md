# 01 —— GPU PHY 流水线**时延**优化计划

> 活文档（可重写）。现状读数与证据见 `00_status.md`；仪表与复跑配方见 `02_measurement.md`。
> 立项日期 **2026-09-24**；立项依据：重上行腿（`s78/s80/s82`）上 **`gpu` 抽干 8 个接收缓冲 ⇒ 接收线程被阻塞 ⇒ 电台 underflow**，
> 而同负载 `cpu` 为 **0–1 次**。用户裁定：**加大池是治标，主攻"缩短 GPU PHY 流水线时延"**。

## 0. 目标与验收（**先写死，不随结果改**）

| # | 验收判据 | 阈值 |
|---|---|---|
| **V1** | `[ul_gpu_pipeline]` 中位跨度 | **≤ 2150 µs**（重载基线 2675 µs，−20%）|
| **V2** | 症状消失：接收池 | `starved_events == 0` 且 `held_max < pool`（池 = 8）|
| **V3** | 电台 | RF 失败 **≤ 10**（cpu 量级 0–1）、`gaps == 0` |
| **V4** | **不许用提交数换时延** | `cbs/lane ≤ 2.00 (max=2)`、`dropped == 0` |
| **V5** | 不回归 | 契约 8/8、`crossings 0.00+0.00`/跳、CRC KO% 不劣化 |

**验收腿 = 重上行配方**（`-R -b 40M -P 4 -t 240`，见 `00_status.md` §5）。**每条改动都要在同一条配方上读 V1–V5**。

## 1. 预算分解（优化对象的量化锚点，腿 `s82`，中位 µs）

```
跨度 2675 = t2f 521 (19.6%) + ce 901 (33.9%) + eq_demap 1234 (46.5%)
其中：车道 residency ≈1125，其 busy ≈95%（merged_hop 1030 + ch_wt 37）
     车道占用 58.8%、能力 886 跳/s vs 需求 520 跳/s  ⇒ 吞吐有余量、时延没有
接收缓冲持有期 = 跨度；池 8 个 × 每槽 1 个 ⇒ 4 ms 就抽干
```
**三个可攻击的量**：`eq_demap`（1234）、`ce`（901，**尾巴 p95 1782 最差**）、`t2f`（521）。

## 2. 计划总览（按"先补仪表 → 再单变量 → 后结构"排序）

| 阶段 | 名称 | 依赖 | 需要空口？ | 产出 |
|---|---|---|---|---|
| **P0** | **仪表补齐**（不然 P1 只能猜）| 无 | 否（离线 + 夹具）| 每 kernel/每段的拆分读数；持有期直方图 |
| **P1** | **单变量臂**：逐段定位 | P0 | 是（每臂一条腿）| "哪一段的哪一部分是时延的真来源" |
| **P2** | **结构/实现改动** | P1 | 视改动 | 缩短主项的改动 + 单测 |
| **P3** | **验收** | P2 | 是（重载配方）| V1–V5 的读数 |

## 3. P0 —— 仪表补齐（**离线**，先做）

| # | 缺口 | 为什么必须有 | 做法 | 判据 |
|---|---|---|---|---|
| **P0-1** | **合并跳内部没有 kernel 级时间**：D1 把一跳做成**一条命令缓冲**，而 Metal 只给*每条命令缓冲*的 `GPUStartTime/GPUEndTime` ⇒ `merged_hop` 的 1030 µs 内部**不可分** | Q1 决定"砍哪个 kernel"还是"改调度"；没有它，P1 只能靠猜 | **诊断臂**：把一跳的 dispatch 分到 2–3 条**诊断用**命令缓冲（只在 `OCUDU_*_DIAG_SPLIT=1` 下生效），读每段 GPU 时间；或 `MTLCounterSampleBuffer` 逐 dispatch 采样 | 拆分后的各段之和 ≈ 原 `merged_hop`（±10%）；**该臂只用于诊断，不进验收**（V4 约束的是修法，不是诊断）|
| **P0-2** | **持有期没有直接读数**：现在只能由"跨度"推断 | V2 的"症状消失"要能直接读；且决定"池该多大" | 在 `retain_for_block/release` 的 token 上记**每次持有的时长**（attach→release），打 p50/p95/p99 + 直方图 | 重载腿上持有 p99 ≈ 跨度 p99；轻载腿上持有更短 |
| **P0-3** | `ce` 段 p95 尾巴（1782 µs / 中位 901）无归因 | 尾延迟是饥饿主因（max 6.3 ms）| 把 `ce` 段按"等块/等认领/宿主阶段/提交"再切一刀（沿用 §5.9.32 的做法：加一个 staged probe）| 尾巴落在哪一子段，逐条可读 |
| **P0-4** | 离线回放**能否**产出同样的三段读数 | 能用回放做的实验就不烧空口腿 | 检查 `ul_chain_replay` 是否经过 `ul_pipeline_probe` 的同一路径；若能，写一个"回放版的段报告" | 回放与空口在同一负载点上的三段比例一致（±20%）|

## 4. P1 —— 单变量臂（每条一个变量，判据先登记）

> 读法一律照 §5.9.32 的判读表（哪段尾巴涨 ⇒ 主攻哪一侧）。**每条臂只改一个变量**，且在**同一重载配方**下跑。

| 臂 | 变量 | 目的 / 预登记判据 |
|---|---|---|
| **P1-1** | `OCUDU_DFT_PIPELINE_DEPTH`（浅 → 深）| 若 `t2f` 与跨度随深度**下降** ⇒ 前端流水线深度不足是其中一段；若**不变** ⇒ 521 µs 是固定成本 |
| **P1-2** | `OCUDU_DFT_OPEN_BLOCK=0`（关合批）| 反向臂：若**变差**（跨度↑、`cbs/lane`↑）⇒ 说明合批确实在省时延；若**变好** ⇒ 合批把时延堆在了同一缓冲里 |
| **P1-3** | `OCUDU_CE_HOLD_EXTRACTION=0`（不把提取留缓冲）| 反向臂：验证"交棒式延迟"对 `ce`/`eq_demap` 的贡献；预期**变差**（提交数↑），但能定量 |
| **P1-4** | 池容量（**诊断用**，见 §6）| 时延不变而 `starved_events` 归零 ⇒ 因果链"持有→池干→阻塞→underflow"坐实；**不作为交付** |
| **P1-5** | `OCUDU_CE_CORR_*` / `OCUDU_CE_INV_BARRIERS`（相关矩阵的 barrier/分片）| 针对 `merged_hop` 里已知的贵项（K1 串行 pivot、atan2 归约、reformat 链；见 `03_recorded_costs.md`）逐项定量 |

## 5. P2 —— 结构/实现改动（按 P1 的结论选一条，不预设）

| 候选 | 形态 | 预期 | 风险 |
|---|---|---|---|
| **P2-A** | **把估计器的"提取/权重"提前**：让它在网格 DMRS 符号就绪时就开跑，而不是等到跳尾 | 缩短 `ce` 的等待与 `eq_demap` 的串行段 | 与交棒次序耦合，需保证顺序正确（有 fence 机制）|
| **P2-B** | **缩短 `eq_demap` 的 GPU 执行**：按 P0-1 的 kernel 拆分，针对最贵 kernel 改线程组/占用率/代数 | 直接砍 1234 µs 的主项 | kernel 改动需逐字节/容差判据（value_net + `-L phy`）|
| **P2-C** | **前端 DFT 的批/深度调优**（若 P1-1 显示有空间）| 砍 521 µs | 与 `cbs/lane` 的约束（V4）冲突时不做 |
| **P2-D** | **池按流水线深度定尺**（`size = ceil(hold_p99 / slot) + margin`，而不是固定 8）| 用**测量**而不是拍脑袋定容量；它是"按设计定尺"，不是加大池 | **不缩短时延**；必须在 V1 达成后再按新时延重算（否则又是治标）|

**纪律**：P2 的任何条目都必须先有 P1 的读数支撑；**不许"顺手一起改"**（否则读数不可归因）。

### 5.1 ★ 建议**先做**的一条：P2-E「输入缓冲寿命解耦」（结构性、离线可验、不加提交、不加大池）

**观察（读码，已在 HEAD 核实）**：交棒那条命令缓冲里，**真正读"接收样点"的只有前端那一段**（DFT / 网格写）；
估计器、均衡、解映射读的是**网格**，不是输入。可是 keepalive token（把接收缓冲留在池外的那个引用）
是挂在**整条命令缓冲的完成**上的（`ocudu_dft_metal_engine.mm` 的 `release_block_tokens` +
`arm_tokens_on_complete` 的 `addCompletedHandler`）⇒ **输入被持有到整跳结束**，而它只需要活到"最后一个读输入的 dispatch"。

**机制已存在**：代码里**已经**用 `MTLSharedEvent` 在命令缓冲**中途**发信号
（`lib/phy/metal/ocudu_metal_queue.mm:464` 的 `encodeSignalEvent:grid_event`、`:528` 的 `stage_fence_event`），
所以"在某次 dispatch 之后发信号"是本代码库既有能力，不需要新机制。

**做法（形态，不是实现细节）**：在"最后一个读输入的 dispatch"之后 `encodeSignalEvent`（一个新事件或复用网格事件），
宿主用 `notifyListener:atValue:` **释放 token**（不阻塞任何线程）⇒ **持有期从"整跳跨度"降到"前端那一段"**。

**预期（可证伪）**：

| 量 | 现在 | 预期 | 判据 |
|---|---|---|---|
| 接收缓冲持有期 | ≈ 整跳跨度（中位 2675 µs）| ≈ `t2f` 段（中位 **521 µs**）| P0-2 的持有期直方图 |
| `[ul_rx_pool] held_max` | **8（=池）** | **≤ 3** | V2 |
| `starved_events` | 17–69 | **0** | **V2** |
| RF 失败 | 476–733 | **≤ 10** | **V3** |
| `cbs/lane` | 2.00 | **2.00（不变）** | **V4（关键：不靠加提交）** |
| `[ul_gpu_pipeline]` 中位 | 2675 | **不变（≈2675）** | **V1 不由此达成**——时延工作照旧做 |

**为什么它是对症的而不是治标**：输入的生命周期**本来**只该到"最后一个读者"；把它绑到"整跳完成"是**多持有**，
而多持有的代价正好落在池上。这不是把池加大去容纳浪费，而是**去掉浪费本身**。

**风险与反向臂**：
* 若**信号之后仍有 dispatch（或任何设备侧读者）读输入**，提前释放会让电台覆盖样点 ⇒ 数据错。**必须先审计"谁读输入"**（P0-1 的拆分正好能回答），
  并让**既有网**当反向臂：`l1_handover_arms` / `l1_hop_arms`（逐字节）、`value_net`（容差 + NO-NaN + LLR 符号）、`-L phy`、契约 8/8。
* 若该臂**全绿而 `starved_events` 不降**，说明持有期还有别的来源 ⇒ 回到 P0-2 的直方图。


## 6. 与"加大池"的关系（用户裁定，别搞混）

* **加大池 = 诊断**（P1-4）：它能**证明**因果链，但**不缩短时延**，因此**不作为交付**、也不满足 V1。
* **P2-D** 是它的"有 principled 版本"：容量**由测得的持有期分布导出**，并随时延的改善重算。
* 判据上二者必须分开：P1-4 只看 `starved_events`；P2-D 必须同时满足 V1 与 V2。

## 7. 里程碑关系与不做的事

* 本工作流**不是**"契约变红"：契约 8/8、crossings `0.00+0.00`、就地装配在**所有重载腿上仍成立**。
  它针对的是**"车道在高负载下给电台添麻烦"**——里程碑之后的新工作项。
* **不做**：用额外提交换时延（V4）；用更大的池冒充时延改善（§6）；改预登记判据去迁就某条腿（沿用主文档 §5.9.121 ⑤ 的规矩）。
