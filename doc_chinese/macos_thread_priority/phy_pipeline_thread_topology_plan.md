## 0. 目标与不变量

**目标（用户 2026-10-01 定调，本规划继承）**：让同一次运行里"同一个任务花同样的时间"，即把
`max` 压下来、`min` 不抬升；量化指标是四条尾部载体 + 三条登记率（§0bis.4）。

**本规划要改变的东西**：不是优先级，不是预算数值，而是**线程的组织方式**——
把今天"事件驱动 + 工作窃取池"的 UL 数据面，改成**若干条自定时的周期线程**，
每条只负责 pipeline 里一段**有界**的工作，并在**电台时钟**上申报自己的时间片。

**不变量（任何一步都必须满足）**

1. **Linux / Ubuntu 行为一字不变**（§7）；
2. **关着旋钮时逐字节不变**（两把钥匙：编译开关 + env）；
3. **申报形状合法**：`computation ≤ constraint < period`。反例已实测有害（开发文档 §10.31：
   `constraint < computation` 时 p50 793 / max 7277 µs）；
4. **不让路就饿死别人**：任何周期线程在自己的窗口外**必须睡**（p220/p221 的教训，§5.1）。
5. **每条线程的时间片必须来自实测**，不许拍（§4）。

| 接收策略 | **每 OFDM 符号一块**（`OCUDU_UL_RX_SYMBOLS=1`） | `[ul_rx_policy] blocks of 1 OFDM symbol` |

## 2. 为什么是"周期化"，而不是继续调优先级

三条实测结论把调度这条线封了口（开发文档 §10.57），同时把方向指向这里：

1. **优先级/档位/时间约束都不降尾部**（P4 七对腿、FIFO 一对腿），因为尾部的停顿是 **①挂起 / ②驱动阻塞**，
   而**看门狗的 `cpu_stolen` 八条腿全为 0**——"可运行却没被调度"这一类没有发生；
2. **FIFO 反而有害**：不让路 ⇒ 饿死同进程的 USB 传输与停机路径（丢 702 万样本、上行 −25%）；
3. **微基准的巨大收益不转移**（TC 540×、FIFO 19×），因为微基准量的是**睡眠线程的唤醒延迟**，
   而池线程是**事件驱动**的：它**不知道"什么时候必须动"**，只knows"活来了"。

⇒ 参考框架赢在**结构**：它的线程**知道自己该在什么绝对时刻动**（TX 由 `target_tx_time` 反推；
RX 阻塞在 `recv()` 且硬件时间戳给它刚性网格）。**周期化改造要补的正是这一条**：
给每个阶段一个**来自电台时钟的绝对时刻**，让线程"睡到 deadline − lead 再自旋"。

## 3. 目标拓扑（5 条线程，其中 2 条已存在）

```
   ┌──────────── 电台（B200，GPSDO）＝唯一时间基准 ────────────┐
   │  slot 500 µs / 符号 35.7 µs / TDD 5 ms（3 个 UL slot）   │
   └──────────────────────────────────────────────────────────┘
        │ 符号到达                        ▲ 绝对时刻发射
        ▼                                 │
  ┌───────────┐   symbol ring   ┌──────────────┐  freq-domain  ┌──────────────┐
  │ T_rx      │ ──────────────▶ │ T_fe (DFT)   │ ────────────▶ │ T_lane       │
  │ 35.7 µs   │  (已存在:pool)  │ 35.7 µs      │  (device,     │ 500 µs       │
  │ 已存在    │                 │ 新: 只 commit│   zero-copy)  │ ce+eqd 融合  │
  └───────────┘                 └──────────────┘               └──────┬───────┘
                                                                      │ LLR(device)
                                                                      ▼
                                                              ┌──────────────┐
                                                              │ T_llr        │
                                                              │ 500 µs: LDPC │
                                                              │ +TB+FAPI/MAC │
                                                              └──────────────┘
  ┌───────────┐
  │ T_tx      │  已存在：自旋到时间戳追上（不做改动）
  └───────────┘
```

### T_rx（已存在，`lower_phy_rx#0`）— 不改结构

* **触发**：电台驱动（阻塞在 `receiver.receive()`，每符号一次，28 000/s）；
* **职责**：把 IQ 搬进池（32 个整 slot buffer，`free_min=27`，从不干涸）；
* **保持原样**。**P5.1 已证"池子等待"不是瓶颈**（§10.54），不要在这里再花腿。

### T_fe（新）— 前端口：符号到达 → 提交 DFT

* **周期**：**35.7 µs**（符号节拍），相位 = 电台符号边界；
* **computation 的来源**：**今天没量到**。`[phy_pipeline] dft radio inputs` 在本模式下是 `0 transforms`
  （融合路径不经过那两条提交路线），`[metal_stats] gpu busy (front_end): commits=0`，`[ul_dft_wait]` 无样本
  ⇒ **这条线程的预算必须先补仪器**（§4.1）。用户估计"14 个符号的 FFT ≈ 40 µs CPU"——**待验证**；
* **职责边界（用户的原则）**：CPU 到此为止 = "申请时间片 → 完成 commit"；**GPU kernel 花多少时间不进这个账**。

### T_lane（新）— 信道估计 + 均衡/解调（融合 lane）

* **周期**：**500 µs**（slot 节拍），相位 = UL slot 边界；TDD 下每 5 ms 只有 3 个 slot 有活；
* **职责**：提交 `ce_weights` + `merged_hop`（今天池线程做的），把 LLR 留在设备上；
* **computation 的来源**：**已有实测**——`host: stage entry → lane commit` 中位 **101.5 µs**、
  p95 195.5、**p99 225.5**、max 862.9 ⇒ 申报 **computation = 300 µs**（覆盖 p99 并留 33% 余量）；
  `constraint = 400 µs`、`period = 500 µs`（形状合法：300 ≤ 400 < 500）；
* **交接**：`merged_hop` 的设备侧 exec p50 = **449.8 µs**，这是**设备时间**，CPU 提交完就撒手。

> ★★ **这条预算有一个前提，必须写在旁边**：101.5 µs 是**融合 lane 自己那一段**的 host 参与，
> 也就是"提交这一段的线程"的切片。而今天池的总 CPU 是 **≈800 µs/lane**（§1.3），
> 也就是**另外 ~700 µs 目前没有归属**——它可能是 t2f 的 host 侧（每 slot 14 次 DFT 提交）、
> LLR 取回/demap、LDPC、FAPI/MAC 中的任何一部分。
> **只有当 P6.0 证明那 ~700 µs 分别属于 T_fe / T_llr（而不是也压在 T_lane 上）时，300 µs 才成立。**
> 若 P6.0 显示某一段自己就 > 它的 period，**那一段就不能是"一条线程"**，而要拆成 N 条
> （例如 TDD 的 3 个连续 UL slot ⇒ 3 条同相位错开的线程，各管一个 slot）。
> **这条规则(§4.3)是本规划里最容易搞错、后果最大的一条。**

### T_llr（新）— LLR 之后：LDPC → TB → FAPI/MAC

* **周期**：**500 µs**，同样的 UL slot 相位；
* **职责**：提交 LDPC、取回 TB、CRC、组装 FAPI、交给 MAC；
* **computation 的来源**：`[ul_ldpc_decode]` 中位 60 µs / p95 106 µs 是 **WALL**（含设备），
  所以**同样需要先补 CPU 仪器**（§4.1）。用户估计"也应小于 500 µs"——**待验证**；
  若实测 p99.9 > 400 µs，则这一步**必须先拆分或继续 offload**，不能硬申报（§6 的分步条件）。

### T_tx（已存在，`lower_phy_tx#0`）— 不动

已经是参考框架的形状（`yield` 自旋到时间戳追上，注释写在 `macos_compat.cpp:817`）。

## 4. 参数从哪里来（**禁止拍脑袋**）

### 4.1 第一步必须先补的仪器：**每阶段 CPU 归属**（P6.0）

今天的缺口，一句话：**我们知道每个阶段的 WALL，但不知道每个阶段的 CPU**。
于是"池线程 43% 一个核都花在哪"无法回答，而这正是"离'CPU 上只剩 commit'还有多远"的唯一读数。

**设计**（在既有地标上加，不加新地标）：

| 地标 | 位置 | 表示 |
|---|---|---|
| `record_start` | `ul_process()` | slot 开始 |
| `record_t2f_end` | 整 slot 频域就绪 | T_fe 的产出 |
| `record_ce_end` | 数据符号估计就绪 | T_lane 的第一段结束 |
| `record_ldpc_start` | LLR 就绪 | T_lane 结束 / T_llr 起点 |
| `record_end_crc_ok` | TB 通过 CRC | T_llr 的产出 |
| `record_fapi_mac_end` | 交给 MAC | 交付 |

在每个地标读一次**本线程 CPU**（`this_thread_cpu_ns()`，一次 Mach 调用），
**仅当上一条地标与本条在同一线程、同一 slot** 时记一个 CPU 增量，按阶段归入直方图；
不连续就**计数并跳过**（`not_contiguous`），在报告里打印连续率——**不许把跨线程的增量当成一个阶段的 CPU**。

**内建自检（这条比数字本身重要）**：各阶段 CPU 之和，必须与
`[ul_thread_cpu]` 的池总 CPU（43% 一个核那一行）在**同一条腿上对得上**（差 < 10%）。
对不上就说明归属漏了阶段或漏了线程，**先修仪器再谈结论**。

**反向臂**：造一个"已知 CPU 形状"的臂（例如只在一个阶段里烧 200 µs），
各阶段直方图必须只有那一个阶段动——测的是归属算术，不是时钟。

### 4.2 每条线程的申报参数表（**飞腿前**填，来源一栏不许空）

| 线程 | period | computation（来源）| constraint | phase（来源）| 保留核数占比 |
|---|---|---|---|---|
| T_fe | 35.7 µs | 待 P6.0 | 待定 | 符号边界（电台）| ? |
| T_lane | 500 µs | **300 µs**（host 参与 p99 225.5 × 1.33）| 400 µs | UL slot 边界 | 60% × 有活比例 |
| T_llr | 500 µs | 待 P6.0 | 待定 | UL slot 边界 | ? |

★ **"保留核数占比"一列必须先算**：`Σ computation/period` 是所有线程的**预留总量**，
必须给**非我们控制的线程**（UHD 的 USB 传输线程、电台驱动、内核）留出余量。
今天的池只需要 **43% 一个核**，而 3 条周期线程若按上表预留，光 T_lane 就是 **60%**；
**总预留要压在 ~1.5 核以内**（14 核机器），并在腿上核对 `[ul_rx] rx_overflows/gaps` 是否为 0——
p221 的教训就是"预留挤掉了数据源"。

### 4.3 ★ 一条线程还是 N 条：由 P6.0 的读数决定，不由偏好决定

判据只有一条，而且它是算术：

```
若 某阶段的 CPU p99.9 ≤ period × 0.6   ⇒ 该阶段可以用 1 条线程（留 40% 余量）
若 超过                                ⇒ 该阶段拆成 N 条同相位错开的线程（N = ceil(p99.9 / (period×0.6))）
```

并且**每拆一条就把总预留加一份**（§4.2 的上限仍然适用）。
TDD 的 3 个连续 UL slot 是天然的拆分维度：3 条同周期、相位各偏 500 µs 的线程，
每条只需承担一个 slot 的活。

## 5. 风险清单与反向臂（每条都来自我们自己的实测）

### 5.1 ★ 不让路 ⇒ 饿死数据源（p220/p221，已实测）

FIFO 臂：看门狗唤醒线程被饿 **100 ms**（对照 0.93 ms）、`runnable>0` 只在臂腿出现（6/16）、
电台 **3 次 overflow**、丢 **7 025 564** 个样本、上行 −25%、`gaps=3`。
**⇒ 本规划的硬约束**：周期线程在自己的 `computation` 用完后**必须回睡**；
`computation < period` **不是建议**；并在腿上把 `gaps / rx_overflows / dl AT/BELOW 0` 当**红线**。

### 5.2 有害形状：`constraint < computation`（开发文档 §10.31）

实测 p50 793 / max 7277 µs。**申报前逐条检查形状**，并让代码在解析时**拒绝**非法形状（已有）。

### 5.3 相位错位会**增加**延迟（本规划新增的风险）

周期预留是**按相位**给的。若线程的激活到达相位与预留相位错开，最坏要等
`period − computation`（T_lane 是 200 µs）**才拿到 CPU**——比今天"被唤醒"的 ~100 µs 更差。
⇒ **相位必须来自电台时钟**，并且**必须量**：用 P5.0 的节拍锚点（`OCUDU_UL_SLOT_GRID`）
按线程分别读残差（现在只有 CE 一个地标；P6.0 要把它扩到各阶段地标）。
**反向臂**：故意把相位偏 250 µs，锚点残差必须出现一个 +250 µs 的台阶。

### 5.4 超额申报是免费的（开发文档 §10.30）

实测：持续 4.6× 超申报、92% 占空仍然正常。⇒ 宁可多报（覆盖 max），不要少报；
但**总预留**仍受 §4.2 的余量约束。

### 5.5 看门狗看不见 < 1 ms 的抢占（开发文档 §10.59(3)）

它每 1 ms 采一次、阈值 100 µs ⇒ 200 µs 的抢占会被判为 "advanced"。
**而本规划的激活正好在 ~100 µs 尺度。** ⇒ 这一层的证据只能来自
`host cpu: stage entry → lane commit`（新增）与"每阶段 CPU"，
**`cpu_stolen = 0` 不能再用作"没有对象"的证据**。

### 5.6 GPU 在关键路径上（本规划新增）

`merged_hop exec p50 = 449.8 µs`（占 lane busy 的 93%）**在一个 500 µs 的 slot 里**。
CPU 侧再完美，这条 lane 的完成时刻也由设备决定 ⇒ **GPU 的排队与抢占（DL 侧同时用 GPU）
是这套周期化的上游不确定性**；规划里必须留一条"设备侧"的观测线（`[metal_stats] wait/exec` +
`[ul_gpu_lane] gap`），并在判据里把"设备占满"和"CPU 迟到"分开。

## 6. 分步落地（每步单独一条腿、单独一个提交、单独一条回滚路径）

| 步 | 内容 | 判据（飞腿前登记）| 回退条件 |
|---|---|---|---|
| **P6.0** | **仪器**：每阶段 CPU 归属 + 各阶段相位锚点 | 各阶段 CPU 之和与池总 CPU 对账（<10%）；反向臂只有一个阶段动；相位反向臂出 +250 µs 台阶 | 对不上账 ⇒ 修仪器，不飞臂 |
| **P6.1** | **一条线程**：把 **T_lane**（lane 提交）改成周期线程（500/300/400 µs，相位 = UL slot）| 该阶段 host 参与的 p95/p99 下降；`gaps=0`；`rx_overflows=0`；三条率不越界；**`[ul_sched]` 回读申报值** | 尾部任一条变差 / `gaps>0` / 体量未改善 ⇒ 撤回（保持默认关）|
| **P6.2** | **T_llr**（LLR 之后）同样周期化 | 同 P6.1 + `ldpc` 与 `ul_pipeline` 的 p95/p99 | 同 P6.1 |
| **P6.3** | **T_fe**（每符号 DFT 提交，35.7 µs）| 同 P6.1；额外看 `t2f` 的 p95/p99 与设备侧 `front_end` 忙 | 同 P6.1；**若 35.7 µs 周期下总预留超过 1.5 核 ⇒ 退回 500 µs 周期** |

## 8. 什么会**否证**这个规划（先写下来，免得事后找理由）

1. **P6.0 量出某个阶段的 CPU p99.9 > 它的 period** ⇒ 该阶段不能周期化，
   必须先拆小或继续 offload（用户的原则是"CPU 上只剩 commit"，这条读数就是说这句话有没有做到）；
2. **总预留 > 1.5 核**，或腿上出现 `gaps>0` / `rx_overflows>0` ⇒ 周期化在抢数据源的 CPU，方案要缩；
3. **相位无法对齐**（各阶段激活相对 slot 网格的相位漂移 > 50 µs，且不收敛）⇒ 周期预留的前提不成立；
4. **设备侧成为主导**（`merged_hop exec` 或其排队时间随 DL 负载增长）⇒ 瓶颈不在 CPU 调度，
   本规划只能拿到很小的一部分；
5. **体量（p95/p99）不动**，只有尾部率变好 ⇒ 与 P4/FIFO 同类，按 §5.1 的红线判断是否值得留。

## 10.2 周期取 **35.7 µs** 还是 **500 µs**：用实测决定，不用偏好

两条路都"读 IQ → FFT/提交 → 写网格"，差别在**什么时候开始**：

| | 周期 35.7 µs（每符号）| 周期 500 µs（每 slot）|
|---|---|---|
| 开始时刻 | 该符号样本一到就做 | **要等 slot 最后一个样本**（整 slot 策略的原文代价）|
| 实测对照 | `t2f 496.2 µs`、hop −25 µs（**当前默认**）| `t2f 536.0 µs`（历史策略，已被替换）|
| 激活次数 | 28 000/s | 2 000/s |
| 预留（按 CPU-vDSP 3 µs / 40 µs，取候选上界）| 10 µs / 35.7 µs = **28%** 一个核 | 60 µs / 500 µs = **12%** 一个核 |
| 实现难度 | 每符号一次 deadline 计算；暴露的只有最后一个 | 一次激活装 14 个变换；但把 40 µs 的延迟加回关键路径 |

**推荐 35.7 µs（每符号）**，理由全部是实测：① 它已经是当前默认且实测更好（−40 µs / hop −25 µs）；
② "13 个藏在到达节拍里、只有最后 1 个暴露"这条结论只有在每符号下成立；
③ 用户上一轮的原话也正是"周期就是一个 OFDM 符号的长度（～35 µs）"。
**若**总预留（§4.2 的 1.5 核上限）在每符号下不可接受，再退到 500 µs——**回退路径是现成的，因为两种粒度代码里都还在**。

## 10.3 这条线程的契约（草案；参数必须由 §10.4 的仪器填）

```cpp
// 一个 OFDM 符号的 FFT 提交线程（macOS 独占 + 默认关 + 两把钥匙）
period      = 35.7 us                 // 符号节拍（30 kHz SCS）
phase       = 电台符号边界            // 由 RX 时间戳导出，手法同 tx_subframe_uhd.cpp 的 target_tx_time
deadline    = 符号边界 + delivery_lead
computation = 待测；候选 10 us        // 见 §10.4：CPU-vDSP 路径每符号 ≈ 2.9 us + 编码开销
constraint  = 15 us                   // 形状必须 computation <= constraint < period
循环        = 睡到 (deadline − spin_margin) 再自旋 → 读该符号 IQ → (CPU FFT | encode+commit) → 写网格 → 回睡
```

* **`delivery_lead` 是可测的**：`tx_slack_note_receive()` 已经在维护"电台时间戳 ↔ 宿主时刻"的映射，
  所以"符号边界 → 样本可读"的分布**直接从既有仪器读**，不需要新接线；
* **GPU 时间不进这个账**（用户原则）：CPU 在 commit 处结束使命；
* **窗口外必须睡**（§5.1 的红线）；
* **不做**：不改数据流、不改 GPU 派发顺序、不改 FAPI/MAC 交付内容（§7 第 4 条）。

# 11. ★★★ P6.1-SLOT：**一条"每 slot 醒一次"的周期线程**（用户 2026-10-03 定稿；**先做这一段**）

> **本节的两次修订都已并入正文**（2026-10-03 下午，用户六条修正）：
> ① 目标明确为 **UL PHY pipeline 的节拍确定性**；
> ② ~~设备时间必须 < period~~ **撤销**——CPU 把 CB 扔给 GPU 就完成使命，GPU 花多久与它无关
> （后端另有一条解耦的线程按 GPU 完成时刻接管 LLR）；
> ③ DL 今天仍全在 CPU ⇒ 暂无 GPU 竞争；
> ④ 电台/USB 投递晚是 UHD 驱动与 macOS 之间的事，**另案处理**，不作为本节的否证条件；
> ⑤ `period` 按 SCS **参数化**（取 `slot_duration`），`computation/constraint` 是**可调参数**不是定值；
> ⑥ "提交或跳过"改成 **"有界等待后提交或跳过"**（推迟有界，不是无限期等待）。

## 11.1 这条路的三个前提，**都已经在树里或已实测**

| # | 前提 | 证据 |
|---|---|---|

## 11.2 与今天默认的**根本差别**（设计要点，不是参数差异）

| | 今天（事件驱动 + 工作窃取池）| 本方案（自定时 + 有界等待）|
|---|---|---|
| 何时开始 | **数据到了才醒** | **按 slot 节拍醒**，与数据是否到达无关 |

| 数据晚到怎么办 | **等着**（无限期）⇒ 节拍被拖走 | **有界等待**（50–100 µs）后提交或跳过 ⇒ **推迟有界** |
| CPU 的工作量 | 池 5 条线程共 ≈**800 µs/lane** | **一条线程 ≈101.5 µs/slot**，只做 encode+commit |

## 11.3 ★ 两段式时间线：**有界等待 + 提交或跳过**

用户 2026-10-03 的修正（原方案是"醒来看一眼，不齐就跳过"，太硬）：

```
wake_at = slot_boundary − wake_lead            // wake_lead = 50~100 µs（待定），用来吸收唤醒时刻自身的抖动
醒来 → 轮询"该 slot 的样本是否已齐"：
        齐 → 立刻 encode + commit（正常路径）
        到 wake_lead 用尽仍不齐 → **跳过并计数**（绝不等待、绝不提交半份数据）
```

* **关键性质：推迟是有界的**（上界 = `wake_lead`），而不是"等到天荒地老"——今天的事件驱动正是后者；
* `wake_lead` 是**架构参数**：它同时决定"能容忍多大的投递抖动"和"最坏推迟多少"；
* `wake_lead` 与 **lead**（数据比 slot 早多久就绪）是两个不同的量：前者是**醒来后的等待预算**，
  后者是**数据本身的提前量**（本方案仍取 ≥1 个 slot，见 §11.4）；
* 配套：**跳过计数 + 跳过原因**是**一等指标**（与 `gaps` 同级），它直接量化 `wake_lead`/lead 够不够。

## 11.5 后端线程：**与前端解耦，周期跟着 GPU 走**

用户 2026-10-03 的架构澄清：

```
T_commit（本节主角）  周期 = slot_duration，只做 encode + commit，扔完 CB 就抽身
      ↓（GPU 执行融合 kernel：DFT+CE+EQ+demap，设备时间 ≈450 µs，**与 T_commit 无关**）
T_llr（后续）         在 GPU 完成后接管 LLR → LDPC → TB → FAPI/MAC
                      它与 T_commit **解耦**；其周期取决于 GPU kernel 实际花了多久
```

* **设备时间不再是本方案的约束**（撤销原 §11.5/§11.9 的论证）：一个 slot 装不下也没关系，
  CB 排队即可；只是后端线程醒来的时刻会跟着晚；
* **后端线程的申报方式取决于 GPU 时间的分布**（这是一个待测的分支）：
  * GPU lane 时间**稳定**（p99−p50 小）⇒ 后端也可按固定周期申报 TC；
  * GPU lane 时间**不稳定** ⇒ 后端应由**完成事件触发 + 有界等待**（同 §11.3 的两段式），
    而不是硬套一个周期——**这一条由 P6.0 的仪器决定，先不预设**；
* **DL 竞争暂不存在**（用户说明：DL 计算今天仍全在 CPU）。若将来 DL 上 GPU，§11.6 的设备侧观测线要重估。

## 11.6 TC 能治什么、**不能**治什么（诚实，不夸大）

| | 结论 | 依据 |
|---|---|---|
| ✅ **能治**：CPU 线程自身被守护进程风暴挤占 | 微基准 2× 超订下唤醒迟到 **103 → 3 µs**；反面教材是 p220/p221：被别的 RT 线程挤时唤醒线程被饿 **100 ms** | §10.55、§10.57 |
| ➖ **不管**：GPU kernel 花多久 | **按设计抽身**（§11.5）；只影响后端线程的醒来时刻 | 用户 2026-10-03 |
| ➖ **另案**：电台/USB 投递晚 | UHD 驱动与 macOS 之间，我们控制不了；若成为突出问题**另案处理** | 用户 2026-10-03 |
| ★ **本方案的价值在"不传播"** | 提交节拍固定 ⇒ 一次停顿不再累积到后面每个阶段。今天 `t2f max=6558 µs`、`ul_pipeline max=7707 µs` 里有相当一部分是**传播**出来的 | 需 §11.8 的仪器证实/否证 |

**判决性读数**：把 P5.0 的节拍锚点（`OCUDU_UL_SLOT_GRID`，今天挂在 CE 地标）**改挂到 commit 地标**
⇒ 残差应从"几十~几千 µs"收敛到 **µs 级**。这是"节拍确定性"的直接测量，也是本方案成败的判据。

## 11.7 ★ 用户提出的问题：`max = 862.9 µs` 是不是**提交中途被干扰**的结果？

用户判断："从道理上讲，提交的时间应该是非常稳定的。" **这个判断可以用仪器判定，但 p220 这条腿还判不了**：

* `host: stage entry → lane commit` 是 **WALL**（中位 101.5、p99 225.5、max 862.9）。WALL 里既可能有
  "真的做得多"（罕见路径：首帧、分配、大 TB），也可能有**被抢占**（提交中途被换下 CPU）；
* **p99/p50 = 2.2** 这个形状**两种解释都成立**，所以不能从分布本身下结论；
* ⇒ **本次提交已经加上了判据性的那一半**：`[ul_gpu_lane] host cpu: stage entry → lane commit`
  （同一窗口的 **THREAD CPU**）。下一对腿里：
  * `cpu ≈ wall` ⇒ 862.9 µs 是**真实工作**，提交本身不稳；
  * `cpu ≪ wall` ⇒ **就是被抢占**，那么"TC 让提交稳定"这条主张在**正确尺度**上被证实。
* ★ 顺带说明为什么这个问题重要：`computation` 只能按 **CPU** 申报。
  如果 862.9 µs 里大半是抢占，那么申报 `computation = 300 µs` 是**诚实**的（工作只需 300 µs），
  而抢占正是 TC 要消灭的东西；反之若它是真实工作，申报 300 µs 就是**少报**，必须抬到 ~900 µs。

**可以先离线回答**（P6.0 的第一条反向臂，见 §11.8 #6）：写一个 **Metal commit 稳定性微基准**——
在 500 µs 节拍上反复 encode+commit 一个（真/假）kernel，量 **wall / CPU** 两个分布，
四臂（baseline / QoS / TC / FIFO）×（idle / hostile）。它不需要电台，几分钟就能给出
"提交时间到底稳不稳、TC 能不能让它稳"这两个数。**这与 §10.55 的做法一致：微基准先证明机制，再花机器时间飞腿。**

## 11.8 先补的仪器（**P6.0-SLOT**，loopback 可验）

| # | 量 | 用途 |
|---|---|---|
| 1 | 每 slot 的 **wait / host cpu / device** 三段分开 | `computation` 的唯一合法来源；把"等"和"做"分开 |
| 2 | **投递延迟分布**（电台 slot 边界 → 样本就绪）| 定数据 lead（≥1 slot 的依据）|
| 3 | **commit 地标的节拍锚点**（P5.0 改挂）| 判决性读数：残差是否收敛到 µs 级 |
| 4 | **跳过计数 + 原因**（样本未到 / 有界等待用尽）| `wake_lead` 与 lead 够不够 |
| 5 | **GPU lane 时间的分布**（p50/p99，及"完成 → 后端醒来"的间隔）| 决定后端线程是"固定周期申报"还是"完成事件 + 有界等待"（§11.5）|
| 6 | **Metal commit 稳定性微基准**（离线，四臂 × 两工况）| 回答 §11.7 的问题，并给出 `computation` 的实证起点 |

**反向臂**：① 关掉申报（跑默认）⇒ 锚点残差必须显著变大；② `wake_lead = 0`（即"不等待"）⇒ 跳过率必须上升；
③ 数据 lead 设为 0（等到样本才提交）⇒ 必须复现今天的**传播**（`max` 回到 ms 级）。

## 11.9 什么会否证本方案

1. **锚点残差没有收敛**（挂到 commit 后仍是 ms 级）⇒ "节拍确定性"不成立——**这是唯一的判决性否证**；
2. **跳过率 > 0.1%** 且加大 `wake_lead` 与 lead 后仍不降 ⇒ 投递延迟本身不可预测（归入"另案"，见 §11.6）；
3. **红线被踩**（`gaps>0` / `rx_overflows>0` / 任一登记率越界）⇒ 预留挤到了数据源（p220/p221 的教训）。

## 11.11 接线设计：**不需要重构 pipeline**，只需要"换一条线程 + 加一个节拍门"

今天 PUSCH lane 的任务跑在 **medium pool**（`main_pool#0..#4`，5 条线程）上：

```cpp
// du_low_executor_mapper.cpp:121-125
auto pusch_srs_execs = create_task_fork_limiter(flexible.non_rt_medium_prio_exec,
                                                flexible.max_pusch_and_srs_concurrency, ...);
phy_config.pusch_executor = pusch_srs_execs[1];
```

而 `max_concurrency <= 1` 会返回一个 **STRAND**（同一时刻只有一个 PUSCH hop）——这一点代码注释里已经写明。
⇒ 本方案的接线只有两件事：

1. **一条独占线程**：给 PUSCH lane 一个**专用 executor**（自己的线程名，如 `pusch_lane`），不再与 medium pool 共享。
   今天 `[sched]` 已经逐线程打印档位，新的线程会自然出现在那一行里，便于回读；
2. **周期化 + 申报**：
   * **节拍门**：在该线程每次处理一个 PUSCH hop 之前，
     `睡到 (slot_boundary − wake_lead)` → **有界等待**该 slot 数据就绪 → 提交 或 跳过并计数（§11.3）；
   * **申报**：用**现成的** `OCUDU_SCHED_TIME_CONSTRAINT`（它今天就支持**按线程名**逐线程选择，
     见 `macos_compat` 的解析器与 §10.45 的七对腿），申报值取 §11.4 的参数表。

**数据流、GPU 派发顺序、FAPI/MAC 交付内容都不动**（§7 第 4 条）。
`OCUDU_UL_RX_POLL_WAIT` 保持关（P5.1 已证在这套配置下是 no-op，§10.54）。

**前置检查（落地前必须过）**：新线程创建后，`[sched]` 必须能回读到它是**独占**的（不在 `main_pool` 里），
且申报值与回读值一致——否则这条腿是"没接上"，不是"没效果"（P5.1 的教训：先证明变量到达了线程）。

### 为什么 #2 不可测（诚实结论，而不是糊过去）

**电台时间戳只是样本计数器，不是绝对时间。** 宿主侧唯一的时间信息是"最新一对 `(radio_ts, host_ns)`"，
所以"这个样本是多久以前在空中"**无法从现有读数算出**——那需要电台的绝对时钟（GPSDO 给得出，但接进来是另一条线）。
宿主能测的只有"相对最新配对"的量，而那正是 `[ul_rx_wait]` 已经给的"这次 `receive()` 等了多久"。

⇒ **lead 不靠测，靠运行中判定**：先定 **1 个 slot**；若锚点出现斜偏/漂移，或**跳过率 > 0.1%**，就把 lead 加到 2 个 slot。
这是一个**运营参数**，不是一个需要新仪器的未知量。

## 11.13 P6.1-SLOT 第一半已落地（2026-10-03 晚）：**lane 网格**（`OCUDU_UL_LANE_GRID`，macOS 独占 + 默认关）

### (1) 它是什么：一条**宿主时基的固定网格**，不是一段延迟

计划的核心机制，也是"为什么是时钟而不是延迟"：**延迟消不掉抖动，时钟才能**。
今天一个 hop 的提交时刻是"数据什么时候到"的函数，所以传输抖动与调度停顿都会移动它；
网格给提交一个**自己的时基**：

| 规则 | 内容 | 为什么 |
|---|---|---|
| **锚定一次** | 以**第一个 hop 的到达时刻**为锚，之后**按整 slot 时长推进** | 单个晚到的 hop 不能移动它 |
| **只往回拉，且很慢** | 观测**早于**网格超过 `deadband`（默认 50 µs）时，按残差的 **1/64** 回拉；**晚到绝不移动它** | 跟随传输的**下界**（稳定），而不是它的尾巴（不稳）|
| **越界重锚** | 残差超出 `[−4 slot, +2 slot]` 时重锚并**计数** | 启动、流重启、多 slot 级中断——滤波跟不上的情形 |
| **闸门** | 在 lane 的 stage entry：不到该 slot 的网格时刻就等；**>100 µs 睡、最后 100 µs 用 `yield` 自旋** | Darwin 会合并短睡眠，纯睡会留下几十 µs 的抖动——正是这里要消掉的东西 |

**观测点在闸门之前**（hop 自己的到达时刻）——网格跟的是"最快到达"这个稳定下界；
若观测点在闸门之后，钳位后的时刻永远是网格本身，滤波就再也看不到漂移（这一点在实现时被专门避开）。

### (2) 它报什么，以及**先看哪个数**

```
[lane_grid] OCUDU_UL_LANE_GRID=1: grid armed from N hop(s), re-armed M time(s);
            clamped=C (mean wait X us, max Y us); late=L; unarmed=U
```

★ **`late` 是 lead 的判决**：它数的是"闸门跑起来时该 slot 的网格时刻**已经过去**"的 hop。
`late` 占比高 ⇒ lead 不够（把 `OCUDU_UL_LANE_GRID_LEAD_US` 调大）；
`clamped` 的等待就是**被刻意加进去的相位对齐延迟**（上界 = lead）。
`unarmed` 非零 ⇒ 网格还没锚上（没有 hop 或旋钮没生效）。

#### 由此定下的两个参数（**推导出来，不是拍的**）

| 参数 | 值 | 依据 |
|---|---|---|
| **重锚带** | **±8 slot（4 ms）** | 它只为"滤波跟不上的情形"存在（启动、流重启、多 slot 中断），那些是**秒级**的；正常散布永远够不到 |
| **跟踪增益** | **1/1024（`OCUDU_UL_LANE_GRID_GAIN_SHIFT`，默认 10）** | 一阶滤波**会把自己滤掉的噪声传出去**：`σ_grid ≈ σ_arrival·√(g/2)`。g=1/64、σ_arrival≈2 ms ⇒ 网格自身游走 **~180 µs**（与要消掉的抖动同量级）；g=1/1024 ⇒ **~45 µs**，而 ppm 级时钟漂移的时间常数仍只有 ~8 s |

旧的 `OCUDU_UL_LANE_GRID_DEADBAND_US` 随它服务的规则一起删除（**留着不用的旋钮就是下一次误读的来源**）。

#### 新增读数：**`overshoot`**——钳位自身的精度

```
[lane_grid] ... clamped=C (mean wait X us, max Y us; overshoot mean Z us, max W us); late=L; ...
```

`overshoot` = 钳位真正返回时**越过自己目标**多少（= `now − target`）。
它分开两件 wait 分布分不开的事：**钳位很准**（几 µs，自旋的分辨率）vs **线程在自己的钳位里被换下 CPU**。
后者正是 TC 要治的、而 1 ms 看门狗**看不见**的那一层（§10.59(3)）。
离线段实测：**mean 0.1 µs / max 31 µs** ⇒ 自旋尾部有效。

#### 下一次飞行要读的四个数

1. **`re-armed`**：应当只剩"启动那一次"（个位数）——若仍占几个百分点，说明还有别的东西在推动它；
2. **`late` 占比**：修正后它是真正的"lead 够不够"读数；
3. **`overshoot max`**：若是几十 µs ⇒ 钳位准；若是毫秒级 ⇒ **线程在钳位内被抢占，这就是 TC 的对象**（也是 §10.60 微基准给出的同一结论）；
4. **`COMMIT` 残差 p50/p95**：被钳住的那部分应当落在**同一个偏移**上（拟合残差≈0），p95 反映的是"晚到、钳不住"的那条尾巴。

### 11.16 p225（修正参数 + `LEAD_US=1500`）：**机制工作了，但代价是 +2 ms 延迟，而且越了一条登记红线**

| 读数 | p225 | 判定 |
|---|---|---|
| `[lane_grid]` | armed 323 646、**re-armed 108（0.03%）**、**clamped 321 539（99.3%）**、**late 2 107（0.65%）** | ✅ 带子修好、钳位按设计工作 |
| `overshoot` | **mean 3.3 µs** / **max 10 093 µs** | 钳位精度好；**但确有 hop 在自己的钳位里被抢占 10 ms** —— 那正是 TC 的对象 |
| `ul_channel_estimation` 中位 | 70.2 → **2 133.7 µs** | **闸门把 lead 全额付成了延迟** |
| `ul_pipeline` 中位 | 1 337 → **3 380 µs**（每窗 35 273/35 274 样本 > 2000 µs）| **延迟翻倍，逐 slot 都付** |
| `AT/BELOW 0`（≤0.0025%）| 58 / 1 302 403 = **0.00445%** | ❌ **越界 1.8 倍** |
| `slip` / `recv` | 0.00041% / 0.00036% | ⚠ 界内，但比 p224 涨 3–4 倍 |
| `gaps` / overflow / contract | 0 / 0 / MET (8/9) | ✅ |
| 锚点残差 p50/p95 | 3 962 / 18 852 µs | ❌ 比 p223 差；**其中相当一部分是仪器**（见下） |

#### (1) 判决：**按预登记，这一臂判负**（红线被越）

§11.10 写死："任一步触红线 ⇒ 保持默认关、撤回代码路径"。`AT/BELOW 0` 越界 1.8 倍，因此**不采纳**。
诚实补充：p224（同样的接缝、更大的平均等待 1854 µs）该率是 0.00115% ✅，所以**这条越界不能简单归因于闸门**——
两条腿的机器条件也不同（`load1` 9.10 vs 5.95、RF 失败 395 次）。但预登记的规则就是规则：**越界即不采纳**，
而"延迟翻倍 + 节拍没变好"本来也不值得采纳。

#### (2) 为什么钳位**注定**做不到节拍确定性（这一轮最重要的结论）

`overshoot mean 3.3 µs` 说明**钳位很准**：提交确实落在 `grid + lead` 上。
但锚点残差 4–19 ms 说明**那个 grid 自己在动**——因为网格跟的是**到达的均值**，而上游的到达均值本身在毫秒级漂移
（半均 ±3 530 µs）。**钳位只能消掉"围绕均值的快抖动"，消不掉"均值本身的慢漂移"。**

⇒ 与 §11.14/§11.15 的推理合起来：**在上游仍然是"活到了才动"的前提下，任何钳位都是把抖动换成延迟。**
要真正拿到节拍确定性，必须**上游也确定**——即用户设计的那条"按自己的网格醒、去把活取走"的线程（P6.1b）。
**闸门这条路到此为止：不采纳、不再调参。**

#### (3) 顺带修掉的第三个仪器缺陷（与 p219 同类）

p225 的锚点带着 `backward=42 (largest 7880 slot(s))`。残差**随最大乱序幅度单调变化**：
p223 9 slot → p95 190 µs；p224 11 → 2 270 µs；p225 **7 880 → 18 852 µs**。相关性太干净，指向拟合被污染：
一个"为几秒前那个 slot 归档的地标"（重复、迟到的重跑、陈旧 PDU）在**最小二乘**里会把整条线拉走。
规则改为：**小乱序（≤8 slot，即在途深度）照留**（那是真观测）；**大乱序排除出拟合并计数**（`... N excluded from the fit`），
与 wrap 阈值同一条纪律——**乱序样本永远不是时钟读数**。新增反向臂：归档一个旧 200 slot 的地标，
拟合必须仍是 500.0 µs / 残差 0，且该样本必须被**计数为排除**。

（该反向臂的第一版自己就写错了：它传了一个生产路径不可能产生的计数值（`2*HYPERFRAME-200`），
读成一次巨大的**向前**跳，于是它"证反了"——测试失败时恰好证明了它名字的反面。已修正并记在文件里。）

## 11.17 ★★ 弹性网格（用户 2026-10-03 补充）：`lead` 与 `max_wait` 之间是一条**有弹性的带**

原方案（我飞过的钳位）只有一个参数 `lead`：**"不早于"** `grid + lead`，而且**从不跳过**（数据永远已经在了）。
用户指出的正确形态是：

```
wake_at = grid(slot) + lead                 ← 最早可以动
   在 [wake_at, wake_at + max_wait] 之间轮询"数据是否到齐"
      到齐 → 立刻提交（落点就在这条带里的某处，具体在哪取决于数据何时到齐）
   max_wait 用尽仍不齐 → 跳过并计数
```

**这条"带"才是设计**：`lead` 决定**最早相位**，`max_wait` 决定**最坏推迟**，落点在两者之间由数据决定。
`max_wait = 0` ⇒ 完全刚性（提交恒在 `grid+lead`，跳过率 = 数据未及时到齐的比例）；
`max_wait = ∞` ⇒ 回落到原来的"无限等待"，**跳过率 = 0**。

### ★ 跳过率是**因变量**，不是判据（用户 2026-10-03）

原登记把"跳过率 ≤0.1%"写成红线——**这是错的**，因为跳过率是 `max_wait` 的函数，而 `max_wait` 该取多少
由**应用层**决定。判据改为：

| 层 | 量 | 角色 |
|---|---|---|
| **应用层（判据）** | **ping 时延**（p50/p99/max）、**iperf3 吞吐与稳定性** | 决定 `max_wait` 该取多少 |
| PHY 层（解释） | 跳过率、`late`、`overshoot`、`COMMIT` 锚点残差 | 解释应用层为什么是这样，**不再是红线** |
| 红线（不变） | `gaps==0`、`rx_overflows==0`、三条登记率、`min` 不升、总预留 ≤1.5 核 | 安全边界 |

**扫描设计**：`max_wait ∈ {0, 0.5 ms, 1 ms, 2 ms, ∞}` × 应用层指标。每个 `max_wait` 都给出
"（跳过率，ping/iperf3）"一个点，**这条曲线就是交付决策的依据**。

### ★★ 为什么弹性带能成立，而我的钳位不能（结构性区别，不是参数区别）

| | 我飞过的钳位（p224/p225） | 弹性线程（本节） |
|---|---|---|
| 何时**开始** | **数据到达之后**（活被派发下来才轮到它）| **按自己的网格醒**（可能早于数据）|
| 网格锚在哪 | lane 到达时刻 ⇒ 跟着**上游的毫秒级漂移**走 | 电台时间 ⇒ 跟**传输的 ppm 级漂移**走（见 §11.18）|
| 数据晚了怎么办 | **无限等**（所以继承了数据的时刻）| **最多等 `max_wait`，否则跳过**（保住节拍）|

⇒ p225 的结论（"钳位只是把抖动换成延迟"）**只针对那种形态**：它没有"跳过"这个选项，所以没有东西保护节拍。
**弹性线程有**——它用"丢掉那个 slot"换"节拍不被动摇"，而这正是用户设计里那句"只有在最大等待时间数据还没有到齐就跳过"。

## 11.18 ★★ 锚信号：以 **UHD 绝对时间**为基准（用户 2026-10-03 补充）

### (1) 今天我的锚错在哪

我的网格把 `(slot, 宿主时刻)` 当成观测，再用一阶滤波去追它的**均值**。问题在于观测里含的是
**整条上游 pipeline 的毫秒级漂移**（数据驱动、TDD 突发、共享池排队），于是网格忠实地跟着**要消掉的那个量**走
（p224/p225：钳位精度 3 µs，锚点残差 4–19 ms）。**滤波器 + 增益 + 重锚带这一整套，是在给一个不该被跟踪的信号做平滑。**

### (2) 参考框架的做法：**映射一次，之后是外推**

`tx_subframe_uhd.cpp`：开跑时把 `usrp->get_time_now()` 与 `mach_absolute_time()` 做**一次**基准映射，
之后每个 TTI 由 `target_tx_time`（电台**绝对**时间）反推宿主唤醒时刻，**每 1000 TTI 纠偏一次**。
⇒ 网格是一条**计算出来的直线**（`host = a + radio_abs`），**不是**一条被滤波的观测序列：
没有增益、没有带宽、没有"追均值"，而逐次到达的抖动**根本进不到网格里**。

### (3) 树里已经有的东西（这不是新发明）

* `radio_uhd_rx_stream.cpp`：`ret.ts = md.time_spec.to_ticks(srate_Hz)` —— **样本计数就是绝对时间的仿射像**
  （`time_spec` 在 GPSDO 下是绝对时间，`clock_source=gpsdo` 我们已在用）。所以**速率是精确的**；
* `tx_slack_note_receive(radio_ts + nof_samples, host_ns)`：宿主侧已经在维护这一对（每接收一次刷新）；
* DL 侧 `metadata.ts = timestamp + tx_time_offset` + `md.time_spec`：**发射侧本来就是绝对时间**；
* TX 等待 `wait_for_tx_timestamp()`：本来就是"自旋到时间戳追上"。

⇒ 需要补的只有一件：**把接收流的时间基（`time_spec`）从驱动发布到 lower PHY**，让网格能用
`host(radio_abs) = a + (radio_abs − radio_abs_anchor)` 直接算，而不是靠滤波去猜。
（这是 `lib/radio/uhd/` 的一处小改动，与 TX 侧对称。）

### (4) 由此得到的三个量，都是**直接可测**的

| 量 | 定义 | 用途 |
|---|---|---|
| **传输投递延迟** | `host_now − host_equivalent(样本的绝对时间)` | **`lead` 的来源**（我此前说"不可测"的那个量，有了绝对时间就可测） |
| **偏移漂移** | 上述延迟随时间的慢变化 | 决定"多久重同步一次"（参考：每 1000 TTI） |
| **弹性带落点** | 提交时刻在 `[lead, lead+max_wait]` 里的位置分布 | 与 §11.17 的扫描一起决定 `max_wait` |

### (5) 本次修掉的两个真缺陷（都在仪器侧）

1. **`[lane_grid]` 只挂在 `atexit` 上 ⇒ 强制退出时整个读数丢失**。gNB 的 `cleanup_signal_handler`
   先 `p0_dump_reports("forced exit")`，紧接着 `signal_handling.cpp` 就 `raise(SIGKILL)`——`atexit` 根本不跑。
   （`[ul_rx_pool]`/`[tx_slack]` 都额外注册进了 p0 dump，所以它们活着。）已同样注册；
   发现方式：loopback 里其它报告全在、唯独 `[lane_grid]` 一行都没有。
2. **锚信号从 lane 到达换成电台前沿**：观测点移到 `tx_slack_note_receive` 旁边（那里**本来就在守卫之外**），
   用 `(frontier/11520) % 20480` 得到该前沿所属的 slot，**每 slot 只发布一次**（接收是每符号一块，十四个块同属一个 slot）。
   离线段实测：10 秒 loopback **`grid armed from 6856 hop(s)`、`re-armed 0`**——
   而 lane 到达做锚时 p225 重锚 108 次、p224 **177 374** 次。**信号选对了，滤波器就不再需要跟它较劲。**

### 11.19 第 1 步已落地（2026-10-03 深夜）：**电台绝对时间成为一条可读的读数**

按 §11.18 的顺序，第 1 步（驱动侧时间基）完成：

| 改动 | 内容 |
|---|---|
| **接口** | `baseband_gateway_receiver::metadata` 增加 **`absolute_ns`**：电台报告的、该块**首样本**的绝对时间（ns，GPSDO 下即 UTC）；电台不报则为 **-1**，且**没有任何既有消费者读它**（纯加法） |

### 11.20 第 1b 步已落地（2026-10-03 深夜）：**网格变成"时钟"——偏移锚定，不走动**

前两版规则都把锚点的**偏移**朝到达"走"（先 1/64、后 1/1024）。两条真腿证明了那买到的是什么：
**走偏移 = 吸收投递延迟**。而投递延迟正是（a）报告要量的量、（b）线程 `lead` 必须覆盖的量——
**网格一旦吸收了它，就按构造报"lead 够用"**：p225 报 0.65% late，而它的提交其实落后 2 ms，那 2 ms 因为被网格跟走了而**不可见**。

现在的规则：

| 量 | 规则 | 为什么 |
|---|---|---|
| **偏移** | 在第一个前哨上**锚定一次，之后永不被任何到达移动**（晚到、早到都不行）| 它是 `late` 与 lag 读数之所以成立的前提。新反向臂断言这一点，**并包含"2000 个一致晚到的到达也不许移动它"**——而且这条臂是旧臂（"晚到必须把网格拉过去"）的**反转**：旧测试断言的性质，就是这条腿找出来的 bug |
| **速率** | 由电台绝对时间估计（基线 ≥60 s，因为两端各带自己的 lag，100 µs/60 s = 1.7 ppm），限幅 ±200 ppm（超出就不是晶振对，是坏时基），**只作用于外推** | 这是"映射一次 + 周期纠偏"里唯一该动的东西：它是**两个时钟**的性质，不是传输的性质 |
| **重锚带** | **1 秒**（不再是 8 slot）| 它不再抓"延迟"（延迟是毫秒级，必须保持可见），只抓**时基被搬动**（流重启）。旧的 8-slot 带会在 4 ms 的延迟上重锚——正是它绝不能吞掉的那个东西 |

**离线段上这个改动就看得见**：loopback 现在报的 lag 不再被走动吃掉——
**`p50=−32 p95=−32 max=30 min=−43 µs`**；那个 **−32 µs 的系统性偏移正是 `lead` 要覆盖的量**，也是旧规则藏起来的量。

顺带修正的分层问题：**P0 注册从 `utils/macos_compat` 移出**（util 不该依赖 PHY 的报告注册表——compat 单测在 `ocudu::register_p0_report` 上链接失败时暴露的），改到 `lower_phy_baseband_processor`——网格的喂入点，也是"为什么需要它"这条理由该待的地方。

**至此第 1 步（电台绝对时间 + 时钟化网格 + 投递延迟可读）完成。**
下一步是第 2 步：**弹性线程**（`lead` 与 `max_wait` 之间的带、提交或跳过、独占 `pusch_lane` 线程 + TC 申报），
其中 `lead` 现在有实测来源（`[lane_grid] FRONTIER delivery lag` 的 p99/max），不再是拍的。

### 11.21 第 2 步已落地（2026-10-04 凌晨）：**弹性线程**（`paced_task_executor` + 独占 `pusch_lane`）

按用户的弹性带设计实现，**数据流一字未动**（GPU 派发顺序、FAPI 交付、谁调用谁都照旧），
变的只是**这条线程什么时候跑它**：

```
wake_at = grid_tick + lead
   在 [wake_at, wake_at + max_wait] 里轮询任务
      有（或期间到达）→ 立刻跑；提交就落在这条带里的某处
   带走完仍没有 → **跳过这个 tick 并计数**
```

★ **与 p224/p225 的区别就是"跳过"这两个字**：那一版**无限等**，于是继承了到达的时刻、节拍跟着数据走
（精度 3 µs 却仍落后 2 ms）。这一版**丢掉这个 tick、保住节拍**——所以**跳过率是 `max_wait` 的产物**，
而决定 `max_wait` 的是应用层，不是任何 PHY 阈值。

| 组成 | 内容 |
|---|---|
| `paced_task_executor` | 自己的线程 + 自己的队列；循环向**同一个网格**要下一个 tick（`lane_grid_next_tick_ns`，与 lane 钳位共用锚点与速率修正 ⇒ 一条腿的两个读数描述同一个时钟）|
| 参数 | **period / lead / band 全是构造参数**，不 hardcode |
| 接线 | `du_low_executor_mapper` 里当 `OCUDU_UL_PACED_LANE=<period µs>` 时把它设为 `phy_config.pusch_executor`；lead/band 取 `OCUDU_UL_PACED_LEAD_US` / `_WAIT_US`；mapper 持有线程，并把**同一个 period**交给网格（两者不可能描述不同时钟）|
| **申报** | **零新接线**：现成的按线程名机制直接生效，离线端到端回读——`[sched_tc] thread=pusch_lane applied period=500us computation=300us constraint=400us duty=60%`、`[sched] … tc=500/300/400us(duty=60%)` |
| 线程档位意图 | 与池 worker 相同的 realtime intent，这样"开 pacing/关约束"的对照腿才可比（否则会同时量到档位差异）|

**离线端到端读数**：loopback 13 秒 **26281 ticks = 2021/s**，即**每个 500 µs slot 恰好一个 tick** ✓；
**skipped = 100%**——没有 UE 流量、永远没有 PUSCH 任务到达。这既是机制照设计工作，也是"空 tick 的代价"的第一个读数。

**测试抓到的两个真缺陷**：
1. **停机协议是坏的**：关 pacing 时循环停在 `pop_blocking` 里，`running=false` **中断不了它** ⇒ 析构的 join 永远等不到
   （测试挂了十分钟、且因为被 kill 连 gtest 横幅都丢了）。现在置标志后再推一个空任务去唤醒它；
   **后面的队列任务故意不排空**——一条腿的停止不该去跑它被要求放弃的积压。
2. `tasks` 计数声明了却从未自增 ⇒ 一个永远读 0 的计数器就是陷阱；补上，并把断言从 0 改成 1。

| ping avg / **min** | 37.105 / 15.737 ms | 33.479 / **15.644 ms**（**min 未升** ✅）|

#### 同时抓到的两个真缺陷（都在仪器侧，"腿自己先说了话"）

1. ★ **外推偏了整整一个超帧**：锚点距离按 `(slot − anchor) % 20480` 算，而 slot 计数器每超帧（30 kHz 下 10.24 s）回绕一次
   ⇒ **每条腿过了头 10.24 秒之后**，外推整整差一个超帧 ⇒ 两腿 `late` 都接近 **100%**（323176/323176 与 234285/234285）、
   钳位全程失灵，投递延迟的 `max = 10 240 070 µs` **恰好是一个超帧**。
   现在距离改为**累加**（`lane_grid_unwrap_distance`，取环上较短方向），因为有两个提问者：接收路径向前推进并**推进累加器**，
   而 lane 可能问一个**已经过去的 slot**——把它读成"差一点一整个超帧"会让钳位等 10.24 s。新增测试走完一个超帧并断言距离继续增长。
2. **`[paced_exec]` 只注册了 p0 dump，而真电台腿是优雅停机**（不跑 p0 dump）⇒ 执行器的账目从不打印；
   而 `[lane_grid]` 恰好相反（只挂 atexit，强制退出时丢）。**两个读数现在两条退出路径都注册**：
   **只挂一条路径的读数，一定会在需要它的那一刻缺席。**

离线段验证：loopback 的投递延迟从 `max=10 240 070 µs` 变成 **`p50 −32 p95 −32 max 0 min −52 µs`**。

### 11.23 ★★★ p228–p231 扫描：**曲线的膝盖是结构决定的**（band 必须 < period），而扫描里还混着一个混淆项

|---|---|---|---|---|---|---|---|

| p227 | 300 µs | 1 | 60 169 | 75.749 ms | 7.444 ms | （未记）| 全过 |
| p231 | 500 µs | 1 | 103 084 | （未记）| （未记）| 3.04 Mbit/s | 全过 |
| p228 | 1 ms | 1 | 132 059 | **53.428 ms** | 7.049 ms | 3.28 Mbit/s | 全过 |
| p229 | 2 ms | 1 | 135 279 | 257.8 ms | 17.3 ms | 2.58 Mbit/s | 全过 |
| p230 | 4 ms | 1 | **137 241** | 173.7 ms | 11.3 ms | 2.04 Mbit/s | 全过 |

八条腿的 `[phy_pipeline] contract` 全部 MET，`gaps=0`、`rx_overflows=0`、`AT/BELOW 0` 率都在登记线内
⇒ **这一轮没有任何一条腿是被红线否掉的**，曲线本身就是结论。

#### (1) ★★★ 结构性规则：**band 必须小于 period**，否则 tick 结构根本不存在

loopback 直接量到了（`OCUDU_UL_PACED_WAIT_US=4000`，period=500 µs）：

| | 4 ms band（无夹紧）| 夹紧后 |
|---|---|---|
| tick 速率 | **257 次/秒** | 2 线程 83251 ticks / 21 s ⇒ **1982 次/秒/线程** |
| 应有的速率 | 2000 次/秒 | 2000 次/秒 |

原因是机制的、不是调参的：**一次"等待"只要长过一个 slot，它就跨掉了后面几个 tick**。而且 `band = period`
就已经退化——等待恰好在下一个 tick 到期，循环 re-sync 到"现在"这个 tick，于是变成"以 period 为步长的无限等待"，
也就是本设计要摆脱的那种行为。⇒ **band 的合法区间是 `band + drain < period`**，
30 kHz 下 period=500 µs，而 lane 的 drain 实测约 100 µs。

⇒ 已把这条规则写进代码：`paced_task_executor` 的 band **夹紧到 period/2**（留一半给等待唤醒出来的那批工作），
**夹紧会在 banner 和报告里说出来**（`band=... (CLAMPED below the period...)`），并且它是一条**跨平台单测**
（`a_band_longer_than_the_period_is_capped_to_it`，Linux 也跑）。

**⇒ 这条规则同时解释了整条曲线**：500 µs/1 ms 两点还在边界附近，2 ms/4 ms 已经落到退化区——
它们的"吞吐更差、ping 更差"不是 band 这个参数的性质，而是**节拍结构消失**的后果。

#### (2) ★★ 混淆项：单线程 ≠ 池的 2 并发，所以 p226 的 6.74 Mbit/s 不是可比数

`[ul_lane_exec]` 说得明白：池的 `max_pusch_and_srs_concurrency = 2`，**一次跑 2 个 hop**；而 paced 臂是
**1 条线程**。hop 的链里大部分是**等 GPU**（wall 时间远超 CPU 时间），所以 1 条线程根本撑不起 2 并发能撑的
slot 率——**这是线程数的性质，不是节拍的性质**，而扫描把这二者混在了一起。

⇒ 已加两个东西：
1. `OCUDU_UL_PACED_THREADS=<n>`：N 条线程**共用同一个网格**（各算各的 tick，网格是同一个），
   单测 `the_threads_run_at_the_same_time_on_one_grid` 用"两个任务必须同时到达 rendezvous 才能完成"把它证明掉；
2. `OCUDU_UL_LANE_CONCURRENCY=<n>`：**串行对照**——把池也压成 1 并发（`<=1` 即 STRAND），
   于是两条臂只剩"工作什么时候跑"这一个差别。loopback 已验：派生值 2 被覆盖成 1，banner 打出 STRAND。

**另一条已经能下的结论**：p230 处理的 hop 数最多（137 241）而吞吐最低（2.04 Mbit/s），p231 最少（103 084）
而吞吐更高（3.04）⇒ **多出来的 hop 不是有用功，是重传**（commit 被推迟一个 slot，吃掉 HARQ 预算）。
⇒ "跳过 ⇒ 丢 slot ⇒ 吞吐腰斩"这个模型是错的，正确的是"**推迟 ⇒ 丢 HARQ 余量 ⇒ 重传**"。

#### (3) 一条真缺陷（仪器侧）：p0 报告表**满了就静默丢弃**

loopback 里 `[paced_exec]` 的报告行消失，一度被读成"节拍没生效"。真因是 `register_p0_report` 的定长表
写满后**默默丢掉**后面的注册。现在：溢出会**大声报**（并说明该报告会在每次 dump/退出报告里缺席）、容量留出余量、
线程上线打一行（"没有线程/没有节拍/退出时对象已不在"这三种失败以前长得一模一样）、`ticks=0` 也打印而不是沉默。

> 在会话噪声之内。本节的读数表仍然有效，结论以 §11.25 为准。

#### (1) ★★★ 两条结论已经稳了

1. **band 在合法区间内（0 / 125 / 250 µs）对应用层几乎无影响**：三条 paced 腿是 **2.50 / 2.74 / 2.79 Mbit/s**（p233/p234/p235），
   而 ping max 65.6–176.1 ms 的差别更像噪声。⇒ §11.23 的"膝盖是结构决定的"得到独立确认：**曲线的差别不在 band 上**。
   同时也说明 **"跳过率"确实不该当判据**——三条腿的 band 差一倍，读数没系统性差别。
2. **paced 臂的吞吐代价不是"线程数"造成的**：p233（2 线程）2.50 与 p234（1 线程）2.74 一样差，
   而池在 1 并发下能跑 **15.9**。⇒ 上一轮怀疑的"单线程 vs 2 并发"混淆项被排除，**代价在"整条 hop 被搬到网格线程上"这件事本身**。

#### (2) 代价的形状：**grant 一样多，数据少 6 倍**（不是解码失败）

同一配置下 UL 每个 slot 都被调度（~600 grant/s，四条腿一致），但：

| | grant | CRC-OK | 填充率 |
|---|---|---|---|
| p232 | 357 702 | 268 947 | **75%** |
| p233 | 363 016 | 109 705 | **30%** |

而 TCP 侧 **Retr 反而更多**（2774 vs 1633）、ping 的 **avg 完全一样**（34.4 ms）、只有尾部更好。
⇒ 这不是"PHY 算错了/丢包"（CRC-OK 的 hop 里一条都没失败），而是**上行链路被传输层自己压下去了**：
相当一部分被调度的 slot 里 UE 没有数据可发。**"节拍 ⇒ 端到端晚一点 ⇒ TCP 窗口/BSR 收 ⇒ UE 填不满 grant"** 这条链，
与本线一直看到的"整条 hop 的 wall 时间远大于 CPU 时间"（`defer_wait` 中位 **~700 µs**，四条腿都一样，含池对照）
是同一件事的两面：**hop 里的等待是既有的，节拍只是把它推过了某个期限**。

#### (3) ★ 一条真缺陷（本线自己造的）：退出报告锁了已经析构的对象 ⇒ `Abort trap: 6`

p233/p234/p235 三条腿在退出时 abort：`libc++abi: terminating due to uncaught exception of type
std::__1::system_error: mutex lock failed: Invalid argument`，而对照腿 p232 干净。原因是**上一轮我自己加的一行**：
`std::atexit(paced_lane_report)` 绑在 mapper 持有的 `static paced_task_executor*` 上，而 mapper 是 `main` 的局部量
⇒ **执行器先析构，atexit 处理器后跑** ⇒ 处理器锁了已释放内存里的 mutex ⇒ 异常逃逸 ⇒ terminate。
代价不只是崩：**它把退出报告打断在半路**，所以三条 paced 腿**连 `[ul_pipeline]` 的 contract 行和 `[paced_exec]` 的账目都没有**
——报告要保护的读数，被报告自己弄丢了。而 p232 之所以干净，是因为那一臂 `paced_lane == nullptr`，报告直接返回。

**loopback 验不出这条**：刚释放、还没被复用的内存里 mutex 依然"能用"，于是那次"验过了"读的是**已释放的字节**——
它给出的 `ticks=83251` 是一次数值上正确、来源上非法的读取。**只有真电台腿能暴露它。**

修法（提交 `95c101172a`）：执行器内部维护**活实例登记表**（登记表本身是永不析构的堆对象，因为它的读者跑在静态量正在被拆掉的时刻），
构造时入表、析构时出表；**析构函数在 join 完线程后自己打一次账**（那是对象确定还活着的最后一刻，也正是真电台腿到达它的时刻）；
两条退出路径都注册 `paced_task_executor::report_all_live`，它**只可能碰到活的对象，没有对象时什么都不打**。
两条新测试：`a_destroyed_executor_is_out_of_the_exit_report_registry`（两侧都断言，"没崩"正是当初放它过去的那种证据）、
`the_destructor_prints_the_reading_a_graceful_exit_would_have_lost`（**真的捕获 stderr**，因为"什么都不打"的版本同样不会崩）。

loopback 复核：`[paced_exec]` 恰好打一次（来自析构），ticks=72438 / 2 线程 / ~18 s = 每 slot 一次，无 abort。

#### (4) 下一步（p236–p238）：把"网格钳位"和"节拍线程"分开，并确认串行效应

paced 臂与 p232 差了**两个**变量：整条 hop 搬上网格线程，以及 `OCUDU_UL_LANE_GRID=1`

#### (1) ★★★ 决定性读数：paced 线程**每秒只 tick 1238 次**，不是 2000

```
[paced_exec] pusch_lane: ticks=2111711 ran=343542 (16.27%) skipped=1768169 (83.73%) tasks=363973
             first task of a tick ran 18.6us after its grid instant (max 260us)
[paced_exec] pusch_lane: period=500us lead=0us band=250us threads=2
```

同腿的 `[lane_grid]` 给出基线时长 **853.1 s** 与 frontier 条数 **1 706 104**（= 853 s × 2000/s，确认 slot 率就是 2000/s）。
于是 **每线程 tick = 2 111 711 / 2 / 853 = 1238 次/秒**，而网格定义的是 **2000 次/秒** ⇒
**38% 的 tick 被 re-sync 悄悄跳过了**。原因不是"抓不到数据"（band 精度是好的：tick 后 **18.6 µs** 就跑起第一个任务，max 260 µs），
而是**一次 hop 任务把线程占住约 1.5 ms ≈ 3 个 slot**（`[ul_pipeline]` 均值 1539 µs），线程在下一个 tick 到来时还没回到循环里。

⇒ **机制没有兑现自己的前提**："每个 slot 醒一次"在"工作单元横跨 3 个 slot"时不可能成立。
而这正是用户设计里那句**"它的工作只是 Metal encode/commit"**在承重：实测一次 encode+commit 只要 **14–47 µs**，
放进 500 µs 的 slot 里有 10 倍余量，**只有那个形态才可能真的一个 slot 一次 tick**。
本轮的数据把这条设计约束从"推测"变成了"量出来的"。

#### (2) 归属：代价在节拍线程，不在网格钳位

p236 单独打开 `OCUDU_UL_LANE_GRID=1`（池、无 paced）后，钳位自己的账目是：

```
[lane_grid] grid armed from 1509466 hop(s), re-armed 0 time(s); clamped=24 (mean wait 5.2us, max 17us;
            overshoot mean 0.4us, max 6us); late=321107; unarmed=0
```

**36 万个 hop 里只有 24 个真的等过（平均 5.2 µs），而 `late` = 99.99%**——即 lane 开始时它那个 slot 的网格时刻**早就过去了**
（§11.16 的"lead 被当延迟付"在这一版参数下不再发生）。⇒ **钳位在这套配置里不是一个延迟机制**，
p238 的 1.44 Mbit/s 不能归给它；归给它的是**节拍线程本身**（p238 填充率 29% vs 池的 75–95%）。

#### (4) ★★ 方法学结论：跨会话的单腿比较**已经不是证据**

同一条 paced 臂（p233 与 p238，只差一个 `b`）：
**2.50 → 1.44 Mbit/s**，ping max **78.1 → 176.96**；池臂的 ping max 在 84–430 之间摆动。
⇒ 从这个规模起，**腿间方差大于臂间差异**。要判断任何"哪个臂更好"，必须

仍然**稳健**的三件事（每条都在所有会话里同向）：

#### (4) 这一轮真正学到的方法学结论

1. **`max` 这条轴在本实验条件下是泊松受限的**：每腿 >1 ms 的 `slip` 只有 3–27 个事件，`sqrt(N)` 就是 ±20–40%；
   而分布主体（p95/p99，百万样本）**已经证明不受这两个旋钮影响**，所以"再加更细的阈值计数"没有意义——要动 `max` 就必须**攒够稀有事件**。
2. 唯一还站着的**方向性**信号（弱，p≈0.125）：网格开时 `slip>1ms` 计数 **3/3 对都更低**（27→15、20→9、13→12），
   `recv>1ms` 也是 3/3 更低（20→8、14→3、6→7）。这与用户的 `max` 目标同向，但 180 s × 3 对分不开。
3. 那条"~100 ms 的 `recv` max"**不是运行时 stall**：它等于被 `[ul_rx_wait] startup=` 单独排除的**流启动样本**
   （七条腿 100.2–101.0 ms，臂间无变化），一度看着像元凶。

### 11.29 ★★★ 13 条腿的 watchdog 汇总：**91% 的 stall 是"等 CPU 之外的东西"**，`cpu_stolen = 0`、`work_slow = 0`

把 p239–p251 十三条腿的 `[ul_watchdog] classified stalls` 加在一起（watchdog 是 1 ms 唤醒器，自己分类）：

| 类别 | 次数 | 占比 | 含义 |
|---|---|---|---|
| `suspended` | **1 956** | 59% | 线程/进程被挂起（阻塞在内核/驱动里，调度器给不了 CPU）|
| `driver_block` | **1 076** | 32% | 阻塞在驱动调用里 |
| `saturated` | 312 | 9% | 机器真的饱和（唯一与"CPU 被抢"有关的一类）|
| **`cpu_stolen`** | **0** | **0%** | **没有任何一次是被别的进程抢走 CPU** |
| **`work_slow`** | **0** | **0%** | **没有任何一次是自己活儿干多了** |

> **更正（2026-10-04，同日，读完 watchdog 源码与它的 `worst` 记录后）**：上面这张表的 `driver_block` 一栏**不可用作证据**。
> 两个原因，都在仪器里：
> 1. `first_blocked=` 打出来的名字是**扫描顺序**的产物——`io_broker_epoll` 这类线程**本来就该**停在 WAITING，
>    而 `blocked>0` 只要求"存在任何一条停在 WAITING 的线程"⇒ 在任何一个健康进程里它几乎恒为真 ⇒ `DRIVER_BLOCK` 是**兜底类**，不是诊断。
> 2. `sample(true, ...)`（waker 自己迟到那条路径）在 `classify()` 里**短路**：waker 一迟到就直接判 SUSPENDED/SATURATED，
>    **根本不看其它线程** ⇒ 大的 stall 全都落进"waker 迟到"，而 waker 本身是一条**没有声明**的普通线程
>    （微基准：普通线程唤醒 p50 103 µs、过载下 max 2567 µs）⇒ SUSPENDED 里混着"waker 自己没被调度"。
>
> 因此下表只能读作"**分类器的输出分布**"，不能读作"stall 的成因分布"。真正还干净的两条是
> **`cpu_stolen=0`（没有一条 watched 之外的解释）与 `work_slow=0`**，以及**`saturated` 窗口里 `sys_busy=100%`** 那几次。
> "stall 到底卡在哪个等待点"必须**重新做仪器**（见 §11.30）。下面这段结论中依赖 `driver_block` 的部分**作废**。

⇒ （原文，依赖 `driver_block` 的部分已作废）91% 的 stall 是"在等 CPU 调度之外的东西"（挂起 + 驱动阻塞）。这条读数把整条线的失败解释干净了：
QoS 档、`SCHED_FIFO`、Mach time constraint、affinity、节拍线程、网格钳位、commit 闸门——**没有一个能作用于"驱动阻塞"或"进程被挂起"**。
它们是 `max` 的来源，而它们不在 CPU 调度器的管辖范围内。

#### (1) 一个必须记下的方法学事实：**两轮之间的环境本身变了 7–27 倍**

同一批臂，`suspended` 事件率：

| 轮次 | 腿长 | 代表腿的 suspended / 秒 |
|---|---|---|
| p239–p245（180 s）| 180 s | 0.017 – 0.072 /s（p244 只有 3 次）|
| p246–p251（600 s）| 600 s | 0.065 – **1.94** /s（p250 有 1164 次）|

⇒ 两轮之间**同一臂的挂起事件率差 7–27 倍**。这正是 §11.27 与 §11.28 **方向相反**的原因：
不是臂变了，是**环境变了**。⇒ 本线"跨轮次比较不可用"这条纪律，现在有了一个量化的理由，
而且它也说明：**单腿 ping max 的比较（甚至三对交替）在这种漂移下都可能给出反向结论。**

#### (2) 结论（写死）

1. **`max` 不是这些线程的优先级/调度策略决定的**：13 条腿里 0 次 CPU 被抢、0 次工作过载，91% 是挂起/驱动阻塞。
   ⇒ "调整 PHY 处理线程的运行时优先级、调度策略，使 max 尽可能小"这个命题，**在本平台上被证否**（不是没调好）。
2. 网格钳位：预登记判据**没有收益**（600 s 轮两对都更差、合计 1.9×，但不显著；180 s 轮方向相反）⇒ **不采纳，保持默认关**。
3. 分布主体（百万级样本的 p95/p99）在所有臂之间**逐微秒相同** ⇒ 这些旋钮既不改善也不损害常规时延。
4. 唯一被验证有效的杠杆仍是**环境**（安静机器：`ce` max 11185 → 1120 µs）；若要继续压 `max`，
   对象是**无线电/驱动路径**（USB 传输，p223 的 `uhd::usb_error` 是这条路径确实在出问题的旁证），不是线程调度。

### 11.30 ★★★ p254：**尾部第一次被点名**——`exec.park`（线程在等活）与 `metal.burst_wait`（等 GPU 完成），不是驱动阻塞、也不是被抢 CPU

[ul_watchdog]   late= 8700.0us trigger=t2f  reporter=exec.park        -> PHY_SERIES

#### (1) 读数说明了什么

1. **PHY 自己的慢跨度**（`eqd` 均衡+解调 22 次、`ce` 信道估计 29 次、`t2f` 2 次，13.6 分钟内共 53 次）被归因到两个等待点：
   - **`exec.park`** —— 上报那条线程**最近一次等待是"在执行器队列里等活"**，即慢跨度里包含**它在空等的部分** ⇒ 这是**排队**，不是被谁挡住；
   - **`metal.burst_wait`** —— 另一些是**等 GPU 完成**（`defer_wait` 那一项）。
2. **没有一次归因到 `radio.rx`** ⇒ 这一轮里**没有 USB/电台接收阻塞**成为慢跨度的原因（上一轮"91% 是挂起/驱动阻塞"的猜测至此被完全取代）。
3. `waker_late=390 of 413` 且同批记录里 `watched[running=9 starved=0 blocked=0]` ⇒ 那些"stall"是**观察者（无声明的 1 ms 线程）自己**迟到，PHY 线程在跑。

#### (2) 为什么这条读数把整条线的失败解释干净了

**一条"在等活"的线程，任何优先级、任何调度策略、任何声明都帮不了它**——它没有可运行的对象。
这正好解释了 §11.29 那张表：QoS、`SCHED_FIFO`、Mach time constraint（P4 七对）、affinity、节拍线程、网格钳位、commit 闸门，
**没有一个能移动 `max`**，而 `cpu_stolen=0`、`work_slow=0` 在十几条腿里反复出现。

⇒ **`max` 的杠杆是结构性的**：让**阶段的输入更早到**（D1 的 hand-over / `grid_ready` / 融合 lane 的排序那一条工作线），
而不是给处理线程调优先级。这是一条**可执行的结论**，也是本任务命题（"调整 PHY 线程优先级/调度策略使 max 最小"）的最终答案：
**在该平台上，答案是否定的；真正的对象是流水线的排队结构。**

#### (5) 量级缺口与补上的那一半：`rx_loop` / `rx_slip`

上面被点名的跨度只有 **1–9 ms**，而同一批腿的 **ping max 是 70–190 ms**——差一个数量级。

已补（提交 `1cd6f63fe3`、`37f6ab9192`）：
1. `rx_loop` / `rx_slip` 以 1 ms 门槛**上报为系列**，进入同一张站点表；
2. 接收线程两次 receive 之间的第一件事——**池取缓冲**（`pop_rx_buffer_or_reserve`）加了 `pool.take` scope；
3. ★ **归因窗口改为显式传入**：旧写法用"现在减去数值"当窗口，而 `rx_loop` 的窗口起点**正是**上一次 `radio.rx` 的结束点
   ⇒ 会把接收调用误判成每一次 loop 空档的元凶。现在只认**严格落在窗口内**的等待，phase 系列也改用它自己已有的 `begin_ns/end_ns`。

下一条腿的三种可能结果（预先写下，避免事后找解释）：
- `reporter=pool.take` ⇒ **环被抽干**（池/后端跟不上），杠杆在池与后端吞吐；
- `reporter=-` ⇒ 窗口内**没有任何等待** ⇒ 接收线程是被**调度走了**，那就回到 CPU 一侧；
- `reporter=` 别的站点 ⇒ 直接指到那条路径。

### 11.32 ★★★ 收官读数：**把 ping 的 RTT 逐段拆开**，PHY 线程调度在其中的贡献是**微秒级**

做法不需要新腿：`--log.all_level info` 的日志里每个 SDU 都带微秒级墙钟，ping 的包按大小就能唯一识别

#### (4) ★ 对"两臂 load 为何不等"的一个机制性解释（下一轮要验的假设）

**Mach time constraint 不只是预留，也是节流**：`computation/period` 是硬预算（臂上池线程 26%、RX 线程 20%）。
于是：

* 臂腿**自身的 CPU 需求被压住** ⇒ 机器 `load1` 更低（6.29 vs 12.26）——这个不等**可能正是臂造成的**，不是环境噪声；
* 而需要**突发**的阶段一旦超过预算就被节流 ⇒ 恰好是**变差的那两条**（`ce`、`t2f` 是最"突发"的两段）。

**测出来的**：
1. 把 TC 声明在池线程上时，`ce`（信道估计）阶段的尾部率在**两轮独立加扰**里都升高（1.31× / 1.60×）；
2. 把 `computation` 提高 92%（1300 → 2500 µs）**没有**改善它 ⇒ 不是"预算不够用"；
3. **同一种** TC 声明在**接收线程**上（`period=500 µs`，与 slot 同周期）却让 `rx` 尾部两轮都降 5–7× ⇒ 危害不是"TC 本身"，而是**特定线程/特定形状**。

**仍属假设（数据不足以定论）**：
* 池线程的 TC 周期是 **5000 µs**，而它的工作**每 500 µs 来一次**（每 slot 都要跑 `t2f`/`ce`/`eqd`）⇒ 用一个 5 ms 的周期去预留一个"每 slot 交付一次"的线程，CPU 的**交付时刻**被 5 ms 的形状塑形；
* 声明 TC 会**永久丢掉该线程的 QoS 档**（Darwin 互斥，§10.29 实测）——对一个成本波动 40× 的线程（`ce` 中位 68.9 µs、max 2875 µs），一个周期性预算策略可能不如原来的 QoS 档；
* `preemptible=1` 允许在计算中途被切开。

⇒ 结论句应写成：**"把时间约束声明在池线程上，在两轮加扰里都让 `ce` 的尾部变差 1.3–1.6×，而原因不是预算大小；它在接收线程上却有效。以本任务的判据（一条都不许劣化）衡量，这条臂不成立。"**

### 11.38 ★★★ 澄清：**FFT 一直在 CPU（vDSP）上算**，不在 Metal kernel 里；而它一个开关就能搬到 GPU

用户问"FFT 是 CPU 逐符号算的，还是在 Metal kernel 里"。答案（代码 + 每腿的启动诊断）：

* 后端由 **`expert_phy --pusch_dft_type`** 决定（`lib/ru/sdr/lower_phy/lower_phy_factory.cpp:28`），**不是** `phy_pipeline` 模式；
* 本线飞过的**每一条腿**都是默认值 ⇒ 启动行写着
  `[lower_phy] DFT backend: rx=cpu tx=cpu (expert_phy --pusch_dft_type cpu; CPU implementation: vdsp)`
  ⇒ **14 次/slot 的 FFT 是主机 CPU 工作**（Apple vDSP），TX 侧（IFFT）按构造也是 CPU；
* 这也解释了之前两个"零"读数：`[metal_stats] gpu busy (front_end): commits=0` 与
  `dft radio inputs: 0 transform(s) went through the two submit routes` —— 那两条探针量的是**设备 DFT 路径**，
  为零正说明 FFT 不在设备上 ✓（它们从来不是"没有 FFT"的证据）。

**各段算术的真实位置（本线这些腿）**：

| 段 | 算术在 | 证据 |
|---|---|---|
| `t2f`（FFT/DFT）| **CPU（vDSP）**，14 次/slot | 启动诊断行 + `front_end busy=0` |
| `ce`（信道估计）| **设备** | `busy split: ch_wt=38.8us/lane` |
| `eqd`（均衡+解映射）| **设备**（融合核）| `busy split: merged_hop=468.5us/lane` |
| `ldpc`（解码）| 本机走 **SW** 工厂（HW 工厂为 nullptr）；解码器内部有 Metal 钩子，未确认本腿是否走它 | `upper_phy_factories.cpp:891` vs `:881`；`[ul_ldpc_decode]` 59–90 µs |

⇒ §11.37 的收支表要修一处：`t2f` 的 491.9 µs **不只是"等 slot 到齐"**，里面还有 **14 次主机 FFT** ✓ ——
所以它是**真正的主机 CPU 工作**（也因此确实对 CPU 调度敏感 ✓），并且是 hop"62% 非设备"里的重要一块。

**可用的杠杆（一个开关，无需改代码）**：`ENABLE_METAL_DFT=ON` ⇒ 这个二进制**已经编进了 Metal DFT**，
`--expert_phy.pusch_dft_type=metal` 即可把 **UL 接收侧的 DFT**（OFDM 解调 + PRACH）搬到设备；
代码侧已有配套机制（D1 hand-over：`retain_symbol_input`、零拷贝 wrap 路径、`grid_ready`；本线腿的
`zero-copy wraps: 1301314 hits, 181992 creates, 0 failures` ✓）。
**注意**：搬过去之后 `t2f` 这个 landmark 的**语义会变**（提交/排空 vs 执行完成），所以 A/B 的判据要用
`ul_pipeline` 与设备 busy 的 `front_end`（后者应从 0 变成非 0，作为"开关真的生效"的正向对照），**不能直接比 `t2f`**。

#### §11.39 补：队列语义 + 优先级在 Darwin 上的"坍缩"

**队列容量（`create_prio_worker(name, exec_name, queue_size, policy, sleep_time, mask, prio)` 的第三个参数）**

| 线程 | 队列容量 | 语义 |
|---|---|---|
| `lower_phy_tx#0` / `lower_phy_ul#0` | **128** | 最多 128 个待执行任务；满了之后 `defer()/execute()` **返回 false**，由调用方处理（丢弃/报错）|
| `lower_phy_rx#0` | **1** | 任何时刻最多 1 个排队任务 ⇒ **严格一次一个**（与"干完重新投递自己"的循环一致；第二条并发投递会被拒）|

`sleep_time = 10 µs` = **队列为空时的轮询间隔**。

**`prio max()` / `max()−1` / `max()−2` 在这两个平台上是两回事**

| | Linux / Ubuntu | macOS（本线所有腿）|
|---|---|---|
| 定义 | `max() = sched_get_priority_max(SCHED_FIFO) − 1 = 98`（故意低 1 以免与 OS 关键任务相争）| 同一定义（代码共用）|
| 生效方式 | `pthread_setschedparam(t, SCHED_FIFO, {98/97/96})` ⇒ **相对次序 tx(98) > ul(97) > rx(96) 真实存在** | **不生效** ✗：`darwin_qos_class_for_prio()` 把"任何非 `no_realtime()` 的值"一律映射为 `QOS_CLASS_USER_INTERACTIVE`（`lib/support/scheduling/darwin_thread_scheduling.cpp:18`），由 `apply_worker_thread_scheduling()` **无条件**调用 |
| 结果 | 三条线程三种优先级 | **三条 + 主池（`max()−2`）全部同档**，`−1/−2` 是死数字 |

腿上 `[sched]` 行印证：每个 PHY 线程都是 `req=USER_INTERACTIVE eff=USER_INTERACTIVE posix=OTHER/31`（同档、无显式策略）。

**⇒ 由此得到的平台结论**：macOS 上"调优先级/调度策略"真正可用的手段**只有两个**——
① **逐线程的 Mach time constraint**（必须由 `OCUDU_SCHED_TIME_CONSTRAINT` 逐线程点名，且声明后永久失去 QoS 档）；
② **全局 FIFO**（已证否：丢 7 M 样本、上行 −25%）。
**QoS 那一层在这台机器上不构成杠杆**（所有 PHY 线程本来同档）——这正是"QoS 档 ≈ 基线"那条读数迟迟无法解释的原因。

#### §11.39 补二：这套优先级机制**是 upstream 的**，Darwin 的"坍缩"**是本 port 的**

| 组件 | 出处 | 证据 |
|---|---|---|
| `os_thread_realtime_priority`（`max()` = `sched_get_priority_max(SCHED_FIFO)−1`、`native_sched_policy()`、`pthread_setschedparam(SCHED_FIFO, …)`）| **upstream ocudu**（当时路径还是 `include/srsgnb/…`）| 提交 `c2777df160` **2022-04-13 Francisco Paisana** "support: use custom types to represent cpu affinity masks and scheduling priorities"；更早的 `427eb17db7`（2022-04-12，同作者）"redesign threading library to leverage std::thread" |
| `lib/support/scheduling/darwin_thread_scheduling.cpp`（`darwin_qos_class_for_prio`、`set_this_thread_qos_class`、Mach TC）| **本 port 新增** | `--diff-filter=A` ⇒ 加入于 **2026-08-16 Jiacheng Wang** |
| `utils/macos_compat/macos_compat.cpp`（`apply_worker_thread_scheduling` 等平台分支）| **本 port 新增** | 加入于 **2026-09-01 Jiacheng Wang** |

⇒ **upstream 给的是"按数值排出的相对次序"（98/97/96，以及主池的 96），而本 port 只保留了它最高的一位**：
`darwin_thread_scheduling.h` 的注释写明理由是"On Darwin, SCHED_FIFO cannot be set without privileges; the QoS class is the closest equivalent"。
**这条理由并不完全准确**：后来的 FIFO 臂**确实**把 SCHED_FIFO 设上了（p183 的 `[sched]` 行 `posix=FIFO/44/45/46`），只是那条臂**有害**（丢 7 M 样本、上行 −25%）⇒ 真正的原因是"设得上但代价不可接受"，而不是"设不上"。

⇒ 这也解释了本线一条老读数：**"QoS 档 ≈ 基线"** —— 因为在这台机器上**所有 PHY 线程本来就在同一个档**，从来没有相对 QoS 可言；
macOS 上唯一能按线程制造差别的是 **Mach time constraint**（逐线程点名，代价是永久丢 QoS 档），其次是**全局 FIFO**（已证否）。

#### §11.39 补三：`relative_priority` —— **同一 QoS 档内部还能分优先级**，而本 port 一直传 0

本机 SDK 的权威定义（`…/MacOSX.sdk/usr/include/pthread/qos.h` 的 API 文档 + `sys/qos.h:153`）：

> "A relative priority **within the QOS class**. This value is a negative offset from the maximum supported scheduler priority
> for the given class. EINVAL will be returned if the value is greater than zero or less than `QOS_MIN_RELATIVE_PRIORITY`."
> `#define QOS_MIN_RELATIVE_PRIORITY (-15)`

⇒ 合法区间 **`[-15, 0]`，即每档内部最多 16 级** ✓；语义是"从该档的**最高**调度优先级往下偏移"，
所以它只能把线程在**档内调低**、不能调高 ✗（要让 X 优先于 Y，得把 Y 调低 ✓）；
层次是**档为大、偏移为小**（class 定 band，offset 在 band 内排序）✓。

**本 port 从未用过它**：`set_this_thread_qos_class()` 里是 `pthread_set_qos_class_self_np(qos, 0)`、
属性路径是 `pthread_attr_set_qos_class_np(&attr, qos, 0)` —— **两处都是 0** ✗ ⇒ 这是一条**没碰过的杠杆**。

**为什么它对本案有意义**：它能在**不丢掉 P 核 QoS 档**的前提下，给实时 PHY 线程之间一个**相对次序** ✓ ——
而这正是 Mach time constraint 只能以"**永久放弃 QoS 档**"为代价换来的东西（Darwin 互斥，§10.29 实测）。
它是"相对优先级"里**代价最小**的候选 ✓。

**先离线验，再飞**（本线一贯纪律）：用现成的微基准骨架，跑两个在 `USER_INTERACTIVE` 内偏移 0 与 −5 的竞争线程，
量唤醒尾延迟；若在微基准里都没有可测差别，就不值得飞腿 ✗。（已有的对照点：把普通线程提到 `USER_INACTIVE`（偏移 0）
在唤醒上**没有任何改善**：103.0 vs 103.0 µs p50 —— 那说的是"档"而不是"档内偏移" ✓。）

### 11.40 ★★★ PHY 线程的 QoS/时间约束架构重规划（用户 2026-10-04 提出的问题）

#### (1) QoS 与 Mach time constraint 是**两种不同性质的东西**

| | **QoS 类**（`pthread_set_qos_class_self_np`）| **Mach time constraint**（`THREAD_TIME_CONSTRAINT_POLICY`）|
|---|---|---|
| 它是什么 | **对系统性能/能耗策略的"分类提示"**（这是什么活）| **一份周期性的预留契约**（每 P 微秒要 C 微秒，C 之内要交）|
| 承诺 | **没有任何时延/CPU 保证** ✗ | 按 `period/computation/constraint` 交付（尽力但有优先级保障）✓ |
| 层次 | 5 档（`USER_INTERACTIVE`…`BACKGROUND`）+ **档内偏移 `[−15,0]`** ✓ | 4 个参数（period/computation/constraint/preemptible）✓ |
| 谁受影响 | 只在**QoS 管理的线程之间**相对排序 ✗ | **对所有线程**（含 QoS 管理的）都排在前面 ✓ |
| 代价 | 几乎为零 ✓ | **永久失去 QoS 档**（Darwin 互斥，§10.29 实测）+ 是一份要被兑现的预留 |
| 设计目的 | 让**任何** App 都能廉价地告诉系统"这段活的紧急程度/该放哪种核/定时器能合并多少" | 给**少数硬实时线程**（音频、驱动、传感器管线）一个能兑现的期限 |

**一句话**：**QoS 是"描述"（让系统的全局能耗/性能策略做决定），time constraint 是"处方"（向系统要一份周期预算）。**
Apple 让两者互斥，正是因为一份周期预留会**扭曲**全局能耗策略——所以系统让你二选一 ✓。

#### (2) QoS 最高档与系统守护进程相争，会怎样？——**赢不了，而且硬赢会把链路打死**

四层证据（都是本线的读数）：

1. **QoS 档只在 QoS 世界内相对排序**：`USER_INTERACTIVE` 不会越过内核/USB/守护进程 ✗；它只是"用户线程里最高的一档"✓。
2. **微基准**：普通线程唤醒 p50 **103.0 µs** → 提到 `USER_INTERACTIVE`(偏移 0) 仍是 **103.0 µs**（p99 反而更差）✗ ⇒ **光靠档，尾延迟不动**。
3. **同一微基准下 Mach time constraint**：2× 过载时唤醒尾 **5358 µs → 9.9 µs** ✓✓ ⇒ 能赢的是**预留**，不是**档**。
4. **硬赢的代价（FIFO 臂，p220/p221）**：`SCHED_FIFO/44–46` 把 PHY 线程抬到内核/USB 之上 ⇒ **丢 7 M 样本、上行 −25%、电台链路被打死** ✗✗ —— 因为**它依赖的内核 IO 被它自己饿死了**。
   另有一条同向的证据：关掉重干扰源（Continuity/BLE/Biome）后 **8–15 ms 那一类停顿消失**，只剩 `launchd`/`runningboardd`/`mDNSResponder` 带来的 **1.7–2.2 ms** ✓——**能赢的是"减少竞争者"，不是"提高自己"**。

⇒ **结论**：与守护进程相争时，`max` 的可动项是"**减少竞争者**"（环境）与"**拿到一份周期预留**"（TC），而**不是**"把 QoS 调到最高" ✗。

#### (3) 重规划：按**工作形状**给每条线程选机制（而不是全都用一个档）

| 线程 | 工作形状 | 今天 | 建议机制 | 状态 |
|---|---|---|---|---|
| `lower_phy_ul#0` | **每 slot 固定**（14 次 FFT）| QoS（与其它实时线程同档）| **TC**：period=500 µs、computation 按 t2f 的固定部分定 | ❓ **从未试过**（p273/p274 待飞）|
| `lower_phy_rx#0` | 每 slot 接收 + 交棒（大部分阻塞）| QoS | TC（已试 500/250/350）| ➖ 载体变化落在噪声底内 ⇒ 不成立 |
| `lower_phy_tx#0` | **有硬空口截止期**的发射交棒 | QoS | **TC**（载体是 `AT/BELOW 0` 率，已登记 ✓）| ❓ 从未试过 |
| `main_pool#0..#4` | **共享、突发**（CE/eqd/解码 + 其它）| QoS | **保持 QoS**（TC 两轮均伤 `ce` ✗）；需要相对次序时用**档内 `relative_priority` 偏移** | TC 已证否 |
| `pusch_lane` / `lane_commit` | 周期（本线新增）| TC 默认关 | 保留能力，默认关 | 机制成立、效果未测出 |
| `radio` / UHD/libusb / SCTP | 驱动内的阻塞 | 不在 `unique_thread` 覆盖范围 | **无法用本机制声明** ✗ | 只能靠环境/驱动 |

**两条待验的、代价最小的候选**（按顺序）：
1. **`lower_phy_ul#0` 的 TC**（p273/p274）——唯一从未被声明过、且形状正确的线程 ✓；
2. **档内 `relative_priority` 偏移**（本 port 一直传 0 ✗）——能在**不丢 QoS 档**的前提下给实时线程一个相对次序，
   但**必须先离线微基准证明它有效**（两线程同在 `USER_INTERACTIVE`、偏移 0 vs −5，量唤醒尾）✓。

### 11.41 ★★★ 架构决定（用户 2026-10-04）：**整条 PHY pipeline 都跑在 Mach time constraint 架构上**（三种模式通用）

#### (1) 用户的论证，以及它对前面失败的重新诊断

> "对 `main_pool#0..#4` 保持 QoS"这个建议本身就说明**现有资源分配对 pool 不够**；而 Mach time constraint 的设计目的
> （"给少数硬实时线程一个能兑现的期限"）**正是 OCUDU PHY pipeline 所需要的** ⇒ 整条 pipeline 都该跑在 TC 架构上，
> 而且与 `phy_pipeline` 的三种模式（cpu / cpu_gpu / gpu）无关。

**实测支持这个重新诊断**：

| | 我们飞过的 pool 臂 | 实测 |
|---|---|---|
| period | **5000 µs**（TDD 周期）| **工作节拍是 500 µs**（每 slot 一次交付）✗ 差 10× |
| computation | 1300 µs (26%) / 2500 µs (50%) | 池线程均值占空 **13%**，但**窗口内突发可达 ~90%**（p99.9 窗口 CPU 8388 µs / 8.39 ms）✗ |

⇒ `ce` 在两轮里变差 1.31× / 1.60×，是**周期与预算都不匹配**的结果，**不是"TC 不适合 pool"** ✗✓。
（P4 的既有证据同向：`computation` 1 ms → 2.5 ms **消除了启动瞬态** ✓ —— 预算按均值给必然伤突发。）

#### (2) 目标架构

**每条 PHY 线程一份预留，period = slot（500 µs @30 kHz），computation 覆盖该线程的"最坏单 slot 突发"**；
线程之间不再靠 QoS 档排序，而是靠各自的预留兑现 ✓。三种模式（cpu / cpu_gpu / gpu）**共用同一套线程形状**，
只是算术落在主机还是设备不同 ⇒ **该架构与卸载模式无关** ✓（这也是它比"按模式调"更根本的地方）。

| 线程 | 工作形状 | period | computation（待定档）| 依据 |
|---|---|---|---|---|
| `lower_phy_ul#0` | 每 slot 14 次 FFT | 500 µs | t2f 的固定部分 + 余量 | §11.40；**从未试过** |
| `lower_phy_tx#0` | 每 slot 发射交棒（硬空口截止期）| 500 µs | `[dl_tx_call]` p99.9 | 载体 `AT/BELOW 0` 已登记 |
| `lower_phy_rx#0` | 每 slot 接收 + 交棒 | 500 µs | 已测（500/250/350）| 保持 |
| `main_pool#0..#4` | 每 slot 的 CE/eqd/解码突发 | **500 µs**（不是 5000）| **覆盖 ~90% 突发的量级**（数百 µs）| 前两轮的修正 |
| `pusch_lane`/`lane_commit` | 周期（本线新增）| 500 µs | 14–47 µs 实测 | 默认关 |

#### (3) 必须先补的两件离线工作（不占空中时间）

1. **★ 定预算的数据来源**：`[ul_thread_cpu]` 现在给的是**窗口**（≈5 次激活，~9 ms）的 CPU ✗ ——
   而预算需要的是**每 slot 的 CPU 分布（p99/p99.9）**。⇒ 扩展该探针，输出每线程的**单 slot CPU 直方图**，
   预算 = p99.9（而不是均值）✓。
2. **档内 `relative_priority` 微基准**（§11.39 补三）：若"相对次序"还能在不丢 QoS 档的情况下拿到，它会成为
   TC 的补充；先离线证明有效再飞 ✓。

#### (4) 一个必须提请裁决的判据变化

TC 架构下**"声明总量"会有数个核**（5 条 pool × 数百 µs / 500 µs + 三条 lower-phy），
而**实测使用量仍只有 ~1.5 核**（pool 0.65 核 ✓）。`computation` 是**上限**、不是消耗 ✓。
⇒ 原登记的"总预留 ≤ ~1.5 核"这条**要改成对"实测 CPU 占用"的限制**，否则会误判一个正确的配置 ✗。
这一点需要用户确认后写进判据。

### 11.42 `pusch_lane` / `lane_commit` 与 `main_pool#0..#4` 的功能分工（代码级）

#### (1) 三个东西各自的角色

| | `main_pool#0..#4`（5 条）| `pusch_lane`（本线新增，默认关）| `lane_commit`（本线新增，默认关）|
|---|---|---|---|
| 性质 | **通用工作池**，同时服务**四个**执行器 | **专用执行器**：只承载 lane 任务 | **单行交接闸门**：只承载 `[cb commit]` |
| 承载的活 | ① `rt_prio_exec`：upper PHY **DL** + MAC 调度；② `high_prio_exec`：控制面 + 定时器；③ **`medium_prio_exec`：PCAP/CU-UP **以及 UL lane**；④ `low_prio_exec`：外部数据 | 一个 lane 任务 = `uplink_processor_impl` 里 `pusch_executor.defer([…]{ pusch_proc->process(pdu) })`（**一个 PDU/一个 hop 的全部主机侧工作**）| `shared_burst::commit()` 的最后一小段：`[cb commit]`（实测 14–47 µs）|
| 与池的关系 | —— | **替代**（`phy_config.pusch_executor = {paced.get(), 1}`），不是叠加 ✗ | **叠加**：池/lane 线程照旧 encode，只把提交让出去 ✓ |
| 并发 | `pusch_executor.max_concurrency = 2`（fork limiter，5 条池线程里**最多 2 个 hop 同时在跑**）| `{paced, 1}` ⇒ **每线程 1 个**（`OCUDU_UL_PACED_THREADS` 后来才允许 N）| 1 |

#### (2) 一个 lane 任务内部有什么

```
pusch_proc->process(pdu)            ← 跑在 pusch_executor 上（池 或 pusch_lane）
 ├─ 信道估计  → pusch_ch_estimator_executor（= 同一个 medium 池，fork limiter 的 [0]）
 ├─ 均衡/解映射 → 并入 Metal 的共享 burst，由 [cb commit] 提交（= lane_commit 若开启）
 └─ LDPC 解码  → 本配置里 pusch_decoder_executor 未由 mapper 赋值 ⇒ 在**同一个任务内**完成
                  （与 `[ul_ldpc_decode]` 在 hop 线程上被测到一致 ✓）
```

⇒ **`pusch_lane` 与池的 medium 执行器承载的是同一件功能**，差别只在"**谁跑**"：一个是专用节拍线程，
一个是**混着 DL/控制面/定时器/PCAP/外部数据**的通用池 ✗✓。

#### (3) 对 §11.41 架构计划的一个直接推论

通用池把 **UL lane 与无关负载混在一起** ⇒ 它的每线程工作是**不规则**的 ✗ ⇒
在它上面按 `period = slot` 做预留时，**保护 UL 节拍的前提是"其它活不吃掉预算"**，而这正好是它做不到的 ✗。
