## 0. 一句话结论

**这条工作流的收益不在"算得更快"，而在"少搬一次、少切一次、少等一次"。**
macOS 上**优先级/QoS 数值上改不动**这条流水线；能动的是**线程的组织方式**（合并、内联、把一次交接变成零次）；
而**绝对 `max` 由外部停顿决定**（7–21 ms 的电台/宿主投递停顿 ✗），任何线程策略都治不了它 ——
**唯一已验证有效的"杠杆"是环境（安静机器）** ✓。

## 1. 立项时立的 flag（原文）与逐条结算

### 1.1 目标（用户 2026-10-01 定调，`phy_pipeline_thread_topology_plan.md` §0 原文）

> 让**同一次运行里"同一个任务花同样的时间"**，即把 `max` 压下来、`min` 不抬升。

| 判据 | 结算 | 数字 |
|---|---|---|
| **`max` 压下来** | ⚠️ **部分成立**：声明（时间约束）本身让 `max` **−8…−24 %** 且**可复现** ✓；但**交付形状 vs 最初对照的 `max` 基本没变** ✗ | 866 → 869 µs（对照 vs 交付形状）✗；869 vs 同形状无声明 948 µs ✓ |
| **`min` 不抬升** | ✓ **成立**（噪声级）| 477 → 482 µs；inline 形状下 `min` 反而**大降**（477 → 156 µs ✓）|
| **同一个任务花同样的时间** | ✓✓ **成立且是本线最强的一项** | `max` 的**跨腿离散度 204 → 10 µs**（TC 的三条腿 859/859/869 vs 无 TC 的 1129/925/948 ✓）；运行内最差窗口 1.2–1.4 % ✓ |
| **首尾**：`median` / p95 / p99 | ✓ 小幅但稳定改善 | 576 → 555（−3.6 %）/ 699 → 672（−3.9 %）/ 729 → 685（−6.0 %）✓ |

★ **用户的总体印象成立** ✓：「**max 并没有得到多少收益，主要收益是纯 CPU 模式下线程间派发/切换 overhead 的消除**」。

### 1.2 规划自己写下的"要改变的东西"（§0 原文）

> 本规划要改变的东西：**不是优先级，不是预算数值，而是线程的组织方式**。

⇒ **这条判断在立项时就是对的** ✓✓ —— 本线的全部正收益都来自它 ✓（§3.2），
而"优先级"那条路被实测判死 ✓（§3.1）。**这一句应当被以后的所有调度类工作引用。**

### 1.3 五条不变量（§0 原文）——**全部守住** ✓

| 不变量 | 结算 |
|---|---|
| 1. **Linux / Ubuntu 行为一字不变** | ✓ 守住：所有新机制都在 `macos_compat` 的平台守卫内；**并且**发现了 probes-OFF 构建盲区并补了守卫脚本（§5.1）|
| 2. 关着旋钮时**逐字节不变** | ✓ 守住：两把钥匙（编译开关 + env）贯彻到底；`[ul_tail]`、`[ul_thread_cpu]`、时间约束、INLINE 开关默认全关 ✓ |
| 3. 申报形状合法（`computation ≤ constraint < period`）| ✓ 守住：非法形状**拒绝施用并报告**，不静默 ✓ |
| 4. 窗口外必须睡（不让路就饿死别人）| ✓ 守住：交付形状的 duty 实测 16.4–17.7 %（声明 30 %，1.7 倍余量）✓ |
| 5. **每条线程的时间片必须来自实测** | ✓✓ 守住：`[ul_thread_cpu]` 就是为此而造（§6），池线程 duty 用 `ps -M` 外部采样交叉验证 ✓ |

### 1.4 量化指标

四条尾部载体 + 三条登记率（`phy_thread_scheduling_plan.md` §0bis.4 登记）；
**操作性定义**也见该文件：
> 实时性不是"一个 slot 内跑完"，而是"**在电台要样本之前交出去**" ——
> `[dl_tx_slack]` 余量分布 + `AT/BELOW 0` 率 + `slip`/`recv` 率 + `gaps`。

本线交付形状在这套定义下：`gaps=0` ✓、健康 CLEAN ✓、`[dl_tx_slack]` p1 ≈ 1005 µs（= 名义值，未变薄）✓。

## 3. 实测换来的两个核心结论

### 3.1 ✗ 优先级 / QoS 这条路是**死的**（数值上改不动）

* macOS 上这套 PHY 线程的**优先级数值无效**：所有线程回读 `eff=USER_INTERACTIVE`、`posix=OTHER/31`，
  唯一的差别只剩 **P 核 / E 核档位**；请求的 QoS 档会被 POSIX 实时调用**静默抹掉且不可恢复**（§10.5/§10.16）。
* 早期 P4（Mach 时间约束）在**当时的形状**上被判"**腿上不可复现**" ✗（七对配对腿的载体比 0.49–2.28，
  §0bis.1）；它只治三类停顿里的第三类（CPU 被抢），且代价是**永久丢掉 QoS 档**。
* 唤醒延迟阶梯（16 个忙线程 / 14 核，500 µs 期限；`wip/sched_microbench/README.md` 的表）：
  **无预留 103–108 µs**（提到 `USER_INTERACTIVE` 不变 ✗）/ **SCHED_FIFO 58.5**（max 91.2）/
  **时间约束 p50 3.2（max 8.2–14.8）µs** ✓ —— 机制本身有效 ✓，问题在于**是否有一条线程承载得起它**（见 3.3★）。

### 3.2 ✓★ 组织方式（orchestration）才是杠杆 —— **这才是本线的收益来源**

| 改动 | 性质 | 实测 |
|---|---|---|
| **rx 与 UL 前端合并**（`dual`）| 少一次线程间交接 | `[ul_handoff]` p50 **9–11 µs → 1 µs** ✓（且**对负载免疫**：忙时前者 1326–1363 µs，后者仍 1 µs）✓；`[ul_time_frequency]` −12.9/−13.7/−13.3 µs（三次复现 ✓）；端到端 −13.5 µs ✓ |
| **PUSCH 链内联**（`INLINE_PUSCH`）| 少一次派发 + 少一次池排队 | 窗口对齐后 median **−62.8 µs（−9.9 %）**，且 p95/p99 **更好** ✓ |
| **解码也内联**（`INLINE_DECODE`）| 让整条链成为**一个**预留主体 | 528 B（单码块）TB 上无代价 ✓；使 §3.1 的声明**第一次变得有效** ✓ |
| **声明（时间约束）** | 把"一条线程的一段工作"变成内核预留 | max −8…−24 %、跨腿离散度 204 → 10 µs ✓（§2.2）|

### ★ 3.3 关键和解：为什么早期 P4 判"无效"而后期判"有效"

**同一机制，两个相反结论，差别不在机制，而在"工作有没有被合到那一条线程上"** ✓✓：

* 早期形状（池链）：一跳的工作**跨 rx / 池 / lane 多条线程** ⇒ 给其中**一条**线程预留，
  覆盖不了这一跳 ✗ ⇒ 载体比 0.49–2.28，不可复现；
* 交付形状（合并 + 全内联）：**从样本到 CRC OK 全在同一条线程上** ⇒ 预留**覆盖整跳** ✓
  ⇒ max 稳定下降且可复现 ✓。

⇒ **"预留只对承载得起它的线程有效"，这本身就是 orchestration 论的一条硬证据** ✓。

### 3.4 ✗ 绝对 `max` 由**外部停顿**决定 —— 任何线程策略都治不了

* 本线遇到的停顿（全部经闸门判为**环境性**）✗：p295 **21 ms**、p298 7.3 ms、p302 12.5 ms、
  p306 **10.2 s**、p309 19.8 ms —— 横跨 cpu / gpu / cpu_gpu **三种模式** ⇒ 与模式无关 ✓；
* 它们的来源是**电台/宿主投递**（`[ul_rx_wait]`、`[ul_lane_grid] FRONTIER 交付滞后`、
  watchdog 的 `radio.rx` 站点 ✗），而不是处理时间 ⇒ `[ul_pipeline]` 的 max 在每条腿上都被它们支配 ✗；
* **唯一已验证有效的杠杆是环境**（安静机器）✓：早期实测 `ce` max **11 185 → 1 120 µs**、
  `eqd` 11 571 → 2 905–3 293、`rx_wait` 10 998 → 2 116–2 442，**≥8 ms 停顿 0 次**（§0bis.1）✓；
* ⇒ 这条与用户印象一致 ✓：**max 的主要收益不来自线程工作** ✗。以后若要在 `max` 上再进一步，
  战场在**投递路径**（电台 ring / USB / 驱动 / 宿主唤醒），不在优先级 ✗。

## 5. 踩过的坑（按类，每条一句教训）

### 5.1 方法论坑（**仪器与判据**）

| 坑 | 教训 |
|---|---|
| `max` 是**单样本**，两条腿样本数不同就不可比 ✗ | 为此造了 `[ul_tail]` 普查：**计数**可相减、可相加；相对锚点跨形状可比，绝对锚点跨腿可比 ✓ |
| 固定锚点会**饱和**（内联形状下 99.9 % 的样本都在 500 µs 之上 ✗）| 锚点必须**两族**：相对（中位数倍数）+ 绝对 ✓ |
| **probes-OFF 是默认构建**，而飞行腿全是 ON ⇒ "没人编的那一支恰好是默认那一支" ✗（Ubuntu 构建因此断掉）| 加 `probes_off_syntax_check.sh`：拿每个 TU 自己的 flags 去掉探针宏做语法检查（34 TU / 50 s）✓ |
| 同一个 CLI 选项传两次 ⇒ **gNB 在任何横幅之前退出** ✗（表现为"手机接不进去、CN 无反应"，像电台故障 ✗）| runner 现在**起飞前拦截重复选项**并给 workaround ✓；"腿不能静默地拿到它没得到的臂" |
| 扫描脚本自身的**误报**：按 basename 找目标会撞别的 target ✗；`.mm` 用 `OBJCXX_*` 而不是 `CXX_*` ✗ | 用**完整源路径 + 对象规则**匹配、按扩展名选 language triplet ✓（为此误加的 5 处 `[[maybe_unused]]` 已全部撤回 ✓）|
| `[sched]` 行里的 `cpu=` 是**线程启动瞬间**的读数 ✗（≈0）| 测 duty 只能用探针或 `observe_threads.sh`（`ps -M` 的 ΔCPU/Δwall）✓ |
| 闸门的"DL 迟到"**有两种原因** ✗（臂本身慢 vs 宿主停顿）| 用**一对**读数分辨：迟到 + watchdog late **很小** ⇒ **进程内（臂）**✓；迟到 + watchdog late **很大** ⇒ **宿主** ✓ |
| 池计数出现 `held_end=-17`、`held_max=UINT64_MAX` ✗ | 根因是**计数顺序**（take 记在缓冲交出去**之后**）⇒ 搬到"离开池的那一刻" ✓，并让违规**读起来像违规** ✓ |

### 5.2 归因坑（**别把 A 的效果记到 B 头上**）

| 坑 | 教训 |
|---|---|
| 链路退化时 HARQ 合并缓冲让**解码变长** ✗（64 vs 44 µs）⇒ 差点写成"TC 让解码快 31 %" | 健康闸门（CLEAN ≥99 %）必须先过；不干净的腿**不解释、直接作废** ✓ |
| ping 的**应用层 RTT** 被 core 侧与 HARQ 重传支配 ✗（402 ms vs gNB 可见 398 ms）| 应用层数字**不能**当线程工作的判据 ✓；改用 gNB 边界（`rtt_split.py` 配 GTPU trace）✓ |
| 环境的 7–21 ms 停顿会**污染整条腿** ✗（一次停顿就能造出 max 与计数）| `dl_gate.sh`：**先过闸门再判读** ✓；"重飞而不是解释" ✓ |
| 单次停顿**不会**污染中位数（可证：19.8 ms ≤ ~40 个时隙 = 1074 样本的 3.7 %）✓ | 分布紧时中位数可用 ✓（但仍标注"不可引用比值" ✗）|

### 5.3 平台坑（**macOS / 硬件**）

| 坑 | 教训 |
|---|---|
| QoS 与 Mach 时间约束**双向互斥**，施加约束就**永久删掉 QoS 档** ✗ | 对 rx 线程这笔交易划算 ✓，对池线程不划算 ✗ ⇒ **逐线程**决策，不许"给所有线程发同一参数" |
| `radio` 线程按设计**不可声明**（旋钮只作用于 worker）| 投递路径的停顿**不在**调度杠杆的射程内 ✗（§3.4）|
| B210 在 **7.68 Msps 主时钟**下 AD9361 停止供钟 ✗ | N1 5 MHz 小区必须用 **15.36**（2× 过采样）✓ |
| 5 MHz 小区下**写任何一个 `pucch` 键**会让哨兵失效 ⇒ 小区被拒 ✗ | 派生配置**不设 pucch 键**，让缩减档生效 ✓ |
| MCS 13 pin 是为**尺寸对齐**设的（A/B 需要）| 换小区（5 MHz）后它**会打爆链路** ✗ ⇒ 模式验证腿用无 pin 配置 ✓ |

### 5.4 被推翻的假设（**记下来，免得重犯**）

* ✗「池线程也声明上会更好」—— 零收益 + DL 低尾劣化 2.9 倍；
* ✗「Metal 解码器接不进去」（历史经验）—— **能接入** ✓，真实代价是**每次 3.5 ms**；
* ✗「模块级混合（cpu_gpu）是通向 gpu 的中间台阶」—— 它是**三者里最慢**的（1901 µs），
  因为每跨一次模块边界就付一次往返 ✗；
* ⚠「`computation = period`（100% duty）安全吗」—— 微基准 03 记它灾难性 ✗、README C 记历史形状无害 ✓，
  **冲突至今未解** ✗ ⇒ 交付形状刻意远离它（30 %）✓。

## 7. 对以后工作的启示：**瓶颈在 orchestration，不在算力** ✓（确认）

### 7.1 用本线的数字确认用户的判断

| 观测 | 数字 | 含义 |
|---|---|---|
| rx 线程一跳的全部工作 | **~85 µs / slot**（duty 16–18 %）| **算力极其富余** ✓ |
| 一跳里的"搬运/协调"代价 | 派发 15 µs、**每跨模块边界 ~340 µs** ✗、融合 lane 单次提交 host 站 ~680 µs ✗、解码每次 **3.5 ms** ✗ | **协调代价 ≫ 计算代价** ✓✓ |
| GPU 占用率 | **0.29 %** ✗ | 设备根本不忙 ⇒ 慢的是"**把它叫起来/等它回来**" ✓ |
| CPU 上同一件活儿 | 均衡+解调 ~20 µs、解码 26–34 µs | 单跳小批量下**算力不是问题**，甚至 CPU 更快 ✓ |
| 绝对 max 的来源 | 电台/宿主投递停顿 7–21 ms ✗ | 连"计算"都不是限值，**投递**才是 ✓ |

⇒ **确认**：**端到端的性能瓶颈不是 CPU/GPU/NPU 的算力，而是它们之间的 orchestration** ✓✓
（派发、交接、提交、排队、唤醒、投递）。

### 7.2 与高层架构文档一致 ✓（原文引用）

`../apple_silicon_heterogeneous_gnb_plan.md`：

* §1「**Metal 的优势是高并发，不是单链路低时延**」✓ —— 与本线"gpu 形状中位是 cpu 形状的 2.6 倍" ✗ 一致；
* §1「各模块的 Metal 实现**允许比 CPU 路径慢 10× 以上**」✓ —— 本线实测解码器慢 ~100× ✗（超出许可范围）；
* §2「**所有 Metal 模块同时打开是更好但非必需的目标**……当前 LDPC layered 变体的 **dispatch 链开销**是主要缺口」✓✓
  —— **架构文档自己就把缺口命名为 dispatch 链开销**，与本线"每模块边界 ~340 µs" ✓ 完全一致；
* §2.1「**兵马未动，粮草先行**：一切可预先准备的资源必须在启动期完成，数据包路径上只允许出现真正数据依赖的计算」✓
  —— 这正是 orchestration 论在架构层的表述 ✓。

### 7.3 由此得到的、可直接执行的方向

1. **时延敏感的路径留在 CPU、并尽量合并到一条线程上** ✓（本线交付形状就是这条原则的成品）；
2. **offload 只做批量/吞吐** ✗ —— 单跳小批量下 GPU 不划算（371–480 µs 设备执行 vs CPU ~20 µs ✗）；
3. **减少边界，而不是加快边界** ✓：能合并成**一条命令缓冲**（融合 lane）就比"每个模块一次提交"快得多
   （1430 vs 1901 µs ✓）；能把两段工作合到一条线程就合并（本线的全部正收益都来自这里 ✓）；
4. **让等待可重叠（in-flight > 1）** ✓ —— 这是 gpu 尾巴唯一有机制支撑的改动（§11.98/§11.109）；
5. **把"投递"当作一等公民** ✗✓ —— 绝对 max 的战场在电台 ring / USB / 驱动 / 宿主唤醒（§3.4），
   谁要压 max，就得先量这条路径（`[ul_rx_wait]` + FRONTIER + watchdog 三件套 ✓）；
6. **先仪器、后杠杆** ✓ —— 本线最贵的一课是"没有分类就读不懂停顿"：装了看门狗才知道
   三类停顿只有一类归调度管 ✓；
7. **默认构建也是被测对象** ✓ —— probes-OFF 盲区说明"只有飞行的配置才被编译过"是系统性风险 ✗。
