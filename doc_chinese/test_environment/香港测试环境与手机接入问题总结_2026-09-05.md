# 香港测试环境与手机接入问题总结（2026-09-05）

## 1. 背景

OCUDU gNB（srsRAN fork，apple-silicon 分支）+ open5GS 核心网的 5G SA 测试系统从北京搬到香港后：
- gNB/核心网侧很快恢复（改 IP 后 NG Setup 成功）
- OAI UE（SDR 软件 UE）全程接入无问题
- 但两台手机（OnePlus 8T、iPhone 17 国行）在香港均无法接入，且行为与在北京时完全不同

调查结论：**问题不在 gNB、核心网、SIM 卡或频率，而在手机 modem 的区域策略门控（手机"知道自己身处何地"，并按区域开关 5G SA 搜索/接入）**。

## 4. 平台对比：Ubuntu gNB vs macOS gNB

### Ubuntu gNB（107）——健康
- 实时性故障仅 1 次
- OAI UE 接入全程成功：注册完成 + PDU 会话 + ping 通核心网 10.45.0.1

### macOS gNB（Mac）——曾因机器过载"假坏"
- 最初 2628 次实时性故障（`late DL_TTI.request` / `PRACH request late` / RF underflow），TX 发不出有效 SSB，手机和 211 扫描都看不到小区

结论：macOS gNB 平台本身可用，但**对系统负载极敏感**（20 MHz TDD 23.04 MS/s 实时要求高），跑 gNB 前必须清退 OneDrive/VS/Spotlight 等重负载进程。

## 6. 核心结论：手机 modem 的区域策略门控

1. 手机通过 **GPS/北斗 + 基站广播 MCC（460 中国 / 454 香港）+ 运营商策略文件** 判定所处区域
2. SA（5G 独立组网）的**小区搜索**不是"全频段随便扫"，而是被区域策略开关控制：
   - OnePlus（Qualcomm）：中国区 SA 搜索放行（北京全通），香港区整个 SA 搜索关闭（NR only 全空）；收紧过程：接入 → 仅可见不可接 → 完全不可见
   - iPhone 国行（Apple）：SA 白名单只含 460xx 中国运营商 PLMN，非 460 的 SA 网络从不显示/接入；iOS 更新后连老 gNB 的 RACH 都不再发起
3. 港区无法用手机测试 = 策略限制，**gNB/核心网/SIM/频率均无责**（OAI UE 全程证明系统健康）
4. 香港本地 SIM 对 OnePlus 无效：说明门控不是"漫游"判定，而是更底层的区域策略

## 6.6 root OnePlus 取证结果（2026-09-05 下午）

通过 adb + root（Magisk）对 OnePlus 8T（KB2000 国行，ColorOS）做了 modem 取证：

- **搜网路径证据**（radio logcat）：
  - auto 模式搜网走 **OPPO 私有搜网控制器**（ONSNetworkScanCtlr，直连 modem QMI），结果不经标准 RIL 日志；只列 3G/4G，无 5G
  - NR-only 搜网三种失败形态：① `QUERY_AVAILABLE_NETWORKS → error 39 SYSTEM_ERR`（modem 拒绝）；② 请求根本不发出（UI 卡死"正在搜索"）；③ OPPO 私有通道静默报错（"搜索网络时出错"一闪）
  - **唯一一次成功**（13:00，重启后第一次搜索）：NR-only 列出 4 家香港运营商 5G + 3G/4G，但无 00101；此后同样操作不再复现——搜索行为不可控，符合区域策略状态机的特征
- **GSCN 对齐实验**：从源码推导出 OCUDU 的 SSB 定位公式（SS_ref = 3000 + 1.44×ceil((pointA+3.6MHz−3000)/1.44)，pointA = 中心−9.18MHz，51CRB/30kHz），三组实测数据验证无误；把 gNB 的 SSB 精确对齐到香港商用 SA 的 SSB 频点 3519.84 MHz（GSCN 7860，商用 SSB 地图上 3300–3600 内唯一检测到的 NR SSB）后，手机搜索**整体失效**（什么都搜不到）
- **PLMN 假扮实验**（配置已备好 `gnb_test_B_fakeplmn.yaml`：3525.0 + PLMN 45499，未完成）：若手机列出 45499 → 001 测试 MCC 导致搜索中断；若仍全空 → 强 SSB 压制商用 GSCN 频点
- **EFS 加密**：modemst1/2、fsg 分区导出后无可读字符串（OPPO 加密 EFS），NV 项无法离线分析
- **MBN**：SDX55 基带库含各运营商 mcfg_sw.mbn（含 CMHK/HK 商用配置）；SA 扫描频点列表在 MBN/EFS 中
- **NSG**：4.7.x 已通过 adb 安装（com.qtrun.QuickTest），无独立 NR5G 页签，观察价值有限

**结论**：香港用手机做 SA 测试不可行（modem 区域策略门控 + ColorOS 搜网实现缺陷叠加）。继续深挖需 diag/QXDM 通道（Windows 或 qcdm@211），成本高、收益不确定；手机测试留到回北京。HK 期间以 OAI UE 为唯一 UE 继续平台对比。

## 6.7 无 WiFi 桥接直连场景（已验证全通）

**场景**：Mac gNB 与 UTM 虚拟机核心网仅通过 UTM 桥（bridge100：192.168.64.1 ↔ 192.168.64.4）互通，无外部网络。

**配置要点**：
- 核心网（122）：AMF ngap 监听 192.168.64.4（+31.122 双模）；UPF gtpu = 192.168.64.4（改后需重启 UPF，AMF 不用）
- Mac gNB（`gnb_uhd_oaiue.yaml`）：`amf.addrs: 192.168.64.4`、`bind_addrs: 192.168.64.1`、`cu_up.ngu.socket.bind_addr: 192.168.64.1`
- 结果：NG Setup + 注册 + PDU 会话 + ping 10.45.0.1 全通（OAI UE 验证）

**教训（OAI UE 稳定性）**：
- 现象：UE 近距离 + `ue-txgain=0`（TX 满功率 89.75）时，gNB 侧 64QAM PUSCH 出现 **SINR 18.9 dB 却 CRC 全 KO、LDPC 迭代跑满** —— 接收链过驱动削波，QPSK（PUCCH）不受影响 → NAS 上行卡死 → 反复 RACH/掉线
- 修复：降低 `ue-txgain`（如 40）或**拉远 UE 与 gNB 的距离**（当前采用：恢复 ue-txgain=0 + 挪远距离）

## 6.9 SIM/UE 交叉实验：iPhone 5G 失败 100% 是手机策略

| UE + SIM | 5G（OCUDU 627264） | LTE（srsRAN 4G） |
|---|---|---|
| OnePlus + 789 | ✅ 接入 + ping | — |
| OnePlus + 890 | ✅ 接入 + ping | — |
| iPhone + 789 | ❌ 无反应（无 RACH） | ✅ 附着（会话 flap） |
| iPhone + 890 | ❌ 无反应 | ✅ 附着（首次认证死亡后自愈） |

**结论**：
- **iPhone 的 5G 失败与 SIM 无关**——两张卡在 OnePlus 上 5G 全通、在 iPhone 上 LTE 全通；iPhone 的 modem 策略拒绝 5G SA（n78 连 RACH 都没有，n1 死在认证）——iOS "进化"实锤
- **iPhone 的"认证死亡"是首次尝试行为**：LTE 上第一次附着死在认证（无响应→释放）、第二次自愈成功；5G 上重试路径被策略卡死
- **SIM 5GS 文件理论彻底证伪**：SIM 无 DF.5GS 但 OnePlus 用它们 5G 全通
- iPhone 在 LTE 的会话 flap 源于 srsepc 缺陷：TAU 未实现 + 第二 APN（IMS）未配置被拒（PDN Connectivity Reject），非手机问题

## 6.10 srsenb（srsRAN 4G）对接 open5gs MME 实验

**配置**（已完成）：211 的 `enb.conf`：mme_addr 192.168.31.122、gtp/s1c 绑定 192.168.31.211；122 的 `mme.yaml` s1ap 192.168.31.122、`sgwu.yaml` gtpu 192.168.31.122（pfcp 保持 127.0.0.6）；守护进程 mmed/sgwcd/sgwud/hssd/pcrfd 运行。

**结果**：iPhone/OnePlus 均能完成附着（认证/安全/会话建立，open5gs 侧 Attach complete），但**反复断开重连**。

**根因**（srsenb 侧缺陷）：带 NAS 的 RRC 重配置未被手机 ACK → SRB1/SRB2 RLC 重传耗尽 → eNB 重试承载建立 → 但 `rrc_bearer_cfg.cc::fill_pending_nas_info` 只在第一次重配置挂 NAS（消费即清空）→ 重试无 NAS → 手机永远收不到激活承载 → 释放重连循环（`Not adding NAS message to connection reconfiguration` 刷屏 + `Signaling max number of reTx`）。

**待排查**：① DL 链路质量（NSG 看 SINR）；② 换干净频点（dl_earfcn 1575=1842.5MHz B3，默认 2685MHz 是 HK B7 商用密集区）；③ srsepc 对照实验（区分 MME 因素 vs enb/射频退化）。OnePlus 未拿到新 IP 即会话未建立（显示旧 5G 残留）。

**对照实验（srsepc）**：enb 换回 srsepc 后仍有断开/重连，但**明显减少**，且手机**成功拿到 IP**——flap 分两层：① 基线层是 srsenb 20.10 自身的 DL RRC 重配置投递缺陷（与核心网无关）；② open5gs 的 NAS 消息更大（IE 更多），加重了打包/重传问题，导致会话无法完成。**结论：LTE 手机测试暂用 srsepc；open5gs 互连 NAS 层已验证可用，flap 修复需升级 srsRAN 4G（21.10+/22.x）或深挖 srsenb RRC 代码**。

**意义**：困扰数月的 iPhone AKA 死亡之谜有了工作配置——iPhone 的 5G SA 行为是复杂的策略状态机，**同一频段在不同环境/状态下结果不同**：

| 环境 | iPhone 5G SA 行为 |
|---|---|
| 北京 · n1（8 月） | RACH→注册请求→**死在认证**（每次） |
| 香港 · n78 627264 | **无 RACH**（完全不尝试） |
| **香港 · n1（现在）** | **完整注册 + 会话建立** ✅ |

**后续观察（20:31）**：iPhone 连接约 2 分钟后掉线——掉线前 DRB1 双向数据活跃（手机在发 IMS SIP 注册，sn 376-379），随后手机停止 ACK 下行（SRB1 DL Poll retransmit 超时）→ RLC 耗尽 → gNB 请求释放（AMF Action:2）。同期 OnePlus（0x4606）PUCCH sinr 30-34 dB 健康，小区无恙。**定性：iPhone 行为从"死在认证"进化为"注册+会话+数据全通，但 IMS SIP 注册期间 DL 静默掉线"**——核心网无 P-CSCF，IMS 注册注定失败，疑似 modem 策略在"网络不可用"判定后主动中止。待复测：掉线是否规律（~2 分钟）、手机侧现象。
