## 0. 一句话结论

> **在边缘节点形态下，Apple Silicon 与同价位 x86+GPU 的原始 FP32 算力大致持平；
> 判别性优势来自三处架构性质：(1) UMA 让异构路由的边际成本为零；(2) 没有 lookaside 的 PCIe 天花板；
> (3) 单核性能使小包/URLLC 的 CPU 路径结构性占优。**
>
> **"平台约束"不构成劣势——目标在约束下已达成，且约束倒逼出了更可移植的车道模型；约束一旦放宽是加分项。**
> **"单厂商风险"不是差别化劣势（两边在加速器上都无法双源，Apple 侧的集成边界反而更少），
> 但 v1.1 更正：它在"近期"是真实的——因为把"硬件能力存在"与"软件栈可用"拆开后，
> 只有 Apple 一家在 Linux 上三引擎都可落（§5.3）。这是一条软件时滞，不是结构性壁垒。**

## 1. 问题的正确形式（这一节决定后面所有分析是否有意义）

### 1.1 三种错误的问法（本仓库历史上都出现过）

| ❌ 错误问法 | 错在哪 |
|---|---|
| "CPU 和 GPU 谁快？" | 在 Apple Silicon 上它们是**联合作战**，不是竞争关系。目标形态是按业务类型把数据送往不同引擎 |
| "我们的 GPU 和 NVIDIA 的 GPU 谁快？" | 比较单元错了。节点内每个引擎都用它最擅长的部分，**比的是节点** |
| "GPU 路径的端到端延迟是多少？" | 那是**一条路径**的延迟，不是**节点**的延迟。时延敏感业务走的是 CPU 路径 |

### 1.2 正确的问法

> **在给定的功率 / 体积 / 成本包线内，一台节点能承载多少个小区、对各类业务分别达到什么时延？**

因为 SWaP-C 是硬约束（路边机柜、灯杆、离网供电），**目标函数是"每瓦每升每美元能承载的小区数"**，而不是峰值 FLOPS。

### 1.3 每个引擎的职责分工（与设计一致）

| 流量类型 | 承载 | 理由 |
|---|---|---|
| V2X 控制信令 / 小包 / URLLC | **P/E 核（CPU 路径）** | 串行链路，单核性能决定；无 GPU 往返 |
| 视频 / 大包 / eMBB | **Metal GPU** | 高并发吞吐 |
| AI 接收机 / 预测 | **ANE/NPU** | 超低功耗推理，且不占 GPU 队列 |

**⇒ 因此"时延"和"吞吐"必须<b>分别归到各自路径</b>去测，不能用一个路径的数字代表整机。**

### 1.4 ★ 评价标准：给用户创造的价值，**不是**评审者的认可

**这一节要纠正一个此前的隐含前提。** 关于"要不要重用上游 CUDA 的抽象"、"怎么设计才更容易被
接受从而合并进 upstream"的那些讨论，都隐含地服务于一个目标：**让评审者认可**。

**那个目标不是评价标准。** 本文（以及相关的架构分析）的评价标准是：

> **给用户创造的收益与价值。在 OCUDU stack 这个例子里，就是 E2E performance；
> 而目标场景是 V2X 这类 URLLC 与 eMBB 并存的边缘应用。**

**⇒ 三条直接后果：**

| # | 后果 |
|---|---|
| 1 | **"上游会不会接受"不进入设计取舍**。一个抽象是否采纳，只看它是否让 E2E 更好、是否让路由更便宜、是否让 CPU 更靠边站——不看它是否与上游相似 |
| 2 | **评价场景从"某个模块快不快"改为"这个异构节点在混合业务下的表现"**。单一业务（只有 URLLC 或只有 eMBB）都能被单一引擎覆盖，**只有混合场景才需要异构**，所以**混合场景才是目标场景**（§9.2 的第三种载荷从"其中一项"提升为**主判据**） |
| 3 | **"与 CUDA 对比"的用途随之改变**：不是为了向谁靠拢，而是为了**不采纳错误的抽象**、并**认出哪些工程手法真的可借鉴**（详见 `metal_vs_cuda_architecture.md` §7） |

**⚠️ 一个必须保留的限定**：评价标准是用户价值，**不等于**"上游合并毫无价值"。
合并能降低**长期维护成本**（当前已经有 500+ 提交的偏离，每次跟进上游都要手工合并）。
**它是手段，不是目的**——所以它由"值不值得这个成本"决定，而不是由"评审者高不高兴"决定。

## 2. 第一性原理：绑定约束到底是什么

### 2.1 先算清楚数据有多大（纯计算，无外部依赖）

目标小区：**100 MHz / 30 kHz SCS / 4RX**

| 量 | 计算 | 结果 |
|---|---|---|
| 采样率 | 100 MHz NR @30 kHz → 122.88 Msps（FFT 4096） | — |
| **原始 IQ 速率** | 122.88 Msps × 4 B(ci16) × 4 端口 | **1.97 GB/s** |
| 每 slot（0.5 ms）IQ | 1.97 GB/s × 0.5 ms | **0.98 MB** |
| 资源网格（FFT 后） | 273 PRB × 12 子载波 × 14 符号 × 4 端口 × 4 B(cbf16) | **0.73 MB/slot** |
| **每 slot 热数据** | IQ + 网格 | **≈ 1.7 MB/slot** |
| **热数据总速率** | × 2000 slot/s | **≈ 3.4 GB/s** |

**⇒ 这个量级远低于任何现代互连的带宽上限。** 本仓库蓝图 §3.1 独立算过同一笔账并得出
"2RX + 2TX 全双工 ≈ 368 MB/s ≈ 3 Gbps；TB5 单向 ≥ 60 Gbps……**裕度 > 10×，瓶颈绝不在链路而在软件**"。

**⇒ 结论 1：带宽不是绑定约束。** 这一条直接作废"273 GB/s vs 63 GB/s"那一类论证。

### 2.2 真正的绑定量：**同一份数据被搬几次**

| 架构 | 数据路径 | 输入跨越 | **每个卸载模块的中间态跨越** |
|---|---|---|---|
| CPU-only x86 | NIC → 主机 DRAM → CPU | 1 | **0** |
| **x86 + lookaside** | NIC → 主机 DRAM → **PCIe→加速器→PCIe→主机 DRAM** | 1 | **2 × N模块** |
| x86 + NVIDIA inline（DPU + GPUDirect） | NIC → DPU → **PCIe/GPUDirect→GPU 显存** → GPU 内全链 | 1 | **0** |
| **Apple：FPGA → UMA → GPU 直读** | FPGA → TB5 → **统一内存** → GPU 读**同一块内存** | 1 | **0** |

### 2.3 lookaside 的链路负载与它的天花板（可独立算得）

保守假设：卸载 CE + LDPC 两个模块，各自输入输出各跨一次：

| 项 | 每 slot 跨 PCIe 的量 |
|---|---|
| CE 往返（网格 0.73 MB + 估计 ~0.73 MB） | ≈ 1.5 MB |
| LDPC 往返（LLR 输入 + TB 输出） | ≈ 1.0 MB |
| **单小区合计** | **≈ 2.5 MB/slot → 5 GB/s** |
| **4 个 100 MHz 小区** | **≈ 20 GB/s** |
| PCIe 4.0 x16 实际上限 | ≈ 25 GB/s |

**⇒ 结论 2：lookaside 架构在"几个 100 MHz 小区"的量级上就会把 PCIe 4.0 打满。**

这与 NVIDIA 自己博客中的声明（"lookaside 多消耗约 40× 带宽"、"PCIe Gen4 撑不住、需要 Gen5"）方向一致，
但**上述推导是独立完成的，不依赖他们的结论**。

### 2.4 UMA 的判别性优势不是带宽，而是"路由免费"

**必须纠正一个常见的过度声称**：不能说"我们的架构零次跨越"——**IQ 仍要跨 TB5**（FPGA 是外置的），
与 NVIDIA 跨 PCIe 是对等的一次。**NVIDIA 的 inline 也把中间态降到 0（全链在 GPU 内）。**

**所以差别在下一层：**

| | NVIDIA inline（离散显存） | **Apple UMA（统一内存）** |
|---|---|---|
| 输入落地位置 | GPU 私有显存 | **CPU/GPU/ANE 共享的内存** |
| 落地后谁能读 | 只有 GPU | **三个引擎都能读** |
| 要把这一 slot 改派给 CPU 或 ANE | **必须再拷一次** | **零成本，改指针即可** |
| 异构路由的边际代价 | **一次拷贝 + 一次同步** | **0** |

**⇒ 结论 3（本分析的核心）：**

> **离散架构的异构 = 把活派给谁，就得把数据搬给谁。**
> **UMA 架构的异构 = 数据不动，只换谁来看。**
>
> **这是本方案唯一无法被 x86+GPU 复制的东西——不是带宽，不是 FLOPS，是路由的边际成本为零。**

## 3. 同价位对比（方法论修正后的版本）

### 3.1 先说清楚本仓库历史上犯过的四次误比较

**这一节保留在这里，是为了防止以后（包括未来的我们）重犯。**

| # | 错误做法 | 为什么错 | 扭曲方向 |
|---|---|---|---|
| 1 | 拿 **H100 的 ~1000 TFLOPS** 对比 **M4 Pro 的 ~8 TFLOPS** | 前者是 **FP16 tensor + 稀疏**，后者是 **FP32 向量**。PHY 的 FFT/CE/均衡是 FP32 向量负载 | **人为放大差距十几倍** |
| 2 | 拿 **M4 Pro**（Apple 桌面线最低配）对比 **H100**（NVIDIA 最高配） | 这不是同价位对比，是最低配对最高配 | 双重扭曲 |
| 3 | 拿 **H100**（数据中心训练卡）作为 vRAN 对标 | vRAN 的对标部件是 L4 / RTX 4000 Ada 这一档 | **同时抬高 x86 侧的价格与算力**，使"每美元"比值失真 |
| 4 | 拿 **GPU 单路径延迟**代表**节点性能** | 时延敏感业务走 CPU 路径；那条测量里 CPU 路径是空闲的 | 用一条路径否定整机 |

### 3.3 价位点 A ≈ $2,700

| | Apple：Mac Studio M4 Max 128GB | x86：Ryzen 9 主机 + L4 |
|---|---|---|

| 可寻址内存 | **128 GB 单一空间** | 64 GB DDR5 + 24 GB 显存 = 88 GB，**分离** |

| **数据路径上的互连** | **无** | **PCIe Gen4 x16** |

**⇒ x86 侧 FP32 强约 1.9×；Apple 侧内存带宽强约 1.8×、可寻址内存更多且是单一空间、自带 NPU、无 PCIe 税。**

### 3.4 价位点 B ≈ $4,000

| | Apple：Mac Studio M3 Ultra 96GB | x86：同价 Ryzen 9 主机 + RTX 4000 Ada |
|---|---|---|
| 加速器 FP32 | ~28–33 TFLOPS【推算】 | 26.7 TFLOPS【官方】 |
| 内存带宽 | **819 GB/s**【官方】 | 360 GB/s【官方】 |
| 内存容量 | **96 GB 统一** | 20 GB 显存 + 64 GB DDR5 |

**⇒ 这个价位点 Apple 占优：FP32 大致持平，带宽 2.3×，统一内存容量 ~4.8×，且自带 CPU+NPU。**

### 3.5 结论

> **❌ 不是"Apple 胜出 2–4×"。**
> **✅ 是：同价位下原始 FP32 算力大致持平（x86 配 L4 时略强），Apple 侧在内存带宽、统一内存容量、集成度上占优。**

**这个结论更弱，但更站得住，而且对我们更有利**：
1. **不需要证明算力赢**——算力持平 + 架构占优就足以支撑论断；
2. 凡是"我们算力是对方 N 倍"的说法，**评审者只要换一个对标部件就能打掉**（§3.1 演示了两次）；
3. **判别性优势是架构性的，不随对标部件更换而改变。**

## 4. 时延轴：小包 / URLLC —— **Apple 结构性占优**

### 4.1 本仓库的实测

> `doc_chinese/metal_ldpc/PLAN.md` §1：UL compute pipeline 探针证明
> **macOS M4 Pro 的纯 CPU 算力（219 µs 中位数）已远超 Ubuntu（892 µs）**。【实测】

**⚠️ 必须标注的限定**：那台 Ubuntu 参照机在 `tests/ci/macos_e2e/REPORT.md` 中被写作 **NUC**
（"the Apple Silicon slot production outruns **the NUC's**"），**不是服务器级 Xeon**。
⇒ 这是"M4 Pro vs NUC 级 x86"，**不可外推为 vs Xeon Gold**。

### 4.2 单核性能排序（独立依据）

| 处理器 | 核数 | Geekbench 6 单核（量级，【推算】） |
|---|---|---|
| **M4 Pro** | 14 | **~3,900** |
| Core i7（NUC 级） | 12–14 | ~2,300–2,600 |
| **Xeon Gold 5412U** | 24 | **~1,600–1,800** |

**⇒ 单核排序：M 系列 > 桌面 x86 > Xeon 级服务器。Xeon Gold 的单核确实低于 NUC。**

### 4.3 为什么这不是偶然，而是设计目标的必然

服务器 CPU 的优化目标是 **每插槽聚合吞吐 × 内存容量**，而非**单线程时延**：

| 服务器 CPU 为聚合吞吐付出的代价 | 对串行链路的影响 |
|---|---|
| 更多核 → 更低频率（5412U base 2.1 GHz） | 直接降低单线程速度 |
| Mesh / 环形互连（而非单片共享 L3） | 核间与访存时延显著升高 |
| NUMA 分区 | 跨节点访存时延翻倍 |
| 为大容量内存优化的访存通路 | 单次访存延迟更高 |

**而我们的时延敏感链路（CE 63.6 µs + LDPC 10–70 µs）是串行的**——串行链路的性能由
**单核速度与访存延迟**决定，**恰好是 Xeon 最不擅长的两个维度**。

**⇒ 在 URLLC / 小包这条轴上，x86 服务器架构是用错了工具**：它拿 24 个核去跑一条只能用 1 个核的链路，
而那个核还比 M 系列慢一倍以上。

**⇒ 结论 4：小包时延这一轴，Apple 结构性占优**（不是我此前暗示的"双方接近"）。

## 5. 单厂商风险：**差别化劣势可以删除，但"近期唯一可用形态"必须承认**（v1.1）

### 5.1 "0.5 厂商"的准确含义

> **x86 + CUDA + NPU 这一侧，需要多个"各自单厂商"的部件才能拼出一个能跑的平台；
> 而 Apple 一侧一个厂商就能跑起来。**

| 平台 | 需要的厂商 | 每个关键部件的可选来源 | **集成边界** |
|---|---|---|---|
| **x86 + CUDA + NPU** | Intel/AMD（CPU）+ NVIDIA（GPU **且** CUDA 锁定）+ 第三家（NPU/推理卡） | CPU 可双源；**GPU/CUDA 单一来源**；NPU 单一来源 | **3–4 个片间边界**（PCIe ×N） |
| **Apple Silicon** | **1 家** | 全部单一来源 | **0 个片间边界** |

### 5.2 关键对称性

**两边在"加速器"上都**无法**双源**（CUDA 只有 NVIDIA）。
⇒ **"单厂商"不构成对 Apple 的差别化劣势**——它是两家共有的风险，只是形状不同：

- x86 侧：**多厂商集成** + 关键部件单一来源
- Apple 侧：**单厂商全集成** + 全部单一来源

**而 Apple 在"集成边界"这一维度上明显更少（0 vs 3–4），这恰恰是本架构的核心优势所在。**

**⇒ 结论 5：残余的真实风险有两条（v1.1 由一条改为两条）——**
**①无可替代来源（采购弹性小），这是规模化采购阶段的商务问题，不是技术问题，且两边都存在；
②近期只有一家的软件栈是就绪的（§5.3），这条是我们要如实承认的。**

### 5.3 ★ 关键证据：硬件已经商品化，**可用的软件栈没有**（v1.1 更正）

> **⚠️ 这一节是对 v1.0 的自我更正。** v1.0 的原文是：
> *"这三点在 2026 年的市场上至少有四家提供 ⇒ 我们不是押在 Apple 上，是押在一个正在商品化的能力上。"*
> **那句话把两个不同的判据合并成了一个**：**硬件能力存在**，与**软件栈可用**。
> 只查前者，答案是"四家都有"；把后者加进来逐家查证厂商自己的文档，**答案是"只有一家"**。

#### 5.3.1 能力类别必须拆成两半

| 半 | 判据 | 查证方式 | v1.0 查了吗 |
|---|---|---|---|
| **硬件半** | 这颗 SoC 里有没有统一内存 / 可编程 GPU / 集成 NPU | 看规格表 | ✅ 查了 |
| **软件半** | **在上面跑我们的负载，需要的那套栈在 Linux 上成不成熟** | 看厂商自己的安装文档与版本历史 | ❌ **没查** |

**"NPU 有多少 TOPS"是必要不充分条件。** 一颗 45 TOPS 的 NPU 如果
①在 Linux 上没有驱动、②只能跑固定推理图而不能编程、③**连模型都不能在 Linux 上编译**，
那么它对我们的价值近似于零——**而这三条在 2026 年至少有两家 x86 厂商各中了一条以上。**

#### 5.3.2 第四列：NPU 在 Linux 上有没有可用的软件栈

**下表最后一列是 v1.1 新增的，全部引厂商自己的文档。**

| 厂商 | 部件 | 统一内存 | NPU 算力 | **NPU 在 Linux 上的软件栈** |
|---|---|---|---|---|
| **Apple** | M4 Pro / M4 Max / M3 Ultra | ✅ 至 128–256 GB | ANE 38 TOPS | ✅ **一个 API（Core ML）同时覆盖 ANE/GPU/CPU**，本仓库已实测（§5.3.4） |
| **Intel** | Core Ultra（Meteor/Arrow/Lunar/Panther/Wildcat Lake） | ✅ LPDDR5X 共享 | 未核实 | ✅ **x86 里最成熟的一家**：`linux-npu-driver` **1.38.0 官方认证 Ubuntu 26.04 LTS、内核 7.0**，带 OpenVINO 2026.3.1（[来源](https://www.linuxcompatible.org/story/intel-npu-driver-1380-adds-ubuntu-2604-lts-support-and-major-kernel-70-upgrade/)）【官方】 |
| **AMD** | Ryzen AI（Strix / Strix Halo / Krackan） | ✅ 至 128 GB | XDNA 2 ~50 TOPS | ⚠️ **有，但缺口明确**：Linux 只支持 STX/KRK，且**只支持 NPU-only 流**——**iGPU 执行在 Linux 上不可用**（GPU 走 DirectML = Windows 独有）；**Linux 上不能生成模型，必须在 Windows 上编译**（[来源](https://ryzenai.docs.amd.com/en/latest/linux.html)、[发行说明](https://ryzenai.docs.amd.com/en/latest/relnotes.html)）【官方】 |
| **Qualcomm** | Snapdragon X Elite | ✅ | Hexagon ~45 TOPS | ❌ **最不成熟**：X1E 的 Linux 支持不完整到**整机项目被取消**；X2 才刚出 Early Developer Preview，量产就绪排在 2026-11，且**明确不承诺任何发行版**（见 §5.3.3）【官方】 |
| **NVIDIA** | GB10（DGX Spark） | ⚠️ **CPU–GPU 相干统一内存**（NVLink-C2C）【待核实：是否构成 §2.4 意义上的"单一地址空间、路由零拷贝"】 | —（GPU 承担） | ✅ CUDA 成熟，但**没有 NPU**；且是离散设备语义（§2.3 的 PCIe 天花板） |

**⇒ 硬件半成立（五家都有），软件半不成立（只有 Apple 一家"三引擎 + Linux 上可编程"齐备）。**

> **标记说明（按本文分栏约定）**：**软件栈列**逐行带厂商来源链接【官方】；
> **统一内存列**为通用架构事实（这五家的 GPU/NPU 都没有独立显存，与 CPU 共用同一内存控制器与
> 同一物理 DRAM），NVIDIA GB10 是唯一需另行核实的一行；
> **NPU 算力列**为厂商公布值【官方】。Intel 一行的"未核实"指的是其 NPU 的**可编程性边界**，
> 见 §8.3。

#### 5.3.3 为什么说它是"软件时滞"而不是"结构性壁垒"

**三条一手证据，全部是厂商自己的时间线：**

| # | 证据 | 说明了什么 |
|---|---|---|
| 1 | **AMD** 的 XDNA NPU 从 Phoenix（Ryzen 7040）**2023 年就出货**，而 **Linux 安装包直到 Ryzen AI 1.7.1 才出现**（该版发行说明："Ryzen AI installer is also available on Linux platform"）；到 1.8.0（文档更新 2026-09-21）**仍然**是 NPU-only 流、**模型生成仍不支持 Linux**；Phoenix/Hawk Point 一代的 NPU 在 Linux 上**完全不受支持** | 硬件领先软件**以年计**【推算】（1.7.1 的具体日期未核实），且旧平台会被直接放弃 |
| 2 | **Qualcomm**：X1E 与 Linaro 合作上游化（2024），结果 **TUXEDO 于 2025-11-21 宣布搁置整机项目**——理由清单里包含电池续航未达标、**无 BIOS 更新途径**、无风扇控制、KVM 虚拟化不可预期、USB4 速率不可用（[来源](https://www.tuxedocomputers.com/en/Discontinuation-of-ARM-notebooks-with-Snapdragon-X-Elite-SoC)） | Linux 支持**不止是 NPU 驱动**，是整个平台使能 |
| 3 | **Qualcomm X2**：Linux 首发为 **Early Developer Preview**（2026-09-25），分三阶段，**量产就绪排在 2026-11**；官方明说**不针对任何发行版**、终端用户的开箱体验"以后再说"；**Canonical 的"完全优化、认证的 Ubuntu 镜像"目标是 2027**（[来源](https://www.cnx-software.com/2026/09/25/qualcomm-releases-linux-developer-preview-snapdragon-x2/)） | 就算软件在追，追的是**几年**的量级，不是几个月 |

**⇒ 但同样是这张表给出了"会关掉"的证据：Intel 已经关掉了。**
`linux-npu-driver` 有官方 Ubuntu 认证、有 OpenVINO、有跨五代硅片的测试通过率——
**这证明"x86 上三引擎可落"不是物理不可能，只是还没有第二个厂商做完。**
所以正确的表述是：**能力类别的软件半正在被补齐，但今天还没补齐。**

#### 5.3.4 ★ 对照证据：为什么"软件半"才是真壁垒 —— Core ML 的引擎无关性

**这一节用的是本仓库自己的一手证据，不是外部资料。**

代码里只有一行决定 AI PHY 落在哪个引擎上（`ocudu_coreml_nn_engine.mm:143`）：

```objc
cfg.computeUnits = MLComputeUnitsAll; // ANE > GPU > CPU as the runtime sees fit
```

**同一个 `.mlmodelc`，不改模型、不重量化、不重训练**——只改这一行，
就能把同一次推理落到 ANE / GPU / CPU 任意一个上。而这三个引擎在**我们自己的负载**上，
可用性完全不同（【实测】，详见 `doc_chinese/ai_ce/AI_CE_20MHz_plan.md`）：

| 引擎 | 我们自己的读数 | 判定 |
|---|---|---|
| **ANE**（HELENA 106 PRB，fp32） | **p50 = 191 µs**（空闲机下限） | ✅ **可用**——源文档据此判定落在 slot 预算内 |
| **GPU**（metal_mmse，同类功能块） | 首调 2.57 ms（无预热）；稳态 ~570–620 µs/授权 | ❌ **实机不可用**——attach 时序窗口爆掉 |
| **CPU**（classical CE） | 25 µs | ✅ 可用，但这不是 AI |

**而下面两条工程代价，是"能落到 ANE 上"之后才可能被发现的**——
它们不在任何规格表里，也不在任何厂商的 TOPS 数字里：

| 现象 | 数值 | 代码位置 |
|---|---|---|
| 在**新线程**上首次 Core ML 推理的前置初始化 | ~12 ms（表现为"首个全带宽 slot 尖峰"） | `ocudu_coreml_nn_engine.mm:30-34` |
| 编译后的 ANE 程序**空闲 ~15–20 s 后被驱逐**，下次推理需重编译 | ~13.6 ms ⇒ 必须每 2 s 保活一次 | `ocudu_coreml_nn_engine.mm:47-51` |

**⇒ 三条推论：**

1. **TOPS 与"这条路能不能跑"之间隔着一整套软件栈**，而栈里藏着
   **引擎专属的成本项**（线程初始化、程序驱逐、编译期、算子覆盖）。
   这些成本只能在"能把负载真的放上去"之后才被测量到。
2. **Core ML 的隐藏价值不是性能，是它把"选哪个引擎"变成了一个可实验的自由度。**
   如果没有这个抽象，**ANE 是否可用根本不会被发现**——因为要验证它，
   得有人先愿意写第三套后端。**我们之所以知道 ANE 在 191 µs 上可用，
   是因为尝试它的边际成本是一行代码，不是三个月。**
3. **这恰恰就是 x86 侧真正的缺口所在。** AMD/Qualcomm 缺的不是硬件，
   是"**一个 API 覆盖三引擎 + 在 Linux 上能自己编译模型**"这一层。
   **Intel + OpenVINO 已经具备这一层**——所以"必须在 Apple 上"是**今天的**事实，
   不是**技术上的必然**。

#### 5.3.5 修正后的表述

**替换 §5.2 结论 5，并替换 §5.4 的"采购风险由市场驱动解决"那条的强度：**

> **残余的真实风险有两条，而不是一条：**
> ① **无可替代来源**（采购弹性小）——两边共有，规模化阶段的商务问题；
> ② **近期只有一家的软件栈是就绪的**——**这条是我们要如实承认的**，
>    它意味着**短期内"建在 Apple 上"不是偏好，而是唯一能跑的形态**。
>
> **但两条都不影响架构结论**：抽象做在"车道 / 读者属地"层而不是"device backend"层
> （`metal_vs_cuda_architecture.md` §7），
> 所以**软件时滞一旦关掉，数据流论证可以直接搬过去**——
> 而 Intel 已经证明它会关掉。

**⚠️ 同时保留 v1.0 那条正确的一半**：能力类别的**硬件半**确实在商品化，
所以这不是一个"押错厂商"的赌注，而是一个"等软件追上"的时间成本。
**混淆"时间成本"与"结构风险"才是真正的错误**——v1.0 犯的就是这个错。

### 5.4 商务逻辑：用消费级硬件做电信

**把上面两条合起来，得到的不是"我们只能选 Apple"，而是一条明确的商务路线：**

| 命题 | 论据 |
|---|---|
| **用消费级硬件解决电信问题** | 消费级 SoC 的出货量比电信级专用板卡高几个数量级 → 供应链更深、更便宜、更不容易被单一产品线放弃 |
| **采购风险由市场驱动解决** | 我们依赖的是**能力类别**的**硬件半**（§5.3.2 五家已提供），不是某一家。硬件一旦被多家提供，采购风险自然下降——**但软件半还没跟上（§5.3），所以这条是中期而非近期的论据** |
| **我们做的事**：把一个通常用于边缘市场的部件，**用在了一个不同的地方** | 这是**应用创新**，不是硬件创新——也正是它容易复制、因而容易被市场跟进的原因 |

**⇒ 这条路线对"单厂商"的正确表述是：**
> **近期必须建在 Apple 上（因为它是唯一"三引擎 + Linux 上可编程"都就绪的形态，§5.3.2），
> 但架构不建在 Apple 上（因为抽象做在车道层）。**
> **前者是时间成本，后者是设计纪律。混淆这两者才是真正的风险。**
> **v1.1 补充**：硬件成熟 ≠ 软件就绪。x86 侧的硬件早就在货架上（AMD 的 NPU 2023 年就出货了），
> 落后的是软件栈，量级是**年**（§5.3.3）。**所以我们等的不是芯片，是栈。**

## 6. 平台约束不是弱项（并且可以量化其"加分项"）

### 6.1 三个平台级硬事实（本仓库蓝图 §0.2）

| # | 约束 | 我们的应对 |
|---|---|---|
| 1 | **ICB 在本平台被阻断**（darwin 25 / AGX G16X 实测） | CPU 编码 + 单命令缓冲 + GPU 内部 MTLEvent 依赖 |
| 2 | **Metal MSL 无跨 threadgroup 软件栅栏** | MTLEvent / MTLFence / 命令缓冲内顺序，或单 TG 持久 kernel |
| 3 | **Apple Silicon 无 CPU 亲和性**（`set_thread_affinity` 是 no-op） | QoS 分类 + Mach time constraint + GPU 卸载 |

### 6.2 目标已在约束下达成

蓝图 §0.2 原文：ICB 被阻断**并不阻止**目标，只是选择了一条不同的实现路径——
"第三阶段**不得把第一版全链管线押在 ICB 上**"，而 ICB "保留为平台修复后的演进项"。

**⇒ 目标（每槽 1 次提交、2 次数据穿越）是在约束下已达成的。约束没有阻止目标。**

### 6.3 "如果没有这个约束"能加多少分——可量化

ICB 的作用是**让 GPU 用预录制的命令重新编码命令缓冲，省掉 CPU 编码开销**。
而我们当前的 CPU 编码开销是可测的：

| 来源 | 本仓库实测 |
|---|---|
| LDPC 分层解码 dispatch 数 | **290 次/解码** × 约 **1.9 µs** → **≈ 550 µs CPU 编码**【实测】 |
| CE 主机耗时段 | `mean total=334.8 µs`，其中 GPU 只忙 130.9 → **≈ 204 µs/跳在 CPU 侧**【实测】 |

**⇒ 若 ICB 可用，这几百微秒量级的 CPU 编码开销正是它要消灭的对象。
最新提交中"72% 的端到端延迟根本不在车道内"，绝大部分落在这里。**

**⇒ 所以 ICB 是实实在在的加分项，不是安慰性说法。**

### 6.3.1 补一条新的实测证据：目标确实在约束下推进（5.9.94）

**"目标在约束下已达成"这句话，现在有了更新的空中证据：**

| 观测 | 值 | 来源 |
|---|---|---|
| `cbs/lane`（每车道命令缓冲数） | **2.70 → 2.00** | 【实测】5.9.94 空中 A/B |
| 槽级跨度 | **优于旧的 prefix 腿** | 【实测】5.9.94 |
| 离线回归门 | **175/175（`-L phy`）** | 【实测】5.9.120 审计 A3 |

**注意这条证据伴随一次机制更换**：旧的"prefix 形式"（K0-d 骑在引擎命令缓冲上）**有缺陷**
（5.9.87–5.9.88 隔离出"prefix 的 A 从未到达 K1"），现已被**带栅栏的相关构建**
（`flush_correlations_fenced()`，每跳一条命令缓冲）取代，旧形式降为反向臂 `OCUDU_CE_CORR_FENCED=0`。
详见 `metal_vs_cuda_architecture.md` §1.9。

**⇒ 意义**：在 ICB 不可用、无跨 TG 栅栏、无 CPU 亲和这三个约束下，
**"每跳一次提交"这个目标是被实测确认在推进的**，不是纸面推演。
这直接支撑 §6.1 的判断——**约束没有阻止目标**。

### 6.4 反向收益（比加分项更有价值）

**在不许用 ICB 的约束下被迫采用的方案（CPU 编码 + 单命令缓冲 + MTLEvent 依赖），是平台可移植的**
——CUDA 上同样成立（一条命令缓冲 + event 排序）。

**如果当初押在 ICB 上，我们会得到一个 Apple 专属、无法移植的调度层。**

**同理：**
- 无跨 TG 软件栅栏 → 逼出 **MTLEvent 显式排序**（比依赖隐式栅栏语义**更清晰、更可验证**）
- 无 CPU 亲和性 → 逼出 **QoS 分类 + Mach time constraint**（**声明式**，比手工绑核更可移植）

**⇒ 结论 6：三个"约束"里至少两个倒逼出了更好的设计。这不是弱项，是被约束塑造出的架构纪律。**

## 8. 诚实清单：尚未解决与尚未证明的

### 8.1 尚未证明（需要实测）

| 项 | 现状 |
|---|---|
| **eMBB 吞吐（GPU 路径）** | 唯一真正未定的性能变量。当前 GPU LDPC 仍慢于自家 CPU；融合车道的端到端预算尚未收敛。<br>**⚠️ 项目自己的里程碑审计（5.9.120 轴 A4）独立确认了这个缺口：132 条腿证据里"没有一条是重上行腿"**，即"重上行负载下车道表现如何"在仓库内尚无有效腿 |
| **Apple GPU 的 FP32 TFLOPS** | 本文件全部为【推算】，**必须实测**后才能引用 |
| **混合流量下的尾部时延** | 理论上我们的优势最大（无 PCIe 队列），但**没有测量** |
| **整机功耗（含 SDR/FPGA/RF）** | 本文件多处标"未核实" |
| **100 MHz / 4×4 的容量** | 当前实链跑通的是 20 MHz / 5 MHz、1–2 层；100 MHz 是数量级外推 |
| **"恰好两次穿越"这一半目标** | ⚠️ 审计 A2：旧差距表逐行消失，但目标里"**恰好两次穿越**"这半句**没有任何计数器**。所以"零穿越"可测（契约第 5 条），"恰好两次"目前只是设计意图 |

### 8.1.1 一条被排除的嫌疑（对 eMBB 结论是利好）

**5.9.106–5.9.109 的链路自适应（LA）工作线把 GPU 车道从 n1 小区的上行问题里排除了：**

| 观测 | 结论 |
|---|---|
| 空 buffer 时调度器给 **5–8 PRB @ 256QAM**；满 buffer 时给 **25 PRB @ MCS0** | 制约是**链路上"带宽 vs 阶数"的权衡**，不是链路预算 |
| 手机全程报告 **10–15 dB 功率余量** | 不是手机功率问题 |
| PUSCH 的 sinr 读数随调制阶数单调上升（QPSK 5.3 vs 256QAM 24.2，同腿内） | 跨腿比中位数是在比**MCS 混合**，此前的比较方法本身有误 |

**⇒ 意义**：n1 的上行表现**不是**车道的锅，也不是链路预算或手机的锅。
**它把"eMBB 吞吐未定"的候选解释从"车道不行"挪到了"调度器的 LA 策略"**——
这对本文件的结论是**利好**：车道尚未被证伪，只是尚未被证明。

**但注意**：这条**不解决**§8.1 第一行的缺口。**重上行腿仍然不存在**，所以
"我们最可能赢的那个场景（eMBB 大包 / 混合流量）"依旧是**未测量**状态。

### 8.2 尚未解决（工程项）

| 项 | 问题 |
|---|---|
| **部署环境等级** | Mac Studio/mini 工作温度 0–35°C、无 IP 等级、无 ECC、消费级保修；而目标场景是路边机柜（−20~50°C）。**需要加固方案及其成本** |
| **采购弹性** | 无第二来源。规模化阶段的商务问题 |
| **x86 侧 NPU 软件栈的成熟度**（v1.1 新增） | 这是 §5.3 的更正的工程面。要真正把车道搬到 x86，缺的不是硬件而是三件事：①**一个 API 覆盖 NPU/GPU/CPU**（Core ML 的对应物）；②**在 Linux 上能自己编译/量化模型**（AMD 今天必须回到 Windows 做这一步）；③**旧平台不会被放弃**（Phoenix/Hawk Point 的 NPU 在 Linux 上完全不受支持）。**Intel + OpenVINO 是目前唯一三者都接近满足的 x86 组合，需要实测验证而不是采信文档** |
| **两处需要统一的口径** | ①"ANE never contending with CPU/GPU" 与本仓库风险登记 R8（"ANE 与 GPU 争抢内存带宽"）矛盾；②"LDPC throughput comparable to accelerator" 与本仓库结论（"GPU decode latency trails the CPU at every size; no crossover exists"）矛盾。**凡对外材料与此处不一致，以本仓库结论为准** |

### 8.3 尚未核实（v1.1 新增，**不得进入对外材料**）

| 项 | 现状 |
|---|---|
| Apple GPU FP32 TFLOPS | 全文件为【推算】，须实测（同 §8.1） |
| Strix Halo 在 Linux 上 NPU **之外**的可用性（ROCm / iGPU 计算） | 未查到一手出处。AMD 的 Linux 文档只说 NPU-only 流，**没有说 iGPU 计算在 Linux 上能不能用**——而这正是"统一内存 + 可编程 GPU"两条能力在 x86 上是否同时成立的关键 |
| Snapdragon X2 的"官方 Linux 支持"具体覆盖到哪一层 | 官方只给了三阶段路线图；**NPU（Hexagon/FastRPC）是否在首阶段可用**需在真实硬件上验证 |
| Intel NPU 的**可编程性**边界 | 已知它是推理图加速器（OpenVINO 模型），**能否承载非推理型的自定义算子链未核实**——这决定了它能否替代 GPU 而不是只替代 ANE |

## 9. 决定性实验：同价位整机对整机（runbook）

**这是把"可推导"变成"可证明"的唯一路径。**

### 9.1 对照组

| | Apple 侧 | x86 侧（同价位） |
|---|---|---|
| 主机 | Mac Studio **M3 Ultra 或 M4 Max**（不再只用 M4 Pro） | 同价位 1U/mini-ITX + 对应档 Xeon/Core |
| 加速器 | （同封装） | L4 或 RTX 4000 Ada 档（**不是 H100**） |
| 网络 | TB5 | 10GbE / 25GbE |
| **CPU 参照机型** | M3 Ultra / M4 Max | **必须是服务器级 Xeon，不能再用 NUC**（否则 §4.1 的 4.1× 不可比） |

### 9.2 变量控制

- 同一份 OCUDU 代码、同一 commit
- **至少两组小区配置**：20 MHz/30 kHz（已跑通）与 100 MHz（目标）
- **三种载荷分别测，再叠加**：
  1. **URLLC 小包** → 走 **CPU 路径**
  2. **eMBB 大包** → 走 **GPU 路径**
  3. **★ 混合流量（主判据）** → lookaside 最痛处（小包被大队列堵住）；也是我们最可能赢的地方

> **★ 为什么第 3 项是主判据而不是"三项之一"（见 §1.4）**：
> **单一业务都能被单一引擎覆盖，只有混合场景才需要异构。**
> 只有 URLLC 时，CPU 路径就够，异构没有价值；只有 eMBB 时，GPU 就够，CPU 路径是闲置的。
> **V2X 的真实需求是两者同时存在**——这才是本架构与同价位 x86+GPU 真正分岔的场景，
> 也是"路由边际成本为零"（§2.4）唯一能被观测到的地方。
> **报告结论时，前两项作为分解，第 3 项作为裁决。**

- 两侧 BOM 都要含外壳 / 电源 / 散热

### 9.3 指标

| # | 指标 | 说明 |
|---|---|---|
| 1 | **URLLC 时延 p50/p99** | CPU 路径 —— 节点对时延敏感业务的真实指标 |
| 2 | **eMBB 吞吐 Mbps/节点** | GPU 路径 |
| 3 | **混合流量尾部时延** | 无 PCIe 队列优势的验证点 |
| 4 | **整机墙插功率** | 含 SDR/FPGA/RF，不只主机 |
| 5 | **每节点 BOM** | 两侧同口径 |
| 6 | **每瓦 · 每升 · 每美元 承载小区数** | **最终采购判据** |

### 9.4 预测（供证伪）

| 轴 | 预测 |
|---|---|
| 功率 / 体积 / 集成度 | Apple **结构性胜出**，差距是数量级 |
| URLLC 时延（CPU 对 CPU） | Apple **占优**（单核排序 + 无卸载税） |
| eMBB 吞吐 | **未定**，取决于 GPU 链优化进度 |

## 10. 结论

0. **评价标准是给用户创造的价值（E2E performance，V2X 这类 URLLC/eMBB 并存的边缘场景），
   不是评审者的认可。** "能否合并进 upstream"只作为降低长期维护成本的手段被权衡（§1.4）。

1. **正确的比较轴**是**整机 × 同价位 × 功率包线内的容量**，不是"谁的 GPU 快"；
   时延与吞吐必须**分别归到各自路径**，而**混合流量下的表现是主判据**——
   单一业务都能被单一引擎覆盖，**只有混合场景才需要异构**（§1.4、§9.2）。

2. **绑定约束不是带宽**（需求 ~3.4 GB/s，裕度 >10×），而是**"同一份数据被搬几次"**：
   - lookaside 在 ~4 个 100 MHz 小区就打满 PCIe 4.0（可独立算得）；
   - NVIDIA inline 与我们在"跨越次数"上对等（输入 1 次、中间态 0 次）；
   - **真正的判别性优势是"路由边际成本为零"**——离散显存下路由 = 拷贝，UMA 下数据不动、只换谁来看。
     **这是 x86+GPU 无法复制的，也是整个异构设计得以成立的前提。**

3. **同价位算力大致持平**，优势在内存带宽、统一内存容量、集成度与小包时延；
   **"算力胜出 N 倍"这类主张不要提**——换一个对标部件就没了。

4. **"平台约束"应从劣势清单删除**（目标已达成，且倒逼出可移植设计，放宽后是加分项）。
   **"单厂商风险"要分两半说（v1.1 更正）**：
   - **硬件半**：我们依赖的是**能力类别**（统一内存 + 可编程 GPU + 集成 NPU），
     这一类别**已有五家提供，其中包含 x86 成员**（§5.3.2）。⇒ **不是押在 Apple 上，是押在一个正在商品化的能力上。**
   - **软件半**：但把"软件栈可用"也当作判据之后，**只有 Apple 一家在 Linux 上三引擎齐备**：
     AMD 在 Linux 上只支持 NPU-only 流、**模型必须回 Windows 编译**；Qualcomm 的 X1E 支持不完整到
     整机项目被取消、X2 才刚出开发者预览；Intel 是 x86 里唯一接近的一家（§5.3.2/§5.3.3）。
     **⇒ 近期"建在 Apple 上"不是偏好，是唯一能跑的形态。这条要如实承认，不要用"四家都有"糊过去。**
   - **但它是软件时滞，不是结构性壁垒**：硬件早就在货架上（AMD 的 NPU 2023 年就出货），
     落后的是栈，量级是**年**；而且**Intel 已经证明它会关掉**。
   - **⇒ 因此我们仍然欢迎 x86 + NPU 提供同等能力**——它消除单厂商问题、扩大市场，
     并验证"能力类别"这个判断。

5. **商务逻辑（§5.4）**：用消费级硬件做电信——消费级 SoC 的出货量比电信级板卡高几个数量级，
   供应链更深更便宜；**我们做的事是把一个通常用于边缘市场的部件用在了一个不同的地方**，
   属于应用创新；采购风险由市场驱动解决，而不是由我们独自承担。
   **⚠️ 但这条是中期论据，不是近期论据**（软件半还没跟上，见第 4 条）。

6. **必须承认的开放项**：eMBB 吞吐未定（项目自己的审计也确认"没有一条重上行腿"）、
   Apple GPU TFLOPS 未实测、部署环境等级未解决、**x86 侧 NPU 软件栈的成熟度**（§8.2）、
   以及 §8.3 的四项【待核实】。**能力类别的"硬件商品化" ≠ "实现可移植"**——
   软件栈每家不同，**而且差的正是"一个 API 覆盖三引擎"这一层**，
   所以抽象必须做在"车道/属地"层而不是"device backend"层。

7. **把可推导变成可证明的唯一路径**是 §9 那场实验，**且以混合流量为裁决项**。
   **在它跑完之前，"更有竞争力"是架构论证，不是测量结论。**
