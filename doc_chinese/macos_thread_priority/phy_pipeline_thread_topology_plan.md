> 申报"，并给了一个三线程的例子（FFT / Metal commit / LLR 之后），要求仔细规划。

## 0. 目标与不变量

**目标（用户 2026-10-01 定调，本规划继承）**：让同一次运行里"同一个任务花同样的时间"，即把
`max` 压下来、`min` 不抬升；量化指标是四条尾部载体 + 三条登记率（§0bis.4）。

**本规划要改变的东西**：不是优先级，不是预算数值，而是**线程的组织方式**——
把今天"事件驱动 + 工作窃取池"的 UL 数据面，改成**若干条自定时的周期线程**，
每条只负责 pipeline 里一段**有界**的工作，并在**电台时钟**上申报自己的时间片。

**不变量（任何一步都必须满足）**

1. **Linux / Ubuntu 行为一字不变**（§7）；
2. **关着旋钮时逐字节不变**（两把钥匙：编译开关 + env）；
3. **申报形状合法**：`computation ≤ constraint < period`。反例已实测有害（开发文档 §10.31：
   `constraint < computation` 时 p50 793 / max 7277 µs）；
4. **不让路就饿死别人**：任何周期线程在自己的窗口外**必须睡**（p220/p221 的教训，§5.1）。
5. **每条线程的时间片必须来自实测**，不许拍（§4）。

### 1.1 几何与到达形态

| 接收策略 | **每 OFDM 符号一块**（`OCUDU_UL_RX_SYMBOLS=1`） | `[ul_rx_policy] blocks of 1 OFDM symbol` |

| 实测 lane 率 | **539/s**（≈0.9 lane/UL slot，与 `ul_ratio=0.30` 一致） | `[ul_gpu_lane] lanes=359310` / 666.6 s |

## 2. 为什么是"周期化"，而不是继续调优先级

三条实测结论把调度这条线封了口（开发文档 §10.57），同时把方向指向这里：

1. **优先级/档位/时间约束都不降尾部**（P4 七对腿、FIFO 一对腿），因为尾部的停顿是 **①挂起 / ②驱动阻塞**，
   而**看门狗的 `cpu_stolen` 八条腿全为 0**——"可运行却没被调度"这一类没有发生；
2. **FIFO 反而有害**：不让路 ⇒ 饿死同进程的 USB 传输与停机路径（丢 702 万样本、上行 −25%）；
3. **微基准的巨大收益不转移**（TC 540×、FIFO 19×），因为微基准量的是**睡眠线程的唤醒延迟**，
   而池线程是**事件驱动**的：它**不知道"什么时候必须动"**，只knows"活来了"。

⇒ 参考框架赢在**结构**：它的线程**知道自己该在什么绝对时刻动**（TX 由 `target_tx_time` 反推；
RX 阻塞在 `recv()` 且硬件时间戳给它刚性网格）。**周期化改造要补的正是这一条**：
给每个阶段一个**来自电台时钟的绝对时刻**，让线程"睡到 deadline − lead 再自旋"。

## 3. 目标拓扑（5 条线程，其中 2 条已存在）

```
   ┌──────────── 电台（B200，GPSDO）＝唯一时间基准 ────────────┐
   │  slot 500 µs / 符号 35.7 µs / TDD 5 ms（3 个 UL slot）   │
   └──────────────────────────────────────────────────────────┘
        │ 符号到达                        ▲ 绝对时刻发射
        ▼                                 │
  ┌───────────┐   symbol ring   ┌──────────────┐  freq-domain  ┌──────────────┐
  │ T_rx      │ ──────────────▶ │ T_fe (DFT)   │ ────────────▶ │ T_lane       │
  │ 35.7 µs   │  (已存在:pool)  │ 35.7 µs      │  (device,     │ 500 µs       │
  │ 已存在    │                 │ 新: 只 commit│   zero-copy)  │ ce+eqd 融合  │
  └───────────┘                 └──────────────┘               └──────┬───────┘
                                                                      │ LLR(device)
                                                                      ▼
                                                              ┌──────────────┐
                                                              │ T_llr        │
                                                              │ 500 µs: LDPC │
                                                              │ +TB+FAPI/MAC │
                                                              └──────────────┘
  ┌───────────┐
  │ T_tx      │  已存在：自旋到时间戳追上（不做改动）
  └───────────┘
```

### T_rx（已存在，`lower_phy_rx#0`）— 不改结构

* **触发**：电台驱动（阻塞在 `receiver.receive()`，每符号一次，28 000/s）；
* **职责**：把 IQ 搬进池（32 个整 slot buffer，`free_min=27`，从不干涸）；
* **保持原样**。**P5.1 已证"池子等待"不是瓶颈**（§10.54），不要在这里再花腿。

### T_fe（新）— 前端口：符号到达 → 提交 DFT

* **周期**：**35.7 µs**（符号节拍），相位 = 电台符号边界；
* **computation 的来源**：**今天没量到**。`[phy_pipeline] dft radio inputs` 在本模式下是 `0 transforms`
  （融合路径不经过那两条提交路线），`[metal_stats] gpu busy (front_end): commits=0`，`[ul_dft_wait]` 无样本
  ⇒ **这条线程的预算必须先补仪器**（§4.1）。用户估计"14 个符号的 FFT ≈ 40 µs CPU"——**待验证**；
* **职责边界（用户的原则）**：CPU 到此为止 = "申请时间片 → 完成 commit"；**GPU kernel 花多少时间不进这个账**。

### T_lane（新）— 信道估计 + 均衡/解调（融合 lane）

* **周期**：**500 µs**（slot 节拍），相位 = UL slot 边界；TDD 下每 5 ms 只有 3 个 slot 有活；
* **职责**：提交 `ce_weights` + `merged_hop`（今天池线程做的），把 LLR 留在设备上；
* **computation 的来源**：**已有实测**——`host: stage entry → lane commit` 中位 **101.5 µs**、
  p95 195.5、**p99 225.5**、max 862.9 ⇒ 申报 **computation = 300 µs**（覆盖 p99 并留 33% 余量）；
  `constraint = 400 µs`、`period = 500 µs`（形状合法：300 ≤ 400 < 500）；
* **交接**：`merged_hop` 的设备侧 exec p50 = **449.8 µs**，这是**设备时间**，CPU 提交完就撒手。

> ★★ **这条预算有一个前提，必须写在旁边**：101.5 µs 是**融合 lane 自己那一段**的 host 参与，
> 也就是"提交这一段的线程"的切片。而今天池的总 CPU 是 **≈800 µs/lane**（§1.3），
> 也就是**另外 ~700 µs 目前没有归属**——它可能是 t2f 的 host 侧（每 slot 14 次 DFT 提交）、
> LLR 取回/demap、LDPC、FAPI/MAC 中的任何一部分。
> **只有当 P6.0 证明那 ~700 µs 分别属于 T_fe / T_llr（而不是也压在 T_lane 上）时，300 µs 才成立。**
> 若 P6.0 显示某一段自己就 > 它的 period，**那一段就不能是"一条线程"**，而要拆成 N 条
> （例如 TDD 的 3 个连续 UL slot ⇒ 3 条同相位错开的线程，各管一个 slot）。
> **这条规则(§4.3)是本规划里最容易搞错、后果最大的一条。**

### T_llr（新）— LLR 之后：LDPC → TB → FAPI/MAC

* **周期**：**500 µs**，同样的 UL slot 相位；
* **职责**：提交 LDPC、取回 TB、CRC、组装 FAPI、交给 MAC；
* **computation 的来源**：`[ul_ldpc_decode]` 中位 60 µs / p95 106 µs 是 **WALL**（含设备），
  所以**同样需要先补 CPU 仪器**（§4.1）。用户估计"也应小于 500 µs"——**待验证**；
  若实测 p99.9 > 400 µs，则这一步**必须先拆分或继续 offload**，不能硬申报（§6 的分步条件）。

### T_tx（已存在，`lower_phy_tx#0`）— 不动

已经是参考框架的形状（`yield` 自旋到时间戳追上，注释写在 `macos_compat.cpp:817`）。

## 4. 参数从哪里来（**禁止拍脑袋**）

### 4.1 第一步必须先补的仪器：**每阶段 CPU 归属**（P6.0）

今天的缺口，一句话：**我们知道每个阶段的 WALL，但不知道每个阶段的 CPU**。
于是"池线程 43% 一个核都花在哪"无法回答，而这正是"离'CPU 上只剩 commit'还有多远"的唯一读数。

**设计**（在既有地标上加，不加新地标）：

| 地标 | 位置 | 表示 |
|---|---|---|
| `record_start` | `ul_process()` | slot 开始 |
| `record_t2f_end` | 整 slot 频域就绪 | T_fe 的产出 |
| `record_ce_end` | 数据符号估计就绪 | T_lane 的第一段结束 |
| `record_ldpc_start` | LLR 就绪 | T_lane 结束 / T_llr 起点 |
| `record_end_crc_ok` | TB 通过 CRC | T_llr 的产出 |
| `record_fapi_mac_end` | 交给 MAC | 交付 |

在每个地标读一次**本线程 CPU**（`this_thread_cpu_ns()`，一次 Mach 调用），
**仅当上一条地标与本条在同一线程、同一 slot** 时记一个 CPU 增量，按阶段归入直方图；
不连续就**计数并跳过**（`not_contiguous`），在报告里打印连续率——**不许把跨线程的增量当成一个阶段的 CPU**。

**内建自检（这条比数字本身重要）**：各阶段 CPU 之和，必须与
`[ul_thread_cpu]` 的池总 CPU（43% 一个核那一行）在**同一条腿上对得上**（差 < 10%）。
对不上就说明归属漏了阶段或漏了线程，**先修仪器再谈结论**。

**反向臂**：造一个"已知 CPU 形状"的臂（例如只在一个阶段里烧 200 µs），
各阶段直方图必须只有那一个阶段动——测的是归属算术，不是时钟。

### 4.2 每条线程的申报参数表（**飞腿前**填，来源一栏不许空）

| 线程 | period | computation（来源）| constraint | phase（来源）| 保留核数占比 |
|---|---|---|---|---|
| T_fe | 35.7 µs | 待 P6.0 | 待定 | 符号边界（电台）| ? |
| T_lane | 500 µs | **300 µs**（host 参与 p99 225.5 × 1.33）| 400 µs | UL slot 边界 | 60% × 有活比例 |
| T_llr | 500 µs | 待 P6.0 | 待定 | UL slot 边界 | ? |

★ **"保留核数占比"一列必须先算**：`Σ computation/period` 是所有线程的**预留总量**，
必须给**非我们控制的线程**（UHD 的 USB 传输线程、电台驱动、内核）留出余量。
今天的池只需要 **43% 一个核**，而 3 条周期线程若按上表预留，光 T_lane 就是 **60%**；
**总预留要压在 ~1.5 核以内**（14 核机器），并在腿上核对 `[ul_rx] rx_overflows/gaps` 是否为 0——
p221 的教训就是"预留挤掉了数据源"。

### 4.3 ★ 一条线程还是 N 条：由 P6.0 的读数决定，不由偏好决定

判据只有一条，而且它是算术：

```
若 某阶段的 CPU p99.9 ≤ period × 0.6   ⇒ 该阶段可以用 1 条线程（留 40% 余量）
若 超过                                ⇒ 该阶段拆成 N 条同相位错开的线程（N = ceil(p99.9 / (period×0.6))）
```

并且**每拆一条就把总预留加一份**（§4.2 的上限仍然适用）。
TDD 的 3 个连续 UL slot 是天然的拆分维度：3 条同周期、相位各偏 500 µs 的线程，
每条只需承担一个 slot 的活。

## 5. 风险清单与反向臂（每条都来自我们自己的实测）

### 5.1 ★ 不让路 ⇒ 饿死数据源（p220/p221，已实测）

FIFO 臂：看门狗唤醒线程被饿 **100 ms**（对照 0.93 ms）、`runnable>0` 只在臂腿出现（6/16）、
电台 **3 次 overflow**、丢 **7 025 564** 个样本、上行 −25%、`gaps=3`。
**⇒ 本规划的硬约束**：周期线程在自己的 `computation` 用完后**必须回睡**；
`computation < period` **不是建议**；并在腿上把 `gaps / rx_overflows / dl AT/BELOW 0` 当**红线**。

### 5.2 有害形状：`constraint < computation`（开发文档 §10.31）

实测 p50 793 / max 7277 µs。**申报前逐条检查形状**，并让代码在解析时**拒绝**非法形状（已有）。

### 5.3 相位错位会**增加**延迟（本规划新增的风险）

周期预留是**按相位**给的。若线程的激活到达相位与预留相位错开，最坏要等
`period − computation`（T_lane 是 200 µs）**才拿到 CPU**——比今天"被唤醒"的 ~100 µs 更差。
⇒ **相位必须来自电台时钟**，并且**必须量**：用 P5.0 的节拍锚点（`OCUDU_UL_SLOT_GRID`）
按线程分别读残差（现在只有 CE 一个地标；P6.0 要把它扩到各阶段地标）。
**反向臂**：故意把相位偏 250 µs，锚点残差必须出现一个 +250 µs 的台阶。

### 5.4 超额申报是免费的（开发文档 §10.30）

实测：持续 4.6× 超申报、92% 占空仍然正常。⇒ 宁可多报（覆盖 max），不要少报；
但**总预留**仍受 §4.2 的余量约束。

### 5.5 看门狗看不见 < 1 ms 的抢占（开发文档 §10.59(3)）

它每 1 ms 采一次、阈值 100 µs ⇒ 200 µs 的抢占会被判为 "advanced"。
**而本规划的激活正好在 ~100 µs 尺度。** ⇒ 这一层的证据只能来自
`host cpu: stage entry → lane commit`（新增）与"每阶段 CPU"，
**`cpu_stolen = 0` 不能再用作"没有对象"的证据**。

### 5.6 GPU 在关键路径上（本规划新增）

`merged_hop exec p50 = 449.8 µs`（占 lane busy 的 93%）**在一个 500 µs 的 slot 里**。
CPU 侧再完美，这条 lane 的完成时刻也由设备决定 ⇒ **GPU 的排队与抢占（DL 侧同时用 GPU）
是这套周期化的上游不确定性**；规划里必须留一条"设备侧"的观测线（`[metal_stats] wait/exec` +
`[ul_gpu_lane] gap`），并在判据里把"设备占满"和"CPU 迟到"分开。

## 6. 分步落地（每步单独一条腿、单独一个提交、单独一条回滚路径）

| 步 | 内容 | 判据（飞腿前登记）| 回退条件 |
|---|---|---|---|
| **P6.0** | **仪器**：每阶段 CPU 归属 + 各阶段相位锚点 | 各阶段 CPU 之和与池总 CPU 对账（<10%）；反向臂只有一个阶段动；相位反向臂出 +250 µs 台阶 | 对不上账 ⇒ 修仪器，不飞臂 |
| **P6.1** | **一条线程**：把 **T_lane**（lane 提交）改成周期线程（500/300/400 µs，相位 = UL slot）| 该阶段 host 参与的 p95/p99 下降；`gaps=0`；`rx_overflows=0`；三条率不越界；**`[ul_sched]` 回读申报值** | 尾部任一条变差 / `gaps>0` / 体量未改善 ⇒ 撤回（保持默认关）|
| **P6.2** | **T_llr**（LLR 之后）同样周期化 | 同 P6.1 + `ldpc` 与 `ul_pipeline` 的 p95/p99 | 同 P6.1 |
| **P6.3** | **T_fe**（每符号 DFT 提交，35.7 µs）| 同 P6.1；额外看 `t2f` 的 p95/p99 与设备侧 `front_end` 忙 | 同 P6.1；**若 35.7 µs 周期下总预留超过 1.5 核 ⇒ 退回 500 µs 周期** |

## 8. 什么会**否证**这个规划（先写下来，免得事后找理由）

1. **P6.0 量出某个阶段的 CPU p99.9 > 它的 period** ⇒ 该阶段不能周期化，
   必须先拆小或继续 offload（用户的原则是"CPU 上只剩 commit"，这条读数就是说这句话有没有做到）；
2. **总预留 > 1.5 核**，或腿上出现 `gaps>0` / `rx_overflows>0` ⇒ 周期化在抢数据源的 CPU，方案要缩；
3. **相位无法对齐**（各阶段激活相对 slot 网格的相位漂移 > 50 µs，且不收敛）⇒ 周期预留的前提不成立；
4. **设备侧成为主导**（`merged_hop exec` 或其排队时间随 DL 负载增长）⇒ 瓶颈不在 CPU 调度，
   本规划只能拿到很小的一部分；
5. **体量（p95/p99）不动**，只有尾部率变好 ⇒ 与 P4/FIFO 同类，按 §5.1 的红线判断是否值得留。

## 10.2 周期取 **35.7 µs** 还是 **500 µs**：用实测决定，不用偏好

两条路都"读 IQ → FFT/提交 → 写网格"，差别在**什么时候开始**：

| | 周期 35.7 µs（每符号）| 周期 500 µs（每 slot）|
|---|---|---|
| 开始时刻 | 该符号样本一到就做 | **要等 slot 最后一个样本**（整 slot 策略的原文代价）|
| 实测对照 | `t2f 496.2 µs`、hop −25 µs（**当前默认**）| `t2f 536.0 µs`（历史策略，已被替换）|
| 激活次数 | 28 000/s | 2 000/s |
| 预留（按 CPU-vDSP 3 µs / 40 µs，取候选上界）| 10 µs / 35.7 µs = **28%** 一个核 | 60 µs / 500 µs = **12%** 一个核 |
| 实现难度 | 每符号一次 deadline 计算；暴露的只有最后一个 | 一次激活装 14 个变换；但把 40 µs 的延迟加回关键路径 |

**推荐 35.7 µs（每符号）**，理由全部是实测：① 它已经是当前默认且实测更好（−40 µs / hop −25 µs）；
② "13 个藏在到达节拍里、只有最后 1 个暴露"这条结论只有在每符号下成立；
③ 用户上一轮的原话也正是"周期就是一个 OFDM 符号的长度（～35 µs）"。
**若**总预留（§4.2 的 1.5 核上限）在每符号下不可接受，再退到 500 µs——**回退路径是现成的，因为两种粒度代码里都还在**。

## 10.3 这条线程的契约（草案；参数必须由 §10.4 的仪器填）

```cpp
// 一个 OFDM 符号的 FFT 提交线程（macOS 独占 + 默认关 + 两把钥匙）
period      = 35.7 us                 // 符号节拍（30 kHz SCS）
phase       = 电台符号边界            // 由 RX 时间戳导出，手法同 tx_subframe_uhd.cpp 的 target_tx_time
deadline    = 符号边界 + delivery_lead
computation = 待测；候选 10 us        // 见 §10.4：CPU-vDSP 路径每符号 ≈ 2.9 us + 编码开销
constraint  = 15 us                   // 形状必须 computation <= constraint < period
循环        = 睡到 (deadline − spin_margin) 再自旋 → 读该符号 IQ → (CPU FFT | encode+commit) → 写网格 → 回睡
```

* **`delivery_lead` 是可测的**：`tx_slack_note_receive()` 已经在维护"电台时间戳 ↔ 宿主时刻"的映射，
  所以"符号边界 → 样本可读"的分布**直接从既有仪器读**，不需要新接线；
* **GPU 时间不进这个账**（用户原则）：CPU 在 commit 处结束使命；
* **窗口外必须睡**（§5.1 的红线）；
* **不做**：不改数据流、不改 GPU 派发顺序、不改 FAPI/MAC 交付内容（§7 第 4 条）。

# 11. ★★★ P6.1-SLOT：**一条"每 slot 醒一次"的周期线程**（用户 2026-10-03 定稿方向；**先做这一段**）

> 用户原话要义：周期直接取 **500 µs（或 1000 µs，以 1 个 slot 为单位）**；**FFT 回到 GPU Metal kernel**
> （"我们已经完成了从 IQ samples 到 demod LLR 整个一步到底的完整链条"）；**CPU 线程每 slot 醒一次，
> 不是阻塞地等 IQ samples**；**用 `set_realtime_priority` 保证它每 500/1000 µs 的执行不被守护进程风暴干扰**
> （LTE 框架已验证 + `synchro_v*` 100 万次为参考）；**CPU 的实际执行时间只是 Metal kernel 的 encode/commit**，
> 应该远小于一个 slot。
>
> **§10（每符号版本）不是被推翻，而是被降级为后续的细粒度优化**——它省的是关键路径长度（−40 µs），
> 本节买的是**节拍的确定性**。按用户的判断，后者才是 `max` 失控的正解。

## 11.1 这条路的三个前提，**都已经在树里或已实测**

| # | 前提 | 证据 |
|---|---|---|
| 1 | **融合链路已经存在**：一次提交覆盖 DFT + 信道估计 + 均衡 + 解调 | `ocudu_metal_lane_probe.h` 的 `stage::merged_hop` 注释原文："**the whole hop (the front end's transforms that wrote the grid, the estimator, the equalization and the demapping) in ONE submission**" |
| 2 | **CPU 切片已实测，远小于一个 slot** | `host: stage entry → lane commit`：中位 **101.5 µs**、p95 195.5、p99 **225.5**、max 862.9（p220）|
| 3 | **设备侧时间已实测** | `merged_hop exec p50 = 449.8 µs`（占 lane busy 93%）；`ch_wt exec p50 = 40.8 µs` |

⇒ 用户"CPU 只是 encode/commit、应该远小于 1 slot"的判断**被实测支持**（中位 101.5 µs，占 slot 的 20%）。

## 11.2 与今天默认的**根本差别**（这是设计要点，不是参数差异）

| | 今天（事件驱动 + 工作窃取池）| 本方案（自定时 + 显式提前量）|
|---|---|---|
| 何时开始 | **数据到了才醒**（池线程被 executor 唤醒）| **按 slot 节拍醒**，与数据是否到达无关 |
| 停顿如何传播 | 一次 ~ms 级停顿把整条 pipeline 往后推（`ul_pipeline max 7707 µs`）| **停顿只影响那一 slot 的数据，不改变提交节拍** |
| 谁保证它跑 | macOS 调度器（我们无法控制，用户指出这正是 `max` 失控的来源）| **TC 预留**（微基准：2× 超订下唤醒迟到 103 → **3 µs**）|
| 数据晚到怎么办 | 线程**等着** ⇒ 节拍被拖走 | **提交或跳过，绝不等待**（见 11.3）|
| CPU 的工作量 | 池 5 条线程共 ≈**800 µs/lane** | **一条线程 ≈101.5 µs/slot**，只做 encode+commit |

## 11.3 ★ "不阻塞"要成立，**lead 必须 ≥ 1 个 slot**（本节最关键的一条）

线程在"slot 边界 + lead"醒来，就要求**它的输入在此之前已经就位**：

```
提交第 N 个 slot 的 kernel  ⇒  第 N 个 slot 的样本必须已完整到达宿主、并已就位到设备缓冲
⇒ 要么 lead ≥ 投递延迟的上界，要么提交的是"上一个 slot"的数据（pipeline 深度 +1 = +500 µs 延迟）
```

**本方案取"深度 +1 slot"**：commit 用的样本比当前 slot 早一个 slot。
* **代价**：端到端延迟 +500 µs。今天 `ul_pipeline` 中位 1377 µs（≈2.75 slot 的 pipeline 深度），
  再加一个 slot 是可承受的，而且**延迟不是本线的目标**（用户的目标是 `max`/`min` 的稳定性）；
* **收益**：**提交时刻与投递抖动解耦**——样本早到/晚到 300 µs 都不改变提交节拍；
* **这正是参考框架的同一手法**：`tx_subframe_uhd.cpp` 写死"0.5 ms 计算 + **1.0 ms USB 传输与 USRP 缓冲**"，
  把抖动预算写进架构，而不是指望调度器。

**配套规则："提交或跳过"**：线程醒来后**只做两件事之一**——
样本齐 ⇒ 提交；样本不齐 ⇒ **跳过并计数**（绝不等待、绝不提交半份数据）。
跳过计数是**一等指标**（与 `gaps` 同级），因为它直接量化"lead 够不够"。

## 11.5 为什么是 **500 µs** 而不是 1000 µs

| | 500 µs | 1000 µs |
|---|---|---|
| 预留 | 60% 一个核 | 30% |
| 每个 command buffer 要装的设备活 | 449.8 µs | **~900 µs ⇒ 逼近甚至超过 period**（违反"设备时间 < period"，见 §11.9）|
| TDD 下的空转 | 每 5 ms 有 3 个 UL slot ⇒ **70% 的预留是空的**，但实测"超额申报免费"（§5.4）| 同样空转 |

⇒ **500 µs**。空转不是代价，而"设备时间必须小于 period"是硬约束。

## 11.6 ★ TC 能治什么、**不能**治什么（诚实，不夸大）

| | 结论 | 依据 |
|---|---|---|
| ✅ **能治**：CPU 线程自身被守护进程风暴挤占 | 微基准 2× 超订下唤醒迟到 **103 → 3 µs**；反面教材是 p220/p221：一旦被别的 RT 线程挤，唤醒线程被饿 **100 ms** | §10.55、§10.57 |
| ❌ **不能治**：① 电台/USB 投递晚（样本没到）、② GPU 被 DL 占满、③ 设备排队 | 这三类由看门狗的 ②/① 与 `merged_hop exec/wait` 量到，TC 给不了数据也清不了设备队列 | §10.50/§10.54/§11.1 |
| ★ **本方案的价值不在"治"，而在"不传播"** | 提交节拍固定 ⇒ 一次停顿不再累积到后面每个阶段。今天 `t2f max=6558 µs`、`ul_pipeline max=7707 µs` 里有相当一部分是**传播**出来的 | 本节论点，需 §11.8 的仪器来证实/否证 |

**要量的正是"解耦"本身**：把 P5.0 的节拍锚点（`OCUDU_UL_SLOT_GRID`，今天挂在 CE 地标）**改挂到 commit 地标**上
⇒ 残差应当从"几十~几千 µs"收敛到**µs 级**，且**与设备侧的 `merged_hop exec` 无关**。这就是本方案的判决性读数。

## 11.7 风险与反向臂

1. **不让路就饿死数据源**（§5.1，p220/p221 实测）：窗口外必须睡；`computation < period` 是红线；
   总预留 60% 一个核 ⇒ 腿上必须核对 `gaps=0`、`rx_overflows=0`；
2. **形状合法性**：`computation ≤ constraint < period`（§10.31 的反例 p50 793 / max 7277 µs）；
3. **相位错位会"增加"延迟**（§5.3）：最坏等 `period − computation = 200 µs`。
   ⇒ **反向臂**：故意把相位偏 250 µs，锚点残差必须出现 +250 µs 台阶；
4. **设备时间必须 < period**（§11.9 的否证条件）：若一次提交要装两个 slot 的活（1000 µs 方案），
   或 DL 侧把 GPU 占满，则 period 内装不下；
5. **lead 不足 ⇒ 跳过率上升**：跳过率越过 0.1% 即判 lead 不够（而不是判"方案错"），
   下一轮把 lead 加到 2 个 slot——**这是一个可调的量，不是要推翻方案**。

## 11.8 先补的仪器（**P6.0-SLOT**，loopback 可验）

| # | 量 | 用途 |
|---|---|---|
| 1 | 每 slot 的 **wait / host cpu / device** 三段分开（同 §10.4）| `computation` 的唯一合法来源；把"等"和"做"分开 |
| 2 | **投递延迟分布**（电台 slot 边界 → 样本可读 + 已就位设备）| 定 `lead` |
| 3 | **commit 地标的节拍锚点**（P5.0 改挂）| 判决性读数：残差是否收敛到 µs 级 |
| 4 | **跳过计数 + 每次跳过的原因**（样本未到 / 设备忙）| lead 够不够、设备是否成瓶颈 |
| 5 | **对照腿**（默认关）| 反向臂：不申报时残差必须更大 |

**两条反向臂（必须能打红）**：① 关掉申报（跑默认）⇒ 锚点残差必须显著变大；
② 把 `lead` 设 0（即"等到样本才提交"）⇒ 必须复现今天的**传播**（`max` 回到 ms 级）。

## 11.9 什么会否证本方案

1. **设备时间 ≥ period**（`merged_hop exec` 的 p99 逼近 500 µs，或 DL 竞争把它推上去）⇒ 一个 slot 装不下，
   必须把 hop 拆开或降低 DL 的 GPU 占用；
2. **跳过率 > 0.1%** 且加 lead 到 2、3 个 slot 仍不降 ⇒ 投递延迟本身不可预测（那是驱动问题，不是调度问题）；
3. **锚点残差没有收敛**（挂到 commit 后残差仍是 ms 级）⇒ "解耦"不成立，本方案的价值主张被否证；
4. **红线被踩**（`gaps>0` / `rx_overflows>0` / 任一登记率越界）⇒ 预留挤到了数据源。

## 11.10 分步与回退

| 步 | 内容 | 判据 |
|---|---|---|
| **P6.0-SLOT** | §11.8 的仪器（含两条反向臂），loopback 先验 | 归属算术对账；反向臂打红 |
| **P6.1-SLOT** | **一条线程 + TC(500/300/400) + lead 1 slot + 提交或跳过**，默认关，同腿对照 | 锚点残差收敛；`gaps=0`；跳过 ≤0.1%；四条载体与三条率不劣化 |
| **P6.2** | LLR 之后（LDPC/TB/FAPI）纳入同一条线程或第二条 | 同上 + `ldpc`/`ul_pipeline` 的 p95/p99 |
| **P6.3** | 只为 UL 数据面退役工作窃取池 | 全套 + 长腿 |

**回退**：任一步触红线或价值主张被否证 ⇒ **保持默认关、撤回代码路径**（本线一贯纪律）。
