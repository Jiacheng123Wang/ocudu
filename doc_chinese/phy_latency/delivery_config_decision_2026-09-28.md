# 交付配置的两项裁决 —— 一页决策清单（2026-09-28）

> **背景**：验收腿（`p85`–`p96`）一直用**命令行**带 `--expert_execution.threads.upper_phy.max_pusch_and_srs_concurrency=2`
> 飞行，而**交付配置本身两项都没设**（`rv_sequence` 取默认 `[0]`、并发 auto→**1**）。
> ⇒ 现在**证据描述的不是出厂配置**，二者必须对齐；对齐需要一次配置改动 + **一对重飞**（`default` + `stress`）。
> 证据来源：§6.143⑦（吞吐臂）、§7.5 / §6.127（并发）、§6.22–§6.28（5 s 停顿的修复 A/B）。

## 决策 1：`cell_cfg.pusch.rv_sequence`（当前未设 ⇒ 默认 `[0]`）

| 项 | 内容 |
|---|---|
| **建议** | 设为 **`[0, 2, 3, 1]`**（与 DL 侧默认一致，也是标准 RV 循环） |
| **收益（实测，同一部手机/同一 iperf3/只差这一个变量）** | TCP 收到 **7.39 → 9.93 Mbit/s（+34.4%）**；重传 25.8%→**8.3%**；BLER 33.2%→**7.9%**；有效 bit/RE 1.90→**2.54**；**MAC 新数据→TCP 存活率 78%→92%**；平均 TB 3214→2626 B（更小但活得下来）|
| **机制** | 默认 `[0]` 让 36% 的重传全是 rv0（无增量冗余）⇒ 重传基本白费；`[0,2,3,1]` 让 RV 合并真正生效 |
| **代价 / 风险** | 交付**行为**改变（非探针）⇒ 必须重飞一对验收腿；对 DL 无影响；`rv` 臂那次没有优雅退出（看门狗偶发），但读数不受影响 |
| **需要什么** | 配置文件一行 + 一对腿（`p103`/`p104`）|
| **状态** | ✅ **已写入交付配置（2026-09-28）**：`cell_cfg.pusch.rv_sequence: [0, 2, 3, 1]`（带依据注释）；已验证：parser（`--dryrun` rc=0）、**round-trip 8/8**、`ctest -L phy -j 1` **202/202**。⏳ 待一对腿重新取证 |

## 决策 2：`expert_execution.threads.upper_phy.max_pusch_and_srs_concurrency`（当前未设 ⇒ auto→1）

| 项 | 内容 |
|---|---|
| **现状矛盾** | **全部近期验收证据都是在 conc 2 上飞的**（命令行），而配置解析出 1（§4 的 `[ul_lane_exec]` 实测）⇒ 出厂配置从未被这些腿描述过 |
| **建议** | **写进配置 = 2**（让配置与证据一致） |
| **收益（实测）** | `p76`（conc 1）对比 `p72`/`p75`（conc 2）：**V1 1606.2 → 1399.5 µs（−13%）**；只改等待类量（`wait` 206.5→54.4、`residency` 623.4→495.7、`gap` 125.7→**0.0**）|
| **代价 / 风险** | ★ 历史上 conc 2 关联过 **`s88`/`s88b` 两次复现的 ~5 s 停顿（`gaps=2`）** ⇒ 这正是"P1-8 带一个代价"的由来；其后**修复 A/B**（§6.22–§6.28）落地，**最近 12 条腿（`p85`–`p96`，全部 conc 2）`gaps=0`、池绿、契约 9/9** ⇒ 风险当前**未复现**，但它是**交付行为改变**，需要一对腿在新配置上重新取证 |
| **备选** | 保持配置 1：那就必须**重飞一对 conc 1 的腿**作为证据（V1 预期 ~1600 µs，判据 ≤2150 仍满足，但余量变小）——**不推荐**：等于放弃 −13% |
| **需要什么** | 配置文件一行 + 一对腿（**与决策 1 合并成同一次重飞**）|
| **状态** | ✅ **已写入交付配置（2026-09-28）**：顶层 `expert_execution.threads.upper_phy.max_pusch_and_srs_concurrency: 2`；**运行时已验证**：`[ul_lane_exec] PUSCH/SRS concurrency = 2 (configured; …)`（短跑一次 `gnb -c <配置>` 读出，不必飞腿）。⏳ 待一对腿重新取证 |

## 决策 3：（不动作）接收侧毫秒级尾部停顿 —— 已定价

见 §6.150：交付形态里设备网格是 G1 强制的 ⇒ 这条尾部代价必须付；只影响 V1 的 max/p99（中位不动）。
**唯一要盯的损失通道**（全设备链时接收池可被握满、曾 `dropped=1`）已由 V2 的 `starved_events==0` 覆盖。**机制仍在追**（§6.150⑥ 的 M1/M2/M3），但那不影响本决策。
