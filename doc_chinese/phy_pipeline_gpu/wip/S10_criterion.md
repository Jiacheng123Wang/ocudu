# S10 — 本线的判据（“GPU in the loop 之后，CPU 靠边站”）

## 1. 判据原文（你定的，取代我之前提的“控制 vs 数据”）

> **数据流进入 GPU 之前，CPU 做什么都属于装配，允许；一旦流开始，CPU 只能在出口等，
> 中间的每一次接触都算——无论它搬的是样本、标量还是索引表。**
>
> 主要目的：**一旦 GPU in the loop，CPU 就该靠边站。如果在中间某个时候还是需要 CPU
> （无论是什么），那把数据流从 CPU 挪到 GPU 的意义就不大。**

**为什么它取代了“控制 vs 数据”**：后者会让我们把索引表、标量、参数块逐个争论归类，
而争论的结论还会随实现变化。**位置是客观的、可测的**：接触发生在流的中间，就是缺陷。

## 2. 两个推论（本轮澄清，都很重要）

### 2.1 指挥工作**也算**（裁定修正）

**我曾写成"指挥工作不算"——那是错的，已按裁定修正。**

> **即使是"指挥"/控制，也是一次 "CPU in the loop"，不是真正的 CPU offloading。
> 真正的 CPU offloading 是 CPU 彻底甩手不管。**

**⇒ 判据的完整表述**：一旦数据流进入 GPU，CPU 只做两件事——
**提交**（把这一跳的命令缓冲交出去）和**在出口等待**。**此之外任何逐跳的宿主计算或数据搬运都是缺陷**，
不管它算的是样本、标量还是索引表，也不管它叫"数据"还是"控制"。

**唯一物理上不可移除的**：Metal 的命令缓冲必须由 CPU `commit`。但那是"提交 + 在出口等"，
正是判据允许的两件事。**关键区别是：提交不需要 CPU 知道任何逐跳的内容。**
一旦提交前需要宿主算点什么（例如建索引表），那就是 in the loop。

**⇒ 对已被标计的点，这条裁定的后果**：
`h_starts` 这类"每 dispatch 由宿主算出来的表"**必须搬到设备侧**，不能以"它是控制面"为由豁免。

### 2.2 缓存命中不算——所以“命中成本是否可忽略”不需要回答

稳态的缓存命中（比较两个 plan key）：

- **不接触任何设备内存** ⇒ 按定义不是一次 host↔device 穿越，**计数器不该被调用**；
- **不等待 GPU** ⇒ 不违反“CPU 靠边站”。

**⇒ 实现要求**：缓存命中的路径上**不得调用 `count_host_write()`**——因为那时什么都没有写。
这样稳态下这个数就是**字面的 0**，而不是“很小”。

**⇒ 因此唯一要测的是“首次建表”**：`newBufferWithBytes`（分配 + 真实上传）的成本，
它决定“新分配的第一个 hop”要付多少。

| **0** | 两张索引表**从宿主侧消灭**（不是缓存）：`hop_tables` 按 plan 缓存；**`h_starts` 搬到设备侧**（见下）| 稳态写 → **0**；`_llr`/`_h` 逐字节不变 |

**“计数下降 + `_llr`/`_h` 逐字节不变”**。

### 4.1 `h_starts` 的设备侧化（批次 0 的核心，也是本线第一个真正的 offload 改动）

代码事实（两处，形态不同，必须分开处理）：

| 站点 | 表达式 | 偏移是否规则 |
|---|---|---|
| `ocudu_equalizer_metal_engine.mm:1190` | `starts[k] = h.offset + k * h_symbol_stride` | **规则**：`base + k*stride` |
| 同文件 `:971` | `h_starts[k] = pending[first + k].h.offset` | **可能不规则**：延迟链上不同 submit 可能落在不同分配 |

**⇒ 两条路，按 `:971` 处理**：
1. 若偏移是规则的 ⇒ **整张表消失**，kernel 直接收 `(base, stride)` 两个标量参数；
2. 若确实不规则（不同 submit 不同分配）⇒ **先让它变规则**——保证一个 run 的所有符号落在同一分配里。
   这正是 `:392-398` 那段代码在防的缺陷（"Symbols that happen to sit in different allocations at a
   uniform distance would satisfy the stride test and then be read - and written - past the end"）。
   **一旦规则，表就不需要了。**

**判据**：`h_starts` 的 host→device 写 → **0**，且 `_llr`/`_h` 逐字节不变。

**⚠ 前置**：离线 harness 每进程只跑 1 跳，缓存/稳态看不到效果。**先补多跳离线判据**，
否则改了也证明不了（批次 0 第一次尝试就是这样失败的，见 §5）。

## 5. 批次 0 的第一次尝试：失败与原因（`addf5a436b` 之后，已回退）

**做了什么**：给两张表加**内容做 key** 的缓存，命中路径不调用计数器。
**结果**：数据逐字节不变（27/27 **0 字节** ✓），但**计数一点没降（36 → 36）**。

**两个原因，都不是实现问题**：

1. **`h_starts` 根本不是可缓存的表**——它描述**这一个 dispatch 要处理哪些符号**，
   同一 hop 内多次调用的**内容真的不同** ⇒ 按内容做 key **必然全部 miss**。我的前提错了。
2. **`hop_tables` 的前提是对的，但离线判据看不见**——`ul_chain_replay` **每进程只跑 1 跳**，
   缓存永远是冷的。

**⇒ 结论：障碍是判据，不是实现。** 按本线纪律"每一步都必须能单独判对错"，
**没有判据的改动不该进树**，所以回退到已验证的 `addf5a436b`。

**⇒ 正确顺序：先补多跳离线判据 → 再做 `h_starts` 的设备侧化。**

## 6. 一个必须记住的教训（本线第三次同类）

**一条检查的措辞比它的数字更容易骗人。** `0 host read(s) ... the fused lane (mode=gpu) allows 0`
读起来是车道结论，实际是**一个模块里 4 个标量点**的结论，我据此错误地宣布过里程碑达成
（已在 `S8_contract_met.md` 顶部撤回）。

**⇒ 宣布任何里程碑之前，先问：这条检查覆盖了哪些模块、哪些方向？**
计数器现在把**申报模块**打印在数字下面那一行，就是为了让这个问题有答案。

## 7. 批次 2 的侦察结论（`unpack_engine_group` 回读）

**回读喂给谁**（代码，`:1583`）：

```cpp
const channel_statistics stats = stats_estimator->estimate(stats_in);
```

**⇒ 完整的往返链，每跳一次**：

```
设备产出 h  →  宿主回读 h（unpack_engine_group，DM-RS 符号）  →  宿主算 3 个统计量
                                                              (fd_hz / tau_rms_s / sigma2)
            →  宿主把这 3 个统计量作为 KERNEL 参数传回设备  →  corr kernel 用它们算 rt_corr/rf_corr
```

**这正是判据禁止的东西**：`dev → host → dev` 的完整往返，而且**每跳一次**。
批 0/1 消灭的写只有 2.65/跳、882 字节，而这一条是 **3.10 读/跳、1420 字节，且带着一次宿主计算**。

### 7.1 两条可能的做法

| 做法 | 内容 | 代价 |
|---|---|---|
| **A. 设备侧统计 kernel** | 新增 MSL kernel，从估计/导频算 fd_hz / tau_rms_s / sigma2，结果留在设备侧 | **需要新 kernel**（本线第一批不是宿主重排的改动）|
| **B. 把统计并入 corr kernel 的序言** | 统计量只被用来算 `rt_corr` / `rf_corr` 的权重，所以不必显式算出这三个数——corr kernel 可以**直接从它已经拿到的数据**推权重 | 省一次 dispatch，但改动面更大、更难做 A/B |

**⇒ 建议先做 A**：它是可分的、可判的（新增 kernel 的输出可以与宿主的 `stats_estimator` 逐值对照），
而且做完之后 `dev → host → dev` 这条链就断了。

### 7.2 判据（照旧）

- **读计数 → 0**（现在 3.10/跳）；
- **`_llr`/`_h` 逐字节不变**（27 捕获 + `--repeat 1` vs `20`）；
- 新增：**设备统计量与宿主 `stats_estimator` 的逐值对照**（新 kernel 的正确性判据，避免又一个空门）。
